**需要修改、确认或补证据的问题**

1. **[规格已违反] VibeInsight 项目改名可能丢失原关联。**

   `spec.md:18、33` 要求项目改名后仍识别同一项目及其关联，身份以可持续标识为准。但 `src/smm_hub/vibeinsight.py` 的 `PostgresSource._repo()` 将主机、端口和仓库路径组成项目键，`VibeInsightSync._commit()` 再用该键创建或查找项目。路径变化会形成新的 Hub 项目，旧关联不会自动迁移。验收记录也明确写了“仓库路径变化按新来源身份处理”。

   请使用能够跨改名保持的上游项目标识，并补充改名前后关联与检索验证；如果上游无法提供这种身份，需要维护者先确认收窄 SPEC，再更新 PLAN。仅验证设备项目显示名变更，不能覆盖这项要求。

2. **[规格未覆盖的用户路径缺口] 首次接入缺少数据库账户及授权范围的取得路径。**

   `README.md:56` 要求“准备数据库只读账户”，`TRIAL_GUIDE.md:88–92` 随即要求填写连接参数。材料没有提供申请对象、取得方式或交接要求。对于只有现有 Hub 管理权限的维护者，这些信息无法从当前入口获得。

   **请维护者决定是否将这一步纳入本次变更。** 若纳入，至少补充：向谁取得主机、端口、数据库、用户名及密码；由谁确认该账户获准读取哪些项目；如何确认实际可见范围符合授权。验收条件应包括：首次接入者能够沿文档完成信息交接，并在启用“全部可读取项目”同步前确认范围。此项不能直接算作现有 SPEC 的实现违约。

3. **[已确认的文档错误] Skill 会把项目检索误报为覆盖整个 Hub。**

   `skills/smm-search/SKILL.md:46` 仍写着：

   > If `archive_scope` is `hub`, search covered all devices in the hub. Local project IDs do not filter the hub.

   这与第 39 行的新指引、`spec.md:24`，以及 `src/smm_local/federation.py::search_archive()` 将本地项目映射为远端键并传递项目范围的实现冲突。Agent 可能把 A 及直接关联项目的结果描述为整个 Hub 的结果，影响用户判断搜索是否完整。

   请改为依据返回的 `scope`、`effective_projects` 和回退原因报告实际范围，并补一条项目检索响应到用户说明的核对证据。
