**三、需要处理的问题**

1. **[P1｜已违反规格] VibeInsight 项目改名可能失去原有关联。**

   `spec.md:18、33` 要求项目改名后仍识别为同一项目，身份使用可持续标识。但 `vibeinsight.py:53–56` 以仓库主机、端口和路径构造项目键，`_commit()` 又将该字符串作为 `HubProjects.upsert()` 的 `source_key`。路径变化会创建新项目，原有关系仍绑定旧项目 ID。

   验收记录明确写出“VibeInsight 仓库路径变化按新来源身份处理”，只验证了设备显示名改动。PLAN 虽记录采用 Git 仓库身份，却未说明这一行为与改名要求的差异。

   **需要：**使用稳定的上游项目标识，或提供保留关联的身份迁移机制；若维护者决定路径变化就是新项目，须先明确改名边界、更新 SPEC 并重新确认，再补对应验收。

2. **[P2｜指引冲突] Skill 仍要求把项目检索解释成全设备检索。**

   `skills/smm-search/SKILL.md:39` 新增“以返回的实际项目范围为准”，但第 46 行仍写“`archive_scope=hub` 覆盖所有设备，本机项目 ID 不过滤 Hub”。

   当前 `federation.py` 已将本机项目 ID 转为稳定远端键并发送项目范围。因此 Agent 完成正确检索后，仍可能错误报告搜索覆盖面，误导用户判断是否需要扩大范围。

   **需要：**修改第 46 行，按 `scope`、`effective_projects` 和 `fallback_reason` 解释实际范围；仅全局 Hub 检索才描述为全局覆盖。

3. **[P2｜材料不足] 公开安装入口是否能取得本次实现，无法判断。**

   `README.md:9、38` 和 `TRIAL_GUIDE.md:15、69` 固定安装 `0.3.0`。验收验证的是独立构建 wheel；材料未给出这些公开发行产物与 `c891339` 的对应关系。

   **需要：**补充发行版本及产物对应关系，或说明发布前如何更新安装入口。现有材料不能认定公开包缺少功能，也不足以证明新用户按文档安装后即可使用。
