结论：建议修改后再合并。材料支持主要同步与检索链路已经跑通，但首次配置的用户路径存在未覆盖的阻塞，Skill 仍包含错误的范围说明，VibeInsight 项目改名也未满足规格要求。

1. **先核对 PLAN：主要方案调整已记录，验证材料仍有缺口**

   当前改动覆盖了计划中的 Hub 存储、来源配置、客户端归属补传、CLI/MCP、Skill 和使用指南。新增 `projects.py`、`vibeinsight_settings.py` 等拆分已反映在 PLAN 第 9–11 行。

   从逐项目分页改为 COPY 流、增加项目检查点下界，已在 PLAN 第 20、42–44 行说明调整原因和验证方法；staging 回执也记录了超时、续跑和最终完成结果。这部分不属于未说明的偏差。

   尚需补齐两点：

   - PLAN 第 19 行新增按消息来源项目索引的方案，但未明确说明相对原方案调整的原因。测试展示了共享会话与跨仓库会话的需要，建议将原因写入计划。
   - PLAN 第 50 行要求七项验收附脱敏响应、进度对比等。现有正文主要是“通过”结论和日志摘要，缺少足以独立核对项目集合、引用字段及失败批次进度的实际输出。属于**验收证据不足**，不能据此断言实现失败。

2. **用户路径回放：第一个阻塞发生在取得可用的上游连接信息**

   用户要达到的结果是：在现有 Agent 中按当前项目搜索，同时找到另一台电脑和 VibeInsight 中相关项目的历史，并读回准确原文。

   从当前可见入口逐步回放：

   | 步骤 | 用户操作及前置条件 | 材料能支持的结果 |
   | --- | --- | --- |
   | 找到安装入口 | README 第 9–23 行安装 Skill；已接入 Hub 的用户可继续沿用现有入口 | 安装路径明确 |
   | 部署或确认 Hub | README 第 35–48 行、指南第 64–84 行提供部署与客户端接入步骤 | HTTPS、Hub 凭证及接入方式有说明 |
   | 配置 VibeInsight | 指南第 88–93 行要求 `psql`、数据库地址、数据库名、只读用户名和密码 | **首次无法继续的位置**：材料未说明维护者到哪里取得或确认这些信息，以及怎样取得符合查询要求的只读账号 |

   具体而言，`PostgresSource.validate()` 不只要求能够登录，还要求读取 `fact_events` 的指定字段；指南只写“用 VibeInsight 数据库的只读账户”，没有提供账号申请、授权要求或可查阅的配置来源。staging 回执中的“使用现有凭据”证明验收者已经具备前置条件，不能证明首次配置者能够取得这些条件。

   这是**现有 SPEC 未覆盖的用户路径缺口**，不是已经证明的规格违反。请维护者明确决定是否纳入本次变更。若纳入，应补充连接信息和只读权限的取得或确认路径，并增加验收条件：维护者仅按公开指南，能够准备所需信息、通过权限验证并看到首次同步结果；不必公开任何秘密值。

   在上述条件由管理员另行提供后，后续路径可继续：配置并查看同步状态 → 按指南第 99–105 行列出项目并建立关联 → Agent 解析当前项目并搜索 → 使用返回的 `hub_id`、`hub_message_id` 读取原文。已有集成测试和 staging 回执支持这条后续链路。

3. **已存在的文档行为冲突：Skill 会错误报告搜索范围**

   `skills/smm-search/SKILL.md` 第 39 行已经要求使用 Hub 的有效项目范围，但第 46 行仍断言：

   > If `archive_scope` is `hub`, search covered all devices in the hub. Local project IDs do not filter the hub.

   当前 `federation.py::search_archive()` 会将本地项目转换为稳定远端标识，Hub 再按当前项目及直接关联过滤。这意味着项目检索成功时，Agent 仍可能按第 46 行将结果解释成覆盖整个 Hub，甚至把范围外的未命中误报为不存在。

   这与 SPEC 第 24 行要求报告实际检索项目不一致。应删除或改写旧指引，明确区分 Hub 全局检索、Hub 项目检索和本机回退，并补一份项目检索结果及对应范围说明作为证据。

4. **规格未满足：VibeInsight 项目改名会成为新身份**

   SPEC 第 18 行要求“项目改名后仍能识别同一个项目及其关联”，第 33 行要求持续标识。当前实现却是：

   - `PostgresSource._repo()` 用仓库主机、端口和路径组成项目身份；
   - `VibeInsightSync._commit()` 将该字符串同时作为项目 key 和名称；
   - `HubProjects.upsert()` 仅在相同 `kind/owner/source_key` 下保留项目 ID。

   因而仓库路径改变会生成新项目，原关联不能自动延续。验收记录也明确承认“VibeInsight 仓库路径变化按新来源身份处理”，仅验证了设备项目显示名修改。

   这是**相对已确认规格的行为偏差**，PLAN 中记录使用 Git 仓库身份不能替代规格重新确认。需要选择并完成其一：实现稳定身份及改名后的关联保留；或请维护者确认收窄改名保证，先更新 SPEC，再同步 PLAN、指南和验收条件。
