**一、审查发现**

1. **[P1｜明确违反 SPEC 的调用方指引] Skill 仍要求把 Hub 项目检索解释为搜索全部设备。**

   `skills/smm-search/SKILL.md:39` 已正确说明 Hub 使用当前项目及其直接关联，并要求依据实际范围报告；但第 46 行仍写着：只要 `archive_scope=hub`，搜索就覆盖 Hub 全部设备，本机项目 ID 不过滤 Hub。

   新实现恰好会把本机项目 ID 转换为稳定键，传递给 Hub（`src/smm_local/federation.py`，新增 `_remote_project_key` 和 `search_archive` 项目分支），再由 Hub 返回 `effective_projects`。第 46 行因此与 SPEC 第 24 行、同文件第 39 行冲突。

   受影响的是执行 Skill 的 Agent 及依赖其回答的用户。检索和读取本身仍可完成，但 Agent 可能错误声称已搜索全部设备，影响用户对遗漏结果的判断。

   建议将第 46 行改为依据返回的 `scope`、`effective_projects` 解释范围，并明确本机 ID 经映射参与 Hub 项目筛选。通过条件：项目查询按返回项目集合说明范围，全局查询才说明覆盖全部可检索档案。

2. **[P2｜规格未覆盖的用户路径缺口] 试用指南把已连接 Hub 的用户引向本机 Web 项目关联。**

   `TRIAL_GUIDE.md:38` 无条件建议在 Web「项目」中建立关联；第 107 行则说明 Hub 检索使用汇总端保存的关联。README 第 63 行表明 Web UI 是本机入口，材料没有展示该页面能修改 Hub 关联。

   用户从 README 安装并接入 Hub 后，按指南第 38 行操作，可能成功建立本机关联，却无法改变本次新增的 Hub 检索范围。已有可用路径是第 97–105 行的 Hub 管理 CLI，因此不是功能完全不可用，而是当前指引可能使用户完成错误位置的配置。

   建议在第 38 行区分本机与 Hub，并链接“管理汇总端的项目关联”，说明由 Hub 维护者配置。通过条件：已接入 Hub 的用户能从实际提问说明判断应联系谁、进入哪段操作说明。

3. **[P2｜规格未覆盖的发现缺口] README 的 Hub 主入口没有介绍新增能力和适用角色。**

   README 第 33–50 行介绍多机汇总，其唯一指南链接文字是“证书信任、各平台服务配置、升级和卸载”。这些文字没有提示维护者可以配置 VibeInsight 或跨来源项目关联。新增详细说明实际位于 `TRIAL_GUIDE.md:86–107`。

   该指南有清晰章节，用户跟随现有链接后继续阅读可以找到，所以不能认定入口不可达；问题是主入口没有让目标维护者知道此次能力存在、值得进入该指南。对只沿 README 完成 Hub 部署的维护者，这增加发现难度，不阻断已知能力后的操作。

   建议在 README 多机汇总段补一句能力与维护者职责，并直接链接两个现有章节。通过条件：从 README 可辨认能力、适用角色及下一步入口，无需先知道命令名称。

4. **[P2｜局部前置信息不足] VibeInsight 配置示例没有说明连接值与获准同步范围如何确认。**

   `TRIAL_GUIDE.md:88–95` 已说明需要 `psql`、服务账户执行权限、只读数据库账户及密码，但示例中的主机、数据库、用户名如何取得，以及账户应具备何种数据范围，没有交代。实际验证查询要求读取 `fact_events` 的指定字段（`src/smm_hub/vibeinsight.py`，`PostgresSource.validate`），同步则导入连接可读取的全部项目。

   已持有正确连接信息的维护者可继续；需要申请访问权限的维护者，仅凭这段内容无法确认应申请什么，也无法判断读取范围是否符合 Intent 第 24 行“获准纳入的项目”。只读并不说明获准读取哪些项目。

   建议说明向 VibeInsight 数据库管理员取得参数，并在配置前确认账户的可见项目就是授权同步范围，补充所需表或字段权限说明入口。通过条件：维护者能确认参数来源、读取权限及同步范围。材料未提供其他授权说明，不能进一步断言存在实际越权。
