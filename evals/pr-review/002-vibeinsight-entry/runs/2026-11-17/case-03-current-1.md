### 实现和文档问题

**[P1，已违反预期行为] Skill 仍要求把 Hub 项目检索解释成全设备搜索。**

位置：`skills/smm-search/SKILL.md` 第 39、46 行。

第 39 行新要求使用返回的实际范围；第 46 行却仍写道：

> If `archive_scope` is `hub`, search covered all devices in the hub. Local project IDs do not filter the hub.

当前 `federation.py::search_archive` 已将本地项目转换成稳定身份发送给 Hub；`hub.py::search` 再按当前项目及直接关联过滤。项目检索并不覆盖 Hub 全部设备档案。

这与 SPEC 第 24 行“标明……实际检索的项目”冲突。Agent 若遵循第 46 行，可能把一次范围有限的无结果查询描述为已搜索全部设备。

需要修改第 46 行，明确区分 Hub 全局搜索和 Hub 项目搜索，并以 `effective_projects`、`archive_scope` 和 `fallback_reason` 解释实际范围。

**[P2，需要规格确认] VibeInsight 仓库路径变化是否属于“项目改名”，现有交付口径不明确。**

位置：

- SPEC 第 18、47 行要求项目改名后关联仍有效。
- PLAN 第 20 行采用 Git 仓库身份。
- `PostgresSource._repo` 用主机、端口和路径构造身份，`VibeInsightSync._commit` 将其作为项目键。
- 验收记录明确写“VibeInsight 仓库路径变化按新来源身份处理”，只验证设备项目显示名变更。

因此，路径变化会形成新项目，原关联不会自动迁移。材料不足以判断这是否属于规格允许的身份变化，不能直接认定违反。

需要维护者确认“改名”的适用边界：若包含 VibeInsight 路径改名，应修改身份或迁移方案并补验；若不包含，应在 SPEC 和使用指南明确说明路径变化后的关联处理方式。
