## 2. 发现的问题

### A. Skill 仍指示 Hub 搜索覆盖全部设备，且本机项目 ID 不过滤 Hub

**明确违反本次项目检索语义；主要影响结果解释。**

位置：`skills/smm-search/SKILL.md:46`。

该段仍写：

> If `archive_scope` is `hub`, search covered all devices in the hub. Local project IDs do not filter the hub.

但同文件第39行已要求按当前项目查询，并使用返回的有效范围；实现也通过 `federation.py` 的 `_remote_project_key`、`search_archive` 将本机项目映射为 Hub 项目范围。

受影响的是通过 Skill 搜索的用户和执行搜索的 Agent。用户实际只检索当前项目及直接关联项目时，Agent 可能据第46行声称已覆盖全部设备，或者错误解释项目参数的作用。这违反 SPEC 第24行要求准确标明实际检索项目的意图。

已有可用路径是第39行及返回的 `effective_projects`，因此**不阻断搜索或原文读取**，但会降低答案范围说明的可靠性。

建议删除旧说法，明确 Hub 全局检索与项目检索的区别。通过条件：面对一个只关联部分项目的 Hub 项目响应，Skill 指引能够让 Agent 按 `effective_projects` 报告范围，不声称覆盖全部设备。

### B. VibeInsight 仓库路径变化形成新身份，与“项目改名后关联仍有效”冲突

**明确的规格符合性问题，需要维护者确认行为边界。**

依据：

- SPEC 第18行要求“项目改名后仍能识别同一个项目及其关联”，第33行要求持续标识。
- `vibeinsight.py` 的 `_repo()` 使用仓库主机、端口和路径组成项目键。
- `_commit()` 将该键传给 `HubProjects.upsert()`；后者按 `kind, owner, source_key` 判断项目身份。
- 验收记录明确说明：“VibeInsight 仓库路径变化按新来源身份处理”，只验证设备项目显示名变更。

受影响的是维护 VibeInsight 项目关联的人，以及依赖该关联搜索的用户。仓库路径变化后，新轮次可能进入新项目；原有链接仍指向旧项目，按当前项目搜索不会自动纳入新项目。

已有路径是维护者重新执行项目列表和关联命令，或用户改用全局检索。因此**不阻断全局查找或旧档案读取**，但会中断原有关联范围对新内容的覆盖。

若产品决定仓库路径变化不属于本规格的“改名”，应先明确修改并重新确认 SPEC，再同步计划和说明；否则需要实现稳定身份及相应迁移验收。仅在验收记录中注明该行为，不足以消除规格冲突。
