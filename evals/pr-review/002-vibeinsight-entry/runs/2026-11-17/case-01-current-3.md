### 3. 需要处理的问题

**1. 高优先级｜已违反规格：VibeInsight 项目改名会失去原身份及关联。**

- 规格要求项目改名后仍识别为同一项目及保留关联，身份采用可持续标识（`spec.md:18、33`）。
- `PostgresSource._repo()` 用 hostname、port、repo_path 拼接项目键（`src/smm_hub/vibeinsight.py:44–47`）；`_commit()` 又将该字符串同时作为 `source_key` 和名称交给 `upsert()`（同文件 `:330–332`）。
- 因而仓库路径改变时会创建另一项目，而不是更新原项目名称。固定验收记录也明确承认“VibeInsight 仓库路径变化按新来源身份处理”；设备改显示名的验证无法覆盖这个问题。

**需要修改或确认：** 使用能跨改名保持的上游项目标识，或提供明确的身份迁移机制；补验改名前后项目 ID、关联和检索范围保持一致。如果本次确实排除 VibeInsight 路径变化，须先修改 SPEC 并由维护者重新确认，不能继续把当前行为计为该项全部通过。

**2. 中优先级｜SPEC 未覆盖的用户路径缺口：连接资料和获准同步范围没有取得、确认路径。**

- 第一处阻塞在 `TRIAL_GUIDE.md:88–91`：要求使用只读账户，但没有交代连接资料的提供者、所需源表权限，以及如何核对授权范围。
- `PostgresSource.validate()` 只验证引用列的读取权限（`vibeinsight.py:99–106`）；配置成功后会自动同步全部可读项目。它无法证明账户权限恰好符合 Intent 中“获准纳入”的范围（`intent.md:24`）。
- 固定验收使用现有凭据，证明的是凭据已经具备之后的链路，未证明维护者能独立完成此前步骤。

**请维护者决定是否纳入本次变更。** 若纳入，应补充：连接资料由谁提供、所需表与列权限、如何在启用前确认可读项目符合授权范围；验收应让维护者依据交付文档完成准备与确认，再配置同步。若由外部运维流程承担，应明确列为前置条件并给出取得途径。现有材料不足以判断真实部署是否已具备该流程。

**3. 中优先级｜交付指引矛盾：Skill 仍告诉 Agent，Hub 搜索覆盖所有设备且本地项目 ID 不过滤 Hub。**

- 新指引要求根据 Hub 返回的实际范围报告结果（`skills/smm-search/SKILL.md:39`）。
- 但同文件 `:46` 仍写着：`archive_scope=hub` 就覆盖所有设备，且本地项目 ID 不过滤 Hub。
- 当前 `federation.py` 会把本地项目 ID 转成远端项目键，并发送项目范围。旧指引可能让 Agent 将项目限定的结果错误描述为全局搜索，也可能错误解释未命中结果。

**需要修改：** 第 46 行应以返回的 `scope`、`effective_projects` 和回退原因解释范围，明确区分 Hub 项目检索与全局检索。这也是 PLAN 要求更新 Skill 指引尚未完成的一部分。
