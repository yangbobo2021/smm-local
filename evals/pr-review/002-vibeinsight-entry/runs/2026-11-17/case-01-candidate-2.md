**三、具体发现**

1. **明确的指引冲突：Skill 仍声称 Hub 搜索不受项目范围限制。**

   `skills/smm-search/SKILL.md:39` 新增“Hub 中的项目关联”和实际范围说明，但第46行仍写：

   > “If `archive_scope` is `hub`, search covered all devices in the hub. Local project IDs do not filter the hub.”

   当前实现恰好通过本地项目的稳定远端身份筛选 Hub：`src/smm_local/federation.py` 的 `search_archive` 将项目范围转换为 `device_id`、`project_id`；Hub 再计算直接关联范围。

   受影响的是通过 Skill 搜索的用户。Agent 可能把一次项目范围搜索解释成覆盖整个 Hub，导致用户高估未命中结果的覆盖面。这与 SPEC 第24行要求标明实际检索项目不一致，属于交付指引的明确冲突；材料不足以证明实际回答已经发生误报。它不阻断检索和读取。

   建议删除旧断言，统一要求依据响应中的实际范围和 `effective_projects` 解释覆盖面。通过条件：同一项目查询时，Skill 所指示的范围与 CLI/MCP 响应一致，不再声称所有 Hub 项目均已搜索。

2. **规格未覆盖的路径缺口：现有“建立关联”说明容易把 Hub 用户导向本机关系。**

   `TRIAL_GUIDE.md:38` 告诉用户“也可以在 Web『项目』中建立关联”；而第107行和 Skill 第39行说明在线项目检索采用 Hub 保存的关系。材料没有展示 Web 页面可管理 Hub 关系，新增管理入口则是第99—105行的 Hub CLI。

   受影响的是已接入 Hub、希望扩大当前项目检索范围的用户。已有可用路径是继续阅读到指南第97行，由维护者使用 Hub CLI；因此不能认定操作被阻断。但用户可能先在 Web 建立本机关联，在线检索范围仍不改变，增加排查和往返成本。

   建议在第38行附近区分本机关联与 Hub 关联，并链接现有管理小节。通过条件：从“实际提问”读到关联说明时，用户能判断自己的部署适用哪个入口，并沿链接找到 Hub 管理命令。是否纳入本次，由维护者决定。

3. **规格未覆盖的发现缺口：主入口没有介绍新增能力及适用对象。**

   README 第33—50行已有通往完整指南的路径，指南第86—107行也已提供详细操作，因此不应报告为“没有文档”或“无法开始”。问题是 README 的能力介绍和链接上下文没有告诉维护者：这里还可以接入 VibeInsight、管理跨设备和跨来源项目关联。

   这主要增加发现难度，不阻断已经知道能力和章节位置的维护者。

   建议在现有多机汇总入口或其他清晰可达入口增加一句适用场景，并使用能识别目标任务的链接文字指向已有章节，无需另写一套教程。通过条件：只从主入口出发，维护者能找到来源配置和项目关联说明；检索用户能知道应向维护者请求关联。是否纳入本次，由维护者决定。
