**1. [P1] Skill 对 Hub 检索范围的旧指令与新行为冲突**

位置：`skills/smm-search/SKILL.md:39、46`。

第 39 行已经要求按当前项目及 Hub 直接关联检索，并依据返回范围报告；第 46 行仍明确说：只要 `archive_scope` 为 `hub`，就覆盖 Hub 全部设备，本机项目 ID 不过滤 Hub。

实际实现中，`src/smm_local/federation.py::search_archive` 会把本机项目映射成稳定标识传给 Hub；`src/smm_hub/hub.py::search` 据此过滤并返回 `effective_projects`。因此，Agent 完成正确查询后，仍可能依据第 46 行错误报告“已搜索全部设备”，使用户把项目范围内的未命中误认为全局没有记录。

已有可用路径是第 39 行及响应中的实际范围，查询本身没有被阻断。问题限定为 **Agent 指令冲突及结果范围误报**，直接影响 SPEC 第 24 行要求的实际检索范围展示。

建议修正第 46 行，区分 Hub 项目查询、Hub 全局查询和本机回退。通过条件：项目查询返回 A、B 时，Agent 只报告 A、B；全局查询才报告全局，断线时报告本机全局和原因。

**2. [P2] 已展示的 VibeInsight 配置入口没有说明连接值的取得和确认方式**

位置：`TRIAL_GUIDE.md:88–95`；`src/smm_hub/hub_admin.py::add_arguments`。

维护者进入该节后，知道需要 `psql`、只读账户和密码，也获得了完整命令形式。但命令直接使用 `db.example.net`、`vibeinsight`、`reader`，没有明确说明这些是示例，以及实际主机、数据库、账户应向谁取得、如何确认对应目标 VibeInsight 实例及获准读取范围。CLI 对 `--host`、`--database`、`--user` 也没有补充帮助。

这不是证明同步不能执行：已有正确连接资料的管理员可以完成配置，配置命令也会验证读取权限。缺口是 **当前局部步骤对尚未持有连接资料的维护者不充分**；权限验证不能替代目标实例和授权范围确认。尤其配置后会拉取账户可读取的全部项目（第 95 行），这些值决定实际归档范围。

这是 SPEC 未明确覆盖的使用路径缺口。建议补充示例值说明、资料提供方及范围确认要求。通过条件：维护者能为每个必填值说明含义、取得渠道，并确认账户可读范围就是预期同步范围，再执行配置。无需额外建设凭据申请系统。

**3. [P2，建议纳入] 普通用户的项目关联指引未区分本机与 Hub**

位置：`TRIAL_GUIDE.md:38、97–107`。

第 38 行直接告诉用户可在 Web「项目」建立关联；第 107 行则说明 Hub 查询使用汇总端关系。实现也确实分别使用本机关系和 Hub 关系。因此，已接入 Hub 的用户沿“实际提问”入口操作时，容易在本机 Web 建立关系后，期待它影响在线 Hub 查询。

已有清晰可达的替代路径：继续阅读同一指南的“管理汇总端的项目关联”，由管理员通过 Hub CLI 配置。因此不是整体操作被阻断，而是 **局部指引未限定适用档案，增加误操作和排查成本**。

这属于规格未覆盖的说明缺口。建议第 38 行注明 Web 关联适用于本机档案，并指向 Hub 关联章节。通过条件：在线 Hub 用户能够从该处判断关系应由谁、在哪里配置，并用返回的 `effective_projects` 确认生效。
