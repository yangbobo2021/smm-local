### 2. 发现的问题

**问题 1｜规格冲突：VibeInsight 仓库改名或路径变化后，原关联不能延续。**

- 约定：`spec.md:18、33` 要求项目使用可持续身份，项目改名后仍能识别同一项目及其关联，没有限定仅适用于设备项目。
- 实现：`src/smm_hub/vibeinsight.py` 的 `PostgresSource._repo()` 用主机、端口和仓库路径组成项目键；`VibeInsightSync._commit()` 又将该键传给 `HubProjects.upsert()`。后者按 `(kind, owner, source_key)` 判断身份。
- 实际证据：验收记录明确“VibeInsight 仓库路径变化按新来源身份处理”，而改名验收只证明了设备项目显示名变化。

因此，已关联的 VibeInsight 仓库改变路径后，新事件会进入另一个 Hub 项目，原关联不会自动覆盖它。维护者仍可通过全局搜索找到新内容，再列出项目并重新关联；受阻的是“原关联持续有效”的预期，并非所有检索。

建议使用可持续的上游项目标识，或明确调整规格、说明需要重新关联并重新确认。通过条件：关联一个 VibeInsight 项目，改变其名称或路径后追加事件，原关联起点仍能检索新增内容；若决定不支持，应明确记录边界及恢复步骤。

**问题 2｜局部指引冲突：Skill 仍指示 Hub 搜索覆盖全部设备，可能错误报告实际范围。**

- `skills/smm-search/SKILL.md:39` 新增了正确说明：Hub 项目检索使用 Hub 的直接关联，并应按返回范围报告。
- 同文件 `:46` 却仍写着：`archive_scope` 为 `hub` 就表示搜索覆盖 Hub 全部设备，且本机项目 ID 不过滤 Hub。
- 实现中，`src/smm_local/federation.py::search_archive()` 已将本机项目转换为远端项目键并发送；`src/smm_hub/hub.py` 的 `/v1/search` 按该范围过滤并返回 `effective_projects`。

Agent 完成项目检索后会同时看到两套相反的解释，可能将 A 及直接关联的结果报告为整个 Hub 的搜索结论。查询和精确读取仍有可用路径，问题集中在范围解释和回答可靠性。

建议更新第 46 行，区分 Hub 全局检索、Hub 项目检索和本机回退。通过条件：面对 Hub 返回的项目范围，Skill 中不存在要求报告“全部设备均已搜索”的冲突指令。

**问题 3｜规格未覆盖的使用路径缺口：普通使用者被引向本机 Web 关联，不能据此完成 Hub 关联目标。**

- `TRIAL_GUIDE.md:38` 面向实际提问者，说明项目检索包含直接关联，并指向 Web「项目」建立关联。
- 但本次 Hub 检索实际读取 Hub 保存的关联，见 `skills/smm-search/SKILL.md:39` 和 `TRIAL_GUIDE.md:107`；管理入口是 `TRIAL_GUIDE.md:97–105` 的 Hub CLI。

沿第 38 行操作的用户可能成功建立本机关联，却仍不能在在线 Hub 项目检索中纳入目标项目。已有可用路径是指南后部的 Hub 项目管理章节，因此这是局部指引不足和额外发现成本，不是功能完全不可用。

建议在第 38 行区分本机与 Hub，并链接到 Hub 管理章节，说明由维护者配置。通过条件：从“实际提问”章节出发，使用者能判断关联应保存在哪里、自己应操作还是联系维护者，并找到正确入口。
