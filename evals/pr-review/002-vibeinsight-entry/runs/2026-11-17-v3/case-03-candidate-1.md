**1. 项目改名的身份保证只覆盖设备项目，未覆盖 VibeInsight 项目**

- 依据：SPEC 第18、33行要求项目改名后仍能识别同一项目及关联，并以可持续标识识别项目。
- 实现：`src/smm_hub/vibeinsight.py` 的 `_repo()`（第49–53行）用 hostname、port、repo_path 拼接项目身份；`_commit()` 把该字符串同时作为 `source_key` 和名称交给 `upsert()`。路径变化会创建新项目，原关联不会自动转移。
- 验收记录明确说明：“VibeInsight 仓库路径变化按新来源身份处理，设备项目显示名变更已验证。”因此不能用“同名、改名和已有历史通过”概括两类项目的改名保证。
- 影响：已关联的 VibeInsight 仓库路径改变后，新增记录可能归入新项目，从原设备项目发起的关联检索不再覆盖它。已有档案和全局检索仍可使用；维护者可重新建立关联。
- 分类：**明确的规格差异**。PLAN 第20行虽说明采用 Git 仓库身份，但没有明确说明这是对改名保证的收窄，SPEC 也未更新。
- 通过条件：提供稳定身份及路径变更后的关联保持验证；或者先由维护者确认收窄 SPEC，明确路径变更的行为、识别方式和重新关联步骤，再同步 PLAN 与验收结论。

**2. Skill 中仍有与新项目检索行为冲突的指令**

- 依据：`skills/smm-search/SKILL.md:39` 已要求按当前项目查询 Hub，并依据返回的实际范围报告结果；第46行却仍说，只要 `archive_scope` 为 `hub`，搜索就覆盖 Hub 的所有设备，并称本机项目 ID 不过滤 Hub。
- 实现：`src/smm_local/federation.py` 的 `search_archive()` 已把本机项目映射为稳定远端键，再传给 Hub；`src/smm_hub/hub.py` 的 `search()` 按当前项目及直接关联过滤。
- 影响：Agent 可以正确完成项目搜索和读取，但随后可能把有限范围的结果描述成覆盖整个 Hub，误导用户判断证据覆盖范围。第39行提供了正确路径，因此这是**局部指引冲突，不是搜索操作阻断**。
- 建议及通过条件：第46行区分 Hub 全局检索与 Hub 项目检索，以 `scope`、`effective_projects` 和回退信息说明实际范围。分别回放项目、全局、断线三种响应，指令应得到一致且准确的范围描述。
- 分类：SPEC 第24行要求正确呈现实际检索项目；实现有支持，Skill 的消费指引仍不一致。

**3. VibeInsight 配置入口已可发现，但连接前置条件的取得说明不足**

从 README 第50行可以到达 `docs/index.md:7`，再进入 `TRIAL_GUIDE.md:86–95`。该路径明确介绍了能力、对象、依赖、配置命令和状态确认，不能认定本功能缺少入口。

但进入配置步骤后：

- `TRIAL_GUIDE.md:88–93` 要求只读账户并给出 `--host`、`--port`、`--database`、`--user`，未说明示例值需要替换成哪套 VibeInsight 数据库的信息、由谁提供，以及账户应获准读取哪些数据。
- `PostgresSource.validate()` 实际要求读取 `fact_events` 的一组指定字段；配置命令验证的是读取能力，没有验证账号本身仅有只读权限。只读事务也不能替代账号权限约束。
- 已取得正确连接信息的维护者有完整可用路径：安装 `psql` → 配置 → 查看状态 → 搜索并读回。材料不足以证明所有维护者都会被阻断；可以证明的是，这个局部步骤不能独立指导尚未取得连接资料的人完成准备。

分类：**SPEC 未覆盖的前置条件说明缺口**。建议补充向 VibeInsight 数据库维护者索取的连接信息、获准项目范围及必要读取权限，并说明如何确认账户符合只读要求。通过条件是维护者能据此取得并核对真实参数，无需猜测示例值或从源码反推权限。是否纳入本次变更交维护者决定。
