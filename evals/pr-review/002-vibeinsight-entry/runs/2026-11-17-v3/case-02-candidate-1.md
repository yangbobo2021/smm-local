审查结论：实现与更新后的 PLAN 大体一致，历史验收覆盖了主要功能，但仍有两处使用指引缺口需要处理。当前材料不能支持“待审提交已完整通过全部验收”的结论；以下未重跑测试，仅回放提供的材料。

### 发现的问题

**1. P2：Skill 对 Hub 项目范围给出互相冲突的指引，可能让 Agent 错报搜索覆盖范围。**

位置：`skills/smm-search/SKILL.md:39、46`。

第 39 行新增说明：Hub 按当前项目和 Hub 直接关联执行查询，应依据返回的实际范围报告。第 46 行仍明确声称：

> If `archive_scope` is `hub`, search covered all devices in the hub. Local project IDs do not filter the hub.

这与当前实现不符。`src/smm_local/federation.py` 的 `search_archive()` 会将本机项目 ID 转换成稳定远端标识，随设备 ID 发给 Hub；`src/smm_hub/hub.py` 的 `/v1/search` 据此筛选项目并返回 `effective_projects`。

受影响的是通过 Skill 搜索项目历史的 Agent 和用户。操作本身有可用路径：第 39 行足以指导正确发起项目搜索，返回值也提供了实际范围。但 Agent 随后读到第 46 行，可能把项目内的空结果解释成已覆盖整个 Hub，或错误说明其他设备的全部历史均已搜索。这是**局部指引冲突和结果解释风险，并非检索操作被阻断**。

这同时违背 SPEC 第 24 行关于报告实际项目范围的要求，以及 PLAN 第 11 行更新 Skill 指引的目标。

建议改写第 46 行，分别说明 Hub 项目检索、Hub 全局检索和本机回退。通过条件：沿 Skill 执行项目查询后，Agent 报告的范围与 `effective_projects` 一致；项目内未命中时，不声称已经搜索整个 Hub。

**2. P2：VibeInsight 配置入口没有充分说明数据库参数及只读账户所需的数据访问约定。**

位置：`TRIAL_GUIDE.md:88–95`；`src/smm_hub/vibeinsight.py` 的 `PostgresSource.validate()`、`_events_sql()`。

指南已明确需要 `psql`、服务账户执行权限和数据库只读账户，也提供了完整配置命令。但展示给维护者的局部内容没有说明：

- `--host`、`--database`、`--user` 应从谁或何处取得并确认，示例数据库名是否只是占位值；
- 该账户必须能访问包含指定事件结构的 `fact_events`，以及非默认 schema 如何使该表可被解析；
- 如何确认账户可见范围恰好是获准同步的项目范围。

实现使用未限定 schema 的 `fact_events`，验证时读取明确的一组列；配置成功后会同步账户可读取的全部项目。因此，“有一个只读账户”不足以判断该账户是否适用于这个入口。连接或表权限错误虽能被验证拒绝，但维护者仍缺少准备正确账户和定位问题的信息。

已有可用路径是：由熟悉数据库部署的人提前提供正确连接、表可见性和授权账户，再执行配置及状态检查。不能据此断言所有维护者都会被阻断；可证明的是**该配置步骤的前置条件说明不足，会增加交接和排障成本**。材料未展示其他数据库接入说明，不能确认是否存在补充入口。

这是 SPEC 未明确覆盖的使用路径缺口。建议补充简短的连接信息交接清单、所需表及权限约定，并说明全部可读项目都会被导入。通过条件：目标维护者能依据指南取得并确认参数、验证目标表可读和授权范围，再完成配置；错误数据库、表不可见或权限不足时能找到对应处理方向。是否纳入本次变更由维护者决定。
