审查结论：建议修改后再合并。主要实现与验收证据覆盖了约定的同步、关联检索和读取行为，但仍有一处规格偏差及两处使用指引冲突。

本次目标是让已接入 Hub 的用户通过现有 CLI/MCP 搜索 VibeInsight 和直接关联项目，并让 Hub 维护者配置只读来源、管理关联。范围包括历史补拉、增量续跑、设备归属补传、引用读取和断线回退；不包括发现没有新增事件的历史正文改写。

### 1. [P2｜明确规格偏差] VibeInsight 项目改名后的身份与关联不能保持

**依据：** SPEC 第18行要求“项目改名后仍能识别同一个项目及其关联”，第33行要求身份使用可持续标识。实际 `src/smm_hub/vibeinsight.py` 的 `PostgresSource._repo()` 用仓库主机、端口和路径生成项目身份，`VibeInsightSync._commit()` 又将该值同时作为 `source_key` 和显示名传给 `HubProjects.upsert()`。验收记录明确注明“VibeInsight 仓库路径变化按新来源身份处理”。

因此，仓库路径变更会建立新项目，原有关联不会自动覆盖新身份下的消息。维护者仍可通过 `project list/link` 手动建立新关联，全局搜索也仍可使用，但这不能满足规格承诺的改名后关联持续有效。

PLAN 第20行记录了仓库身份方案，却没有说明它对已确认改名行为的改变。应实现稳定身份，或按 AGENTS 第28—31行先明确修改规格及验收条件。通过条件应覆盖：已关联的 VibeInsight 项目改名后，新增消息仍进入原关联检索范围。

### 2. [P2｜使用路径缺口] Skill 对 Hub 项目范围给出相互冲突的指令

**位置：** `skills/smm-search/SKILL.md:39`、`:46`。

第39行正确要求按当前项目搜索，并使用 Hub 返回的有效范围；第46行仍称：

> “If `archive_scope` is `hub`, search covered all devices in the hub. Local project IDs do not filter the hub.”

实际 `src/smm_local/federation.py::search_archive()` 已把本地项目 ID 转换为远端项目标识，Hub 再按当前项目及直接关联过滤。Agent 按第46行解释结果时，可能把一次项目检索报告成覆盖整个 Hub，夸大“未找到”的证据范围。

搜索和读取操作已有可用路径，问题在结果解释，而非操作阻断。建议区分 Hub 全局检索与项目检索，并统一要求依据 `scope`、`effective_projects` 和回退信息报告范围。通过条件是同一次项目查询不会再被 Skill 指引解释为全局查询。

### 3. [P2｜规格未覆盖的指引缺口] 既有指南仍把本机 Web 关联作为项目检索的管理入口

**位置：** `TRIAL_GUIDE.md:38`、`:99–107`。

第38行告诉用户：

> “也可以在 Web「项目」中建立关联。”

新增第107行则说明，连接 Hub 时，CLI/MCP 查询的是 **Hub 保存的关联**。从“实际提问”入口进入的用户可能按第38行完成本机关联，再发起默认的在线项目搜索，结果却没有包含目标项目。

已有正确替代路径：README 第52—57行提供了新能力入口，指南第99—105行也明确说明如何列出 Hub 项目 ID、建立和解除关联。因此不能判定整体能力不可发现；能够确认的是第38行这个局部入口缺少适用范围，增加了误配置和排查成本。

建议在该处区分本机关联与 Hub 关联，并链接到对应管理章节。通过条件是用户能在选择管理入口前判断：本次搜索使用哪份关联，以及修改后应通过什么查询确认生效。
