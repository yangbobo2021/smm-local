结论：建议修改后再合并。材料证明核心同步、关联检索和精确读取已有较充分的验收，但存在一项规格偏差和两处使用指引冲突。

本次约定的结果是：Hub 自动归档只读连接可访问的 VibeInsight 项目及新增轮次；维护者统一管理跨设备、跨来源的双向直接关联；现有 CLI/MCP 按当前项目及直接关联检索，并保留可追溯引用。影响汇总端维护者、已接入 Hub 的用户，以及消费 Skill 指令的 Agent。范围包括历史归属补传、旧客户端兼容和断线回退；不包括无新增事件的历史正文改写。

1. **[P1，明确违反规格] VibeInsight 仓库路径变化后，项目身份和既有关联不能延续。**

   位置：`src/smm_hub/vibeinsight.py` 的 `PostgresSource._repo()`、`VibeInsightSync._commit()`；`src/smm_hub/projects.py` 的 `upsert()`。

   实现把仓库主机、端口和路径拼成项目身份，再以该字符串作为 `source_key` 创建项目。仓库路径变化会创建新项目，关联仍指向旧项目。因此，用户原先从设备项目 A 通过关联搜索 VibeInsight 项目 C，路径变化后的新增对话不会自动进入 A 的范围。

   这与 SPEC 第18行“项目改名后仍能识别同一个项目及其关联”及第33行“项目身份以可持续标识为准”不一致。验收记录明确写明“VibeInsight 仓库路径变化按新来源身份处理”，只验证了设备项目改显示名，不能据此宣告验收项4完整通过。

   PLAN 第20行已经描述采用 Git 仓库身份，但没有解决这项规格冲突。按 `AGENTS.md:28–31`，应实现可持续身份或显式迁移关系；若决定将仓库路径变化排除在改名保证之外，应先修改并重新确认 SPEC。通过条件应包含：关联后改变 VibeInsight 项目名称或路径，旧关联仍覆盖其新增轮次，或按重新确认的边界明确验收。

2. **[P2，规格未覆盖的指引冲突] Skill 仍要求 Agent 把 Hub 项目检索解释成全设备检索。**

   位置：`skills/smm-search/SKILL.md:39` 与 `:46`。

   第39行新增指引正确要求使用 Hub 返回的实际项目范围；第46行却仍写着：

   > “If `archive_scope` is `hub`, search covered all devices in the hub. Local project IDs do not filter the hub.”

   实际代码在 `src/smm_local/federation.py` 的 `search_archive()` 中，把本机项目 ID 转为远端键，并发送设备和项目范围；Hub 随后只检索当前项目及直接关联。Agent 同时遵循两处指令时，可能将一次受限查询错误报告为覆盖整个 Hub，影响用户对结果完整性的判断。

   搜索和读取入口本身可用，第39行也已经提供正确说明；问题限定在范围解释。建议第46行区分 Hub 全局、Hub 项目和本机回退，并以 `scope`、`effective_projects`、`fallback_reason` 为准。通过条件：Agent 对三类响应给出的范围说明分别与实际集合一致。

3. **[P2，规格未覆盖的使用路径缺口] 试用指南仍把本机 Web 关联入口作为项目检索的通用配置方法。**

   位置：`TRIAL_GUIDE.md:38`、`:99–107`。

   第38行告诉用户：

   > “也可以在 Web「项目」中建立关联。”

   但本次变化使已连接 Hub 的项目查询使用 **Hub 保存的关联**。用户从“实际提问”一节按提示在本机 Web 建立关系后，在线查询不会因此扩展 Hub 范围，容易出现“已经关联仍搜不到”的结果。

   后面的第99–107行提供了可用的 Hub CLI 管理路径；`README.md:50 → docs/index.md:8 → TRIAL_GUIDE.md` 的导航也确实能发现它，因此不能认定整体操作路径被阻断。具体缺口是第38行没有说明适用档案，也没有引导 Hub 用户交由维护者配置。

   建议在该处区分本机关联与 Hub 关联，并链接现有管理章节。通过条件：用户从“实际提问”开始，能够确定该在哪里建立关系，配置后的有效项目集合与预期一致。
