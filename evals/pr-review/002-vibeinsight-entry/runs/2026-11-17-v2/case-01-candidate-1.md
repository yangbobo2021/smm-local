1. **[P1，明确规格偏差] VibeInsight 项目路径变更会丢失原项目关联。**

   位置：`src/smm_hub/vibeinsight.py` 的 `PostgresSource._repo()`、`VibeInsightSync._commit()`；`src/smm_hub/projects.py` 的 `upsert()`。

   `_repo()` 用仓库主机、端口和路径组成项目身份，`_commit()` 再将该字符串同时作为项目键和名称保存。仓库路径改变后会创建新项目，原有关联仍指向旧项目，按当前设备项目搜索无法自动纳入新路径下的对话。

   SPEC 第18、33行要求项目改名后仍能识别同一项目及其关联，并采用可持续标识。验收记录明确写明“VibeInsight 仓库路径变化按新来源身份处理”，但改名验收仅验证了设备显示名。PLAN 第20行补充了仓库身份方案，没有说明这是对上述行为的限制，也没有对应的 SPEC 调整。

   已归档内容仍可通过旧关联或全局检索找到，因此影响是关联检索不能持续覆盖新记录。应采用稳定的上游身份或提供显式迁移方式；若上游不能支持，应交维护者确认并修订规格。通过条件是：关联后的 VibeInsight 项目发生受支持的改名操作，新增记录仍能从原关联起点检索。

2. **[P2，使用路径指引冲突] Skill 仍断言 Hub 不按项目过滤。**

   位置：`skills/smm-search/SKILL.md:39`、`:46`。

   第39行已要求按 Hub 关联及返回的有效范围报告结果；第46行却仍写：

   > “If `archive_scope` is `hub`, search covered all devices in the hub. Local project IDs do not filter the hub.”

   实际实现由 `federation.py::search_archive()` 将本机项目映射为远端键，再由 Hub 按项目及直接关联过滤。Agent 即使正确完成查询，也可能据第46行把局部结果报告成全 Hub 搜索，误判未命中的历史不存在。

   查询和读取入口本身可用，问题在范围解释。应统一为依据 `scope`、`effective_projects` 和回退原因报告；通过条件是项目查询不会被描述为全局查询，只有全局请求才作全局解释。

3. **[P2，规格未覆盖的使用路径缺口] 通用提问指南把 Hub 用户引向本机 Web 关联。**

   位置：`TRIAL_GUIDE.md:38`、`:97–107`。

   第38行向用户说明项目检索时，建议“也可以在 Web『项目』中建立关联”；新增第107行则说明在线 CLI/MCP 使用 Hub 保存的关联。按前一处指引建立本机关联，不能完成在线 Hub 关联检索目标。

   第97–105行已有可用的 Hub CLI 路径，并说明项目 ID 从 `project list` 取得，这部分足够支持管理员操作。具体缺口是第38行没有说明适用范围，也没有跳转到该路径；不能据此认定整个功能不可发现。

   建议在第38行区分本机与 Hub 关联，并链接“管理汇总端的项目关联”。通过条件是：已接入 Hub 的用户从“实际提问”开始阅读，能判断应由谁、在哪里配置关系，并找到项目 ID 的取得方式。是否纳入本次变更由维护者决定。
