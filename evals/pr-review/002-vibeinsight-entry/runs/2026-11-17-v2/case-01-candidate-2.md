结论：建议修改后再合并。材料支持主要同步、检索与恢复路径已实现，但仍有一项规格偏差和两处使用指引缺口。

本次约定的结果是：Hub 自动归档 VibeInsight 可读项目，现有 CLI/MCP 按当前项目及 Hub 直接关联检索，并能精确读取原文。受影响者包括搜索历史的用户、消费工具结果的 Agent，以及配置来源和关联的 Hub 维护者。范围限于直接关联、新增事件驱动的增量同步和现有单用户模式；历史消息原地改写不在范围内。

1. **[P1，明确规格偏差] VibeInsight 项目改名后的身份与关联没有得到保持。**

   SPEC 第18、33行要求项目改名后仍能识别同一个项目及其关联，并以持续标识确定身份。实际实现中，`src/smm_hub/vibeinsight.py` 的 `_repo()` 用主机、端口和仓库路径构造项目身份，`VibeInsightSync._commit()` 又将该值作为 `HubProjects.upsert()` 的 `source_key`。仓库路径改变后会创建新项目，原来的关联仍指向旧项目。

   验收记录明确说明“VibeInsight 仓库路径变化按新来源身份处理”，但只验证了设备项目显示名变化。PLAN 第20行记录采用 Git 仓库身份，没有说明这与项目改名约定的关系，也没有对应的 SPEC 调整。

   已归档内容仍可从旧项目或全局搜索找到；具体影响是改名后新增内容不会自动进入原关联范围。应使用可持续身份保留关联，或先由维护者确认收窄规格。通过条件应包括：已关联的 VibeInsight 项目改名后追加事件，仍能从原关联起点搜到，且身份、旧引用和关联保持有效。

2. **[P2，明确指引冲突] 搜索 Skill 仍告诉 Agent：Hub 不受本地项目 ID 筛选。**

   `skills/smm-search/SKILL.md` 第39行新增说明，要求按当前项目查询，并以 Hub 返回的有效范围报告结果；但第46行仍写着：

   > “search covered all devices in the hub. Local project IDs do not filter the hub.”

   实际 `src/smm_local/federation.py::search_archive()` 已将本地项目 ID 转成稳定键，并向支持 `projects` 能力的 Hub 发送项目范围。Agent 依照第46行解释结果时，可能把项目范围的搜索误报为全局覆盖，使用户错误判断遗漏范围。

   第39行和返回的 `effective_projects` 已提供正确路径，因此这是解释冲突，并非搜索操作阻断。应让第46行区分项目检索、全局检索及旧 Hub 的兼容行为。通过条件是同一 Skill 对这些响应给出一致且准确的范围说明。

3. **[P2，规格未覆盖的使用路径缺口] 现有提问入口仍引导用户在本机 Web 配置关联，未说明它不能配置 Hub 关联。**

   `TRIAL_GUIDE.md` 第38行告诉用户，跨项目时“也可以在 Web『项目』中建立关联”；新增第99—107行则说明，在线项目检索使用 Hub CLI 配置的关联。`README.md` 第84行同样只笼统描述“直接关联”。

   用户从“实际提问”章节进入，在本机 Web 建立关联后，可能期待在线搜索扩展范围；实际在线请求由 Hub 保存的关系决定。新增 Hub 管理章节确实提供了可用操作：先列出项目，再以返回的 ID 建立关联，因此不能判断整个操作路径不可完成。已能确认的问题是局部入口未交代关联的作用位置，增加了误配和排查成本。

   建议维护者决定是否在本次补充一句本机与 Hub 关联的适用条件，并从第38行链接到 Hub 管理章节。通过条件是用户能够从提问入口判断在哪里配置当前搜索所使用的关联，并通过返回的有效项目集合确认生效。
