结论：实现与验收材料基本覆盖同步、项目关联、检索及读取目标，但仍有两处直接影响使用指引的冲突，以及一处需要维护者确认的规格偏差。建议处理后再合并。

本次约定的结果是：Hub 自动归档连接可读取的全部 VibeInsight 项目；维护者通过 Hub CLI 管理直接、双向的项目关联；已接入的客户端通过现有 CLI/MCP 按当前项目检索，并保留可追溯引用。影响对象包括检索用户、Hub 管理员，以及消费项目范围和来源字段的 Agent。生产部署、历史消息原地修改的自动刷新不在已验证范围内。

1. **[P2，使用路径缺口] Skill 同时要求按 Hub 实际项目范围报告，又断言 Hub 搜索覆盖所有设备，可能让 Agent 错报检索范围。**

   `skills/smm-search/SKILL.md:39` 已正确要求传入当前项目，并依据返回的有效范围报告；但第 46 行仍写着：

   > If `archive_scope` is `hub`, search covered all devices in the hub. Local project IDs do not filter the hub.

   实际实现中，`src/smm_local/federation.py::search_archive` 会将本机项目转换为稳定标识传给 Hub，Hub 再按当前项目及直接关联过滤。因此 `archive_scope="hub"` 只表示执行档案，并不代表搜索覆盖所有设备的全部项目。

   已有正确路径是第 39 行和响应中的 `effective_projects`，所以这不会阻断查询；具体后果是 Agent 可能把项目检索无命中解释为整个 Hub 都没有相关历史。建议删除或改写第 46 行，并保留旧 Hub 不支持项目范围时的兼容说明。通过条件：项目检索与全局检索的报告分别符合实际响应，不再仅凭 `archive_scope` 推断覆盖范围。

2. **[P2，使用路径缺口] 指南仍把 Web 项目关联作为通用操作入口，未说明它不能配置本次 Hub 检索使用的关系。**

   `TRIAL_GUIDE.md:38` 告诉用户：

   > 也可以在 Web「项目」中建立关联。

   但新增的第 99–107 行说明，在线项目检索使用 **Hub 保存的关联**，应通过 `smm-hub hub project list/link/unlink` 管理；Skill 第 39 行也采用这一规则。实现中的 `HubProjects.effective` 读取 Hub 关系，没有材料显示本机 Web 的关联会同步到 Hub。

   因而，已配置 Hub 的用户沿第 38 行操作，可能成功建立本机关联，却仍搜不到目标项目。新增管理员 CLI 路径是可用的，并且已经说明项目 ID 从哪里取得；缺口在于旧入口没有限定适用档案，也没有引向正确入口。建议在第 38 行区分本机与 Hub 关联，并链接本指南的“管理汇总端的项目关联”。通过条件：用户从该处能判断应在哪个档案建立关系，并找到相应操作说明。

3. **[P2，规格偏差] VibeInsight 仓库路径变化会创建新项目身份，与规格未限定来源的“改名后关联有效”存在冲突。**

   `spec.md:18、33` 要求项目使用持续身份，项目改名后仍能识别原项目及关联；验收项 4（第 47 行）也要求目标项目改名后关联有效。

   实际上，`src/smm_hub/vibeinsight.py::PostgresSource._repo` 用仓库主机、端口和路径组成项目标识，`VibeInsightSync._commit` 又将该值同时作为 `source_key` 和显示名。路径变化后会成为另一项目，原关联不会自动迁移。验收记录明确承认“VibeInsight 仓库路径变化按新来源身份处理”，只验证了设备项目改显示名后关联有效。

   `plan.md:20` 已记录使用 Git 仓库身份的方案，但未解释它如何满足上述改名要求，也未见 SPEC 收窄及重新确认的依据。建议维护者明确区分显示名变化与仓库身份变化：若路径变化属于本次承诺的改名，应保留身份和关联；若应视为新项目，应按 `AGENTS.md:28–31` 更新并确认规格边界。通过条件是按确认后的定义验证改名行为，并说明既有关联的结果。
