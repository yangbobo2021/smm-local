# SPEC 生成 EVAL：平台交付与验收范围

本评测提取自 PR #21 的平台验收遗漏，以及维护者于 2026-11-17 对 SPEC 职责的澄清。
评测对象是起草阶段的规格正文，检验它能否在实现前，根据项目支持范围、需求及设计，
约定交付适用的环境、平台风险和必要验收证据。历史来源与受控改写见 [provenance.md](provenance.md)。

本轮只定义 EVAL，尚未执行模型生成、评分或 Prompt 对比。正式 SPEC 模板、产品代码和
PR #21 均未因本 EVAL 修改。[current-spec.md](templates/current-spec.md) 是原模板的固定快照。

## 执行方式

每次在全新上下文中只提供一版待测 SPEC 模板和一份 `cases/case-*.md`，要求直接输出规格正文。
材料已自足，不访问仓库、网络、其他样本或本聊天。不将本说明、评分规则、历史失败、
既有 SPEC 或其他版本回答提供给生成者；不能额外提示“请检查跨平台”，否则改变了评测任务。

| 样本 | 固定资料及用途 |
| --- | --- |
| [Case 01](cases/case-01.md) | 源自 VibeInsight 同步遗漏的构造样本。三平台服务、外部客户端、秘密文件及重启续跑，需要识别各平台的实际运行验收义务。 |
| [Case 02](cases/case-02.md) | 文案变更对照。支持三平台，但只修改静态 CLI 帮助，要求合理接受当前环境的验证范围。 |
| [Case 03](cases/case-03.md) | 共用逻辑变更对照。三平台契约不变，风险限定为纯排序函数，可用当前环境验证共用行为并说明适用依据。 |
| [Case 04](cases/case-04.md) | 部署范围对照。Hub 仅交付 Linux，客户端支持三平台但本次不变，防止把客户端平台错误扩展成 Hub 验收矩阵。 |
| [Case 05](cases/case-05.md) | 信息不足对照。平台范围未确认，不能默认为当前电脑足够，也不能擅自宣布三平台交付。 |
| [Case 06](cases/case-06.md) | 既有 `001-source-cli-help/input.md` 的逐字副本，沿用原五项标准，保护参数用途、取值来源和兼容行为的生成能力。 |

Case 01 不是历史输入的逐字回放；它把历史项目资料和已选设计整理为自足输入，并明确固定
原先遗漏的平台前提。Case 02–05 是人工构造的对照。Case 06 为既有评测的原文回归。

## 评分与未来比较

生成结束后，独立评分者只接收对应样本、匿名规格回答和 [rubric.md](rubric.md)。
Case 06 另接收被引用的 [原评分规则](../001-source-cli-help/rubric.md)。
按每个检查 ID 记录 0/1、回答原文摘录和判断理由。缺失项写明未找到相应承诺，不猜测作者意图。
不按关键词、固定标题或是否使用表格评分。

每个样本的全部检查通过，才算该样本通过。六个样本分别报告结果；Case 01 通过但
低风险对照或旧样本回归失败，不能视为解决了问题。运行异常与内容不合格分开记录。

若以后比较模板/Prompt，每版每个样本执行三次，同一套固定材料与运行配置共 18 次/版。
记录实际模型、设置、待测模板、输入、回答和评分的哈希；在评分完成前隐藏版本标签，
执行前冻结顺序。报告每项得分和每个样本的通过次数，不把本次定义当作执行结果，
也不根据这组样本宣称对所有项目已具有泛化效果。

[frozen.json](frozen.json) 固定当前材料、基线模板和旧回归规则的 SHA-256。
新增候选或修订材料时另留版本，不能用修改评分规则解释已经取得的结果。
