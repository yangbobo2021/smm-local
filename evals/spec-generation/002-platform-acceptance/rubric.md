# SPEC 生成评分：平台交付与验收范围

仅给评分者。生成者收到一版 SPEC 模板与一个 case，不收到本规则和其他样本。
每项 0/1，接受语义等价表述和跨段明确引用。记录规格原文摘录及理由；每个 case 全项通过才算通过。
本轮尚无生成回答和得分。

## 通用判分边界

- 评分对象为 SPEC 正文。交付平台、风险判断及必要验收覆盖须由规格作出决定或明确列为待确认。
  “由 PLAN 决定需要哪些平台”“保证跨平台”“必要时其他平台测试”都未形成可判定要求。
- SPEC 可以约定必须在哪类真实环境验证什么结果；不要求具体虚拟机、命令、脚本、CI 实现或执行顺序。
  不因没有这些 PLAN 细节扣分。若关键义务只放入未来 PLAN、可选建议或不具约束力的附言，不算覆盖。
- 区分继承的产品支持范围与本次需执行的验证范围。接受有依据地复用共用逻辑证据，
  不要求每次变更在所有系统重复完整测试，也不允许通过缩减产品支持范围来回避验收。
- 不将“已有平台未验证”自动当作已确认排除。不能把未执行写成已通过，也不能据缺少证据宣称功能已失败。
- 以材料中真实差异为依据，不能只按是否出现 Windows/Linux/macOS 或表格评分。
  后文各项都要检查行为、环境与通过结果之间是否有明确对应。

## Case 01：服务、外部程序与凭据持久化

| ID | 1 分条件 |
| --- | --- |
| H1 交付范围 | 继承 Hub 与本机端 Windows/Linux/macOS 支持，明确新能力在相应平台成立；不能默认为仅 macOS 或无依据缩减范围。 |
| H2 设计风险 | 结合已选设计识别平台差异，至少覆盖服务账号/环境调用外部 `psql`、秘密文件访问控制和启停/重启生命周期；据此说明当前 macOS 运行证据不足以完成三平台验收。仅罗列系统名称或笼统说“注意兼容”不得分。 |
| H3 各平台实际运行 | SPEC 明确要求 Windows、Linux、macOS 各自的 Hub 在既有服务方式与实际服务账号环境下完成来源访问和同步，能从 SMM 搜索并读回原文。可以共用合成来源数据，不要求真实服务器造数。单一系统换目录、只模拟 `sys.platform`、只构建 wheel 或只跑共用单测不能替代此义务。 |
| H4 凭据与重启结果 | 上述平台验收明确覆盖保存配置/凭据后服务重启、无重新输入地续跑，服务账号能读秘密文件且未授权普通账号不能读；原会话继续追加、不丢已提交归档/进度且不重复。不能仅以另一段无平台归属的功能用例代替；允许明确声明相关条件适用于 H3 的每个平台。 |
| H5 本机端覆盖 | 客户端三平台均需有与 Hub 交互的 CLI/MCP 项目检索及引用读取证据；可以连接一个已验证 Hub，不要求三乘三操作系统组合，也不要求三个系统各重复全部数据库算法测试。 |
| H6 功能不退化 | 保留来源可见性变化后的早历史补齐、无效凭据不覆盖、单层双向关联与解除、同名/原引用兼容、离线本机全局回退及首版不发现原地改写的边界；可用共用功能验收表达。 |
| H7 验收层级与结论 | 必要平台覆盖为 SPEC 的通过条件，机器/命令可留给 PLAN。不能以“其他平台未验证但列出来即可”宣称三平台交付合格；允许共用算法证据与平台集成证据分工，不无依据强制三乘三平台组合或真实 staging 全量同步。 |

## Case 02：静态帮助文案

| ID | 1 分条件 |
| --- | --- |
| T1 需求结果 | 两条帮助均能表达回退的是插件适配器、保留已导入对话，不改变命令名、参数、实际回退及退出/无写入行为。 |
| T2 依据与覆盖判断 | 保留产品三平台支持，依据静态共用字符串、输出/依赖/打包未变且无已知编码差异，明确当前环境的两处输出及兼容验证可满足本次变更验收。不能仅以“开发机恰好是 macOS”作为充分理由。 |
| T3 控制额外要求 | 不把三平台分别安装、启停服务、连接 PostgreSQL 或各平台完整回归作为本次必过门槛；不把文案改动扩成新的运行机制。可说明有新平台差异证据时需重新评估。 |

## Case 03：共用纯逻辑

| ID | 1 分条件 |
| --- | --- |
| L1 行为可判定 | 验收覆盖同分按数值会话 ID 升序、打乱输入仍稳定、不同分数排序及结果/过滤/limit 语义保持；避免把数值排序误成字典序。 |
| L2 支持与证据区分 | 三平台仍遵循同一排序契约。依据纯函数、相同数值语义、无系统依赖及不变调用层，明确当前环境中的共用行为证据可支撑本次修改；不能把它说成三平台服务已经实际运行通过。 |
| L3 控制额外要求 | 不无依据要求三平台完整安装、来源同步、系统服务或外部 PostgreSQL 验收；也不能因为“纯 Python”就忽略输入中要求的行为测试。 |

## Case 04：部署范围不同于客户端平台

| ID | 1 分条件 |
| --- | --- |
| S1 范围准确 | 明确 Hub 本次交付 Linux systemd，客户端支持三平台不等于新增 Windows/macOS Hub 支持。 |
| S2 针对性风险 | 识别本次是系统服务启动/重启与服务账号环境问题；当前 macOS 共用逻辑验证不足以证明 Linux systemd 行为。 |
| S3 必要执行证据 | SPEC 要求在 Linux 实际服务环境验证系统重启后服务自动启动并同步、无需重新输入凭据、归档和进度保留、恢复重试不重复，以及失败状态和已有归档可检索；不只要求前台函数调用或手动重启进程成功。允许沿用一个明确适用于全部状态的环境约定。 |
| S4 不扩大范围 | 不把 Windows/macOS Hub 运行作为必过条件，不无依据要求客户端三平台完整回归。可以检查既有协议可读性，但不能增加资料未要求的平台承诺。 |

## Case 05：支持范围与设计未确认

| ID | 1 分条件 |
| --- | --- |
| U1 待确认事项 | 在 SPEC 草稿列明需确认的操作系统/后台运行方式及服务账号、凭据持久化和访问边界，并说明它们如何影响验收环境或通过条件。不能只说“环境未知”。 |
| U2 不猜测平台 | 不以 Python 版本、开发机或 README 路径推断仅支持 macOS或已支持三平台。可给条件化草案，但这些支持决定必须仍标为待确认。 |
| U3 不提前判充分 | 保留自动续跑、已归档对话可检索、失败与重试去重的功能目标，同时明确平台/设计范围确认前不能把当前终端执行当作后台交付验收充分证据，也不能把决定全部下放给 PLAN。 |

## 最小判分校准

这些是假设回答片段的判分约束，不是实际模型输出或执行结果：

| 假设输出 | 必须判定 |
| --- | --- |
| Case 01 只写“Windows/Linux/macOS 均支持”，后附“pytest 全绿” | H1 可得分；H2–H5 没有相应内容则不得分，不能整体通过。 |
| Case 01 把所有系统实测留作 PLAN 自选，SPEC 无覆盖义务 | H7 不得分，即使功能条件完整。 |
| Case 02 强制每个平台重新部署服务并连接 PostgreSQL 才通过 | T3 不得分，不能因显得严格而加分。 |

| Case 05 明确待确认环境并给条件化验收，不虚构执行结果 | 可以通过，不能因草稿仍有待确认项就判失败。 |
