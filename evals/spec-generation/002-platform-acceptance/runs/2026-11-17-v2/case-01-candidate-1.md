# 规格：Hub 自动同步 VibeInsight 历史与项目关联检索

意图依据：[已确认意图](./intent.md)。本规格沿用 Hub 与本机端对 Windows、Linux、macOS 的现有支持范围及服务运行方式。尚需维护者确认的接口与配置决定在下文列明。

## 预期行为

### 来源配置与自动恢复

1. 维护者通过 Hub CLI 提供 VibeInsight PostgreSQL 来源连接信息并输入密码，验证成功后保存。连接信息须能确定服务器地址、端口、数据库、登录用户及必要的连接安全设置；这些值由来源数据库维护者提供或确认。密码不得通过命令输出回显。
2. 配置验证须确认连接可用、能够执行所需只读查询，并且长期运行的 Hub 服务能够使用该配置调用 `psql`。仅 CLI 当前账号连接成功不足以判定配置有效。
3. 新配置验证失败时，CLI 返回可诊断的失败原因，原有效连接参数和密码保持有效。首次配置失败时，不形成有效来源配置。
4. 验证成功后，连接参数保存至 Hub 配置文件，密码保存至服务状态目录的专用秘密文件。Hub 重启后自动读取并继续同步，无需重新输入密码。
5. 来源连接失败、凭据失效或 `psql` 不可用时，已有归档仍可检索和读取。来源恢复后，Hub 自动重试尚未成功归档的数据。

### 历史同步

1. 配置生效后，Hub 自动发现并同步该来源账号可读取的全部项目历史，无需逐项目配置关联。
2. Hub 持续同步新增会话事件，以及既有会话后续追加的轮次。重复读取同一事件或轮次不得产生重复归档。
3. 来源后来新增可读项目时，即使该项目历史早于已有同步进度，Hub 仍须发现并补齐其可读历史，再持续同步后续事件。
4. 同步批次的归档数据与进度一同提交。中断或重启后，从已提交位置继续；未成功提交的数据重新读取，近期事件回查产生的重复数据被去重。
5. 项目关联不构成同步前提；未关联的 VibeInsight 项目同样进入归档。

### 项目关联与检索

1. 项目关联由 Hub 维护者统一管理，可连接设备项目与 VibeInsight 项目，也可连接不同设备项目。维护者能够建立、查看和解除关联，并通过稳定身份区分同名项目。
2. 关联双向生效。查询项目 A 时，检索范围包含 A 及与 A 直接关联的项目；从任一关联端查询遵循相同规则。
3. 关系只扩展一层。例如 A—B、B—C 且 A 与 C 无直接关联时，查询 A 包含 A、B，不因 B—C 包含 C；查询 B 包含 A、B、C。
4. 解除关联后，后续项目查询不再通过该关系扩展范围，已归档数据及其原文引用仍保留可用。
5. 本机端补传项目归属。CLI/MCP 发起项目查询时携带当前项目身份，Hub 据此应用直接关联范围；不得仅凭项目名称合并身份。
6. 现有 CLI/MCP 能检索和读取同步归档。检索结果提供来源、项目、原会话及消息位置，使调用方能精确读取对应原文。同名项目、不同来源的相似会话及既有原文引用保持可区分、可用。
7. 旧客户端的全局查询继续有效，不因缺少当前项目身份而被收窄。Hub 不可用时，沿用本机全局回退行为。

## 边界与约束

- 首版为单用户，不引入多用户权限模型。
- 仅覆盖新增会话事件与追加轮次；不承诺发现没有新增事件的历史正文原地改写。
- 对 VibeInsight 仅执行只读查询，不修改来源数据。
- Hub 与本机端继续支持 Windows、Linux、macOS，不以当前开发电脑为依据缩减范围。
- Hub 保持既有运行方式：Windows 使用 LocalService 系统服务，Linux 使用 systemd 用户服务，macOS 使用 launchd 系统服务。
- `psql` 是 Hub 服务的外部运行依赖。CLI 与服务可能使用不同账号、搜索路径和环境，交付必须覆盖服务实际调用、连接及读取秘密文件的能力。
- 秘密文件须允许 Hub 运行账号读取，并阻止其他未授权普通账号读取。CLI 输出、日志和对话数据库不得包含密码原值。
- 合成事件可用于默认回归，无需在真实服务器造数；合成事件不能替代实际服务环境下对 `psql`、来源连接和秘密文件访问的验证。

## 设计决策

1. **凭据与服务环境**  
   连接参数与密码分开保存。配置验证须覆盖长期运行服务的实际环境，避免将维护者交互账号下的成功误认为服务可用。配置更新失败或中断不得破坏原有效配置，也不得留下连接参数与密码不匹配的有效状态。

2. **同步完整性**  
   同步进度保存在 Hub 数据库，归档与进度原子提交，并回查近期事件去重。项目发现与历史补齐不能仅依赖来源全局最新位置，否则后来获得读取权限的旧历史可能被跳过。

3. **稳定身份与原文定位**  
   来源、项目、会话和消息位置须组成无歧义的定位信息。项目关联改变检索范围，不改变归档身份或既有引用。

4. **实施前待维护者确认**
   - Hub CLI 的来源配置、状态查看及关联管理命令形式；连接安全选项的必填条件、默认值与确认途径。
   - 各平台如何安装、定位或显式指定服务使用的 `psql`，以及配置文件和秘密文件的具体位置。该决定影响服务可执行性与权限验收。
   - 项目稳定身份的展示、获取和选择方式，确保维护者能够从管理入口准确选择同名项目。
   - 自动发现、同步及故障重试的时限，以及近期事件回查范围。验收需据此判定自动同步是否及时完成。
   - 来源事件的稳定标识、排序与追加判据，以及 CLI/MCP 定位字段和旧引用兼容方式。该决定须支持去重、补齐和精确原文读取。

## 验收条件

### 三个平台的实际服务证据

以下条件须分别在 Windows LocalService 系统服务、Linux systemd 用户服务、macOS launchd 系统服务中取得通过证据：

1. **配置与权限**  
   在维护者 CLI 环境与实际服务环境下，使用有效来源配置完成验证保存；服务能调用选定 `psql`、读取秘密文件并执行所需只读查询。未授权普通账号不能读取密码。使用无效凭据更新失败后，原配置仍能同步；CLI 输出、日志和对话数据库中均无密码原值。

2. **同步、重启与补齐**  
   来源预置历史会话后，服务自动归档并可通过 CLI/MCP 精确读取。随后新增会话、为旧会话追加轮次，并重复提供事件，结果完整且无重复。重启服务后无需输入密码，仍能归档后续数据。再新增一个可读项目，其历史早于已有进度，服务须补齐该项目历史。

3. **中断与恢复**  
   在同步批次提交边界附近中断并恢复服务，归档与进度不得出现部分提交造成的遗漏，重读不得产生重复。来源不可用期间，已有结果及原文仍可读取；恢复连接后，遗漏数据在已确认重试时限内补齐。

以上服务验收可使用受控 PostgreSQL 来源和合成事件，不要求在生产来源造数；必须实际经过服务调用的 `psql` 路径。

### 共用行为判据

以下内容与关系逻辑可在当前 macOS 独立 Hub 环境集中验证，前提是三平台使用相同实现和数据契约；若存在平台分支，相关分支须补充实际平台证据：

1. 建立设备项目与 VibeInsight 项目、不同设备项目之间的关联，验证双向查询。使用 A—B—C 关系验证一层扩展；解除关联后范围立即符合新关系，归档及既有原文引用仍可用。
2. 使用同名但身份不同的项目及相似会话，验证项目身份不混淆，CLI/MCP 返回的来源、项目、原会话和消息位置能读取准确原文。
3. 未关联项目仍自动同步；旧客户端全局查询仍覆盖原有全局范围；仅原地改写且没有新增事件的正文不作为必须发现的变更。

### 本机端兼容证据

Windows、Linux、macOS 本机端均须取得项目归属补传、CLI/MCP 携带当前项目身份及 Hub 不可用时本机全局回退的实际运行证据。每个平台均须验证对应操作后的查询范围和原文读取结果，不能只验证启动成功。旧客户端全局查询兼容性可使用同一协议实现集中验证。

当前资料仅说明 macOS 具备测试及安装条件，尚不构成通过证据。Windows/Linux 缺少的必要执行记录属于交付未完成项；共用单测、wheel 构建或合成事件测试不能替代上述实际平台和服务证据。具体机器、命令、执行顺序和 CI 配置写入 plan.md。
