# 规格：Hub 服务启动后自动同步已配置来源

依据：[已确认意图](./intent.md)。

## 预期行为

1. Linux systemd 用户服务每次启动后，Hub 自动执行已有的一次同步操作，拉取已配置来源的新对话，无需用户手动运行同步命令。机器重启后，由 systemd 启动该用户服务时，同样触发同步。
2. 启动同步沿用 Hub 用户状态目录中的已有来源凭据，并从数据库保存的进度继续处理。用户无需为启动同步重新提供凭据、重建配置或重置进度。
3. 启动同步失败时，Hub 报告可定位问题的失败原因；同步失败不阻止已有归档通过既有接口被检索。
4. 同步失败后再次执行已有同步操作，或后续服务启动再次触发同步时，不重复导入已保存的消息。此次不新增自动重试策略。
5. 同步算法、API、CLI/MCP、客户端程序和配置格式保持现有行为。Windows、macOS、Linux 本机客户端继续通过既有 HTTPS 协议访问 Hub。

## 边界与约束

- 本次 Hub 交付仅支持 Linux systemd 用户服务，不包含 Windows/macOS Hub，也不扩展至其他 Linux 部署方式。
- 三种操作系统上的本机客户端属于既有访问入口；本次不修改客户端，不要求各客户端平台重复执行整套同步验收。
- 凭据仅允许相应 Linux 服务账号读取。启动同步必须在该账号及其服务环境中找到并读取已有状态目录，不能依赖交互式登录会话提供的环境。
- 此次仅接入已有一次同步操作，不改变来源配置方式、进度语义或消息去重规则。
- 当前 macOS 开发环境只能提供共用逻辑验证，不能证明 Linux systemd 生命周期行为成立。当前没有实际 Linux 服务启动或机器重启后的执行证据。

以下事项须由维护者确认：

- systemd 用户服务是否已有随机器重启、无需交互式登录即可启动的配置承诺；若没有，须明确本次交付所需的启用条件、配置责任及用户确认途径。该决定直接影响“机器重启后自动同步”能否成立。
- 在缺少交互式登录环境时，服务如何确定既有 Hub 状态目录；若需要补充服务配置，须明确配置值的含义及获取方式，并保持现有应用配置格式不变。
- 启动同步失败原因通过哪个既有日志或状态入口呈现，以及用户如何查看。

## 设计决策

- 将已有一次同步操作接入 Hub 服务启动后的生命周期，复用已有凭据加载、数据库进度及去重逻辑，避免形成第二套同步实现。
- 启动同步失败与已有归档检索可用性分离。错误处理不得因同步失败而使已有归档无法检索。
- 服务账号、状态目录访问权限及非交互式服务环境是本次主要风险，必须在实际 Linux systemd 用户服务中验证；仅调用同步函数或成功构建软件包不足以证明这些行为。
- 本次没有改变客户端或 HTTPS 协议。客户端兼容性可通过既有协议的检索验证及共用回归验证支撑，无需新增 Windows/macOS Hub 验收环境。

## 验收条件

以下第 1—5 项必须取得实际 Linux systemd 用户服务环境中的通过证据。共用前提为：服务使用目标 Linux 服务账号，已有来源配置、凭据、数据库进度及可检索归档；来源中存在尚未导入的新对话。

1. **服务启动自动同步**  
   在服务停止状态下启动用户服务，无需手动运行同步命令，即可拉取新对话；同步沿用已有凭据和数据库进度，新导入内容可通过既有检索接口查询，已有归档仍可检索。

2. **机器重启后自动同步**  
   按维护者确认的自动启动配置完成部署后，机器重启且不进行交互式登录、不手动启动服务或执行同步命令，用户服务自动启动并完成新对话同步；新旧归档均可通过既有 HTTPS 接口检索。

3. **服务环境凭据访问**  
   在不依赖交互式登录环境的实际服务启动中，服务账号能够读取原有用户状态目录中的凭据及数据库，完成同步，无需复制凭据、放宽其访问权限或重置进度。

4. **同步失败仍可检索**  
   分别覆盖来源访问失败和服务账号无法读取凭据的启动状态。每种状态下，启动同步失败后，确认的报告入口均提供可定位的失败原因，且既有 HTTPS 检索请求仍能返回已有归档。错误报告不得泄露凭据内容。

5. **失败后重试不重复导入**  
   覆盖已保存部分消息后同步失败的状态。恢复失败条件后，通过已有同步操作重试，以及通过后续服务启动再次同步，均能继续处理剩余内容；已保存消息不重复导入，最终新旧归档均可检索。可使用可控故障建立该状态，但须保留实际服务生命周期的验证证据。

6. **既有接口兼容**  
   共用逻辑和接口回归验证确认：既有 API、CLI/MCP、配置格式及 HTTPS 检索行为保持兼容。结合上述 Linux 服务中的实际 HTTPS 检索证据，支撑未改动的三平台客户端访问承诺；该验证不表示已在各客户端平台实际运行通过。

7. **交付完成判定**  
   维护者确认上述待决定事项，且必需的 Linux 服务启动、机器重启、失败可检索及重试去重证据全部通过后，方可判定交付完成。macOS 共用逻辑测试、包构建或将 Linux 验证标记为“未验证”，均不能替代这些证据。具体机器、操作步骤、命令及证据采集方式写入 `plan.md`。
