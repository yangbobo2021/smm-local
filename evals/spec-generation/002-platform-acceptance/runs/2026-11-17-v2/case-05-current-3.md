# 规格：Hub 重启后自动恢复同步

本规格依据同目录下已确认的 [intent.md](intent.md)。后台运行的部署范围、服务类型、运行账号及凭据持久化方案仍需维护者决定；当前开发电脑为 macOS，不构成仅支持 macOS 的依据。

## 预期行为

1. 已配置数据来源并完成后台运行配置后，机器重启，Hub 自动继续同步，无需用户手动启动同步命令或重新输入凭据。
2. 恢复同步时，Hub 保留现有归档和已记录的同步进度，继续处理尚未导入的数据。
3. 某个来源不可达时，Hub 保留该来源已有归档的可检索性，并报告同步失败。失败不得清空归档或重置同步进度。
4. 来源恢复可达后，Hub 自动重试并继续同步，无需用户重新配置来源或输入凭据。
5. 重启恢复、失败重试及重复读取已处理数据时，不重复导入已有归档记录。

## 边界与约束

- 本次变更面向已配置的数据来源，不要求自动发现或配置新来源。
- 运行环境须满足现有 Python 3.11+ 要求。
- 支持的操作系统和部署方式尚未确认。不得依据 README 示例路径或当前开发电脑推定部署范围，也不得将 Windows/Linux 支持视为已确认要求。
- 在维护者确认的部署范围内，自动恢复同步不得依赖用户打开交互式终端。
- 现有归档、同步进度及前台同步命令的使用方式须保持兼容；原有通过环境变量提供凭据的方式仍可使用。
- 来源不可达时，持续同步无法完成，但已有归档仍须可检索。
- 凭据失效、撤销或权限不足时的恢复行为不属于“来源恢复可达”即可解决的情况，其报告及更新流程仍需明确。

## 设计决策

以下事项须在实施前由维护者确认：

| 待决定事项 | 需要确认的内容 |
| --- | --- |
| 部署范围 | 本次支持的操作系统及部署环境；不能默认仅支持 macOS，也不能默认新增 Windows/Linux 支持。 |
| 后台运行方式 | 服务类型、启动机制和运行账号，以及该账号访问归档、进度和凭据所需的权限。 |
| 凭据持久化 | 存储与保护方式、后台服务的读取方式、首次保存及后续更新流程；同时明确持久化凭据与环境变量并存时的优先级。 |
| 状态持久化 | 后台服务如何访问并沿用现有归档和进度，避免因运行账号或环境变化而使用空的新状态。 |
| 失败报告 | 用户查看失败的入口，以及足以识别受影响来源和失败原因的信息；报告不得暴露凭据。 |
| 重试策略 | 自动重试的触发条件、间隔或退避规则，以及重启后如何延续重试。 |
| 去重依据 | 各来源识别已导入记录的依据，以及中断后重读数据时避免重复导入的规则。 |

这些决定直接影响重启后能否取得凭据和原有状态，以及失败恢复是否可靠，不能仅从现有前台运行经历推定。

## 验收条件

1. 在维护者确认的部署环境中，完成一次后台运行配置后重启机器，无需打开交互式终端、手动启动命令或再次输入凭据，Hub 自动开始同步已配置来源。
2. 重启前已有的归档在重启后仍可检索，已记录的同步进度得到保留，未导入的数据能够继续导入。
3. 来源不可达时，用户能通过已确认的报告入口识别受影响来源及失败原因，报告不包含凭据。
4. 来源不可达及重试期间，已有归档仍可检索，归档和同步进度不因连接失败而被清空或重置。
5. 来源恢复可达后，Hub 按已确认的重试策略自动恢复同步，无需重新配置来源或输入凭据。
6. 对重启恢复、失败重试和中断后重新读取的数据，已有记录不重复导入，尚未导入的记录能够入库。
7. 现有前台同步命令仍可通过环境变量取得凭据，并继续使用现有归档和进度。
8. 部署范围及上述设计决策均已明确，验收结论限定于已确认的环境，不将未确认的平台宣称为已支持。
