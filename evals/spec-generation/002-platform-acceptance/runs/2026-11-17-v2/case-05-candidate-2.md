# 规格：Hub 重启后自动恢复同步

依据同目录下已确认的 [intent.md](intent.md)。本次变更应使 Hub 在机器重启后自动继续同步已配置的数据来源，保留归档、同步进度及可复用的凭据；来源不可达时保留归档检索能力，恢复后重试且不重复导入。

操作系统、后台运行方式、部署账号及凭据持久化方案尚待维护者确认。这些决定影响交付内容和验收环境，确认并取得必要证据前不能判定交付通过。

## 预期行为

1. **配置后台同步**
   - 管理者能够将已配置的数据来源纳入随系统启动的后台同步。
   - 配置入口须说明归档、同步进度和凭据的保存位置或引用方式，以及后台运行账号所需的访问权限。
   - 原命令使用的凭据来自环境变量，不能假定后台运行环境会继承交互式终端的变量。首次配置须明确如何将已有凭据转为后台可用的持久化凭据；具体入口、必要配置值、获取和确认方式待凭据方案确定后补齐并审阅。

2. **机器重启后继续同步**
   - 在后台同步配置完成且凭据仍有效的前提下，机器重启后，Hub 自动启动并继续同步已配置的数据来源，无需人工打开终端、执行前台命令或重新输入凭据。
   - Hub 使用重启前的归档和已保存进度继续处理，不清空已有数据，不因重启重复导入已归档内容。

3. **来源不可达时保留归档并报告失败**
   - 当某个来源不可达时，Hub 保留该来源已有归档和可恢复进度，已有归档仍可通过项目现有检索入口检索。
   - 管理者能够通过明确的后台状态或日志入口识别失败来源及失败原因。错误信息不得包含凭据。
   - 状态或日志入口及其访问方式待后台运行方案确认。

4. **来源恢复后自动重试**
   - 来源恢复可达后，Hub 无需人工重启服务或重新配置凭据即可再次尝试同步，并最终导入新增内容。
   - 重试不得重复导入已归档内容，包括中断发生在内容写入与进度保存之间的情况。
   - 重试触发方式、间隔或退避规则，以及用于判定恢复成功的等待上限，须在实施前确认并写入本规格。

## 边界与约束

- 仓库当前仅声明 Python 3.11+，没有已确认的操作系统、服务类型或部署账号范围。开发电脑为 macOS、README 示例路径及已有前台运行记录均不能作为后台部署支持承诺。
- 本次既不能默认仅支持 macOS，也不能默认新增 Windows/Linux 支持。维护者须确认后台组件的实际支持平台及运行方式；若检索入口具有独立的运行环境要求，也须分别明确。
- 必须保留现有归档、同步进度和前台同步入口。新增凭据持久化不得迫使现有环境变量调用方式迁移，也不得静默覆盖已有数据。
- 自动恢复以已完成后台配置、持久化数据可用且凭据有效为前提。凭据过期或被撤销不属于来源暂时不可达后的自动恢复保证；此时仍须保留归档并报告可识别的认证失败。
- 不得假定交互式用户与后台账号具有相同的环境变量、文件权限、工作目录或凭据访问能力。
- 本规格未确定支持范围和必要运行配置，因此当前仅为待审阅草稿，不能作为已具备完整实施与验收依据的定稿。

## 设计决策

以下事项须由维护者在实施前确认，并将结果补入本规格：

| 待确认事项 | 对交付与验收的影响 |
| --- | --- |
| 支持的操作系统及版本范围 | 决定后台集成方式和必须取得实际运行证据的平台，不能以当前 macOS 环境代替决定 |
| 后台启动机制与部署账号 | 决定系统启动后的进程生命周期、是否依赖用户登录，以及归档和凭据的访问权限 |
| 归档、进度及配置的持久化位置 | 决定后台服务能否继续使用现有数据，以及如何处理已有数据的接入 |
| 凭据持久化方式及首次配置入口 | 决定凭据如何安全保存、由哪个账号读取，以及重启后能否在无人操作时使用；不得以明文日志暴露凭据 |
| 失败状态或日志入口 | 决定管理者如何确认后台同步失败及定位受影响来源 |
| 自动重试规则与恢复等待上限 | 决定故障恢复行为及其可独立判定的验收标准 |
| 前台与后台同时运行的处理方式 | 须明确拒绝并发、互斥或安全协作的行为，避免归档重复或进度损坏 |

归档写入、进度保存与重复检测须共同保证中断后可恢复。凭据持久化方案还须考虑后台账号、文件权限及可能存在的登录解锁依赖；若方案只能在用户登录后访问凭据，须明确其是否满足维护者要求的系统启动行为，不得隐含降低承诺。

## 验收条件

1. **规格决定完整**
   - 支持平台、运行方式、账号、持久化配置、失败查看入口、重试规则及并发处理方式均已确认。
   - 管理者能够依据定稿说明完成配置，必要值的含义、适用范围及获取或确认方式均明确。

2. **实际重启恢复**
   - 在每个确认支持的后台部署环境中，预先配置有效凭据、已有归档及非初始同步进度，并确认后台账号具有所需权限。
   - 机器实际重启后，Hub 在约定的启动条件下自动运行，无需人工启动同步或重新输入凭据；原归档仍可检索，进度得到延续，新增内容成功导入，已有内容无重复。
   - 若承诺无需用户登录，此用例必须在无人登录状态下取得通过证据。

3. **不可达与恢复的完整链路**
   - 在每个确认支持的后台部署环境中，使用已有归档、进度和有效持久化凭据，使来源在机器重启前即不可达，并持续至后台启动后。
   - Hub 自动运行，保留归档和可恢复进度；现有检索入口仍能查到已归档内容；约定入口显示受影响来源及失败原因，且不泄露凭据。
   - 恢复来源后，Hub 在确认的重试等待上限内自动成功同步新增内容，无需人工重启或重新输入凭据；已有归档无丢失、无重复。

4. **中断与并发边界**
   - 验证同步在归档写入与进度保存之间中断后，再次运行不会丢失或重复导入内容。
   - 验证前台与后台同时启动时符合已确认的并发处理规则，且归档和进度保持一致。
   - 与服务终止、锁和持久化存储有关的行为须在每个采用不同服务机制或存储语义的实际部署环境中验证。纯重复检测等共用逻辑可复用测试，但不能代替实际重启及故障恢复证据。

5. **认证失败与现有入口兼容**
   - 在各确认支持的后台部署环境中，凭据不可用时，Hub 保留可检索归档并报告可识别的认证失败，不输出凭据，也不静默重置进度。
   - 现有前台命令仍可通过环境变量取得凭据并完成同步，既有归档和进度可继续使用。

上述环境可复用相同行为判据，无需重复全部共用逻辑测试；但每个确认支持的后台部署环境都必须取得对应的实际重启、凭据访问、故障报告及自动恢复证据。单元测试或包构建不能替代这些证据。缺少必要环境或通过证据时，本次交付仍未完成。具体机器、命令、实施顺序及测试步骤写入 plan.md。
