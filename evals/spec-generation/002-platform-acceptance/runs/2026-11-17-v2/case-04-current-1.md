# 规格：Hub systemd 用户服务启动时自动同步

以同目录下已确认的 [intent.md](./intent.md) 为依据。尚需维护者决定的事项列于「设计决策」。

## 预期行为

1. Linux systemd 用户服务每次启动后，Hub 自动触发一次已有的同步操作，拉取已配置来源中的新对话，无需用户手动执行同步命令。机器重启后，只要该用户服务自动启动，也应触发同步。
2. 自动同步使用相应 Linux 服务账号在 Hub 用户状态目录中已有的来源凭据，并沿用数据库中已有的同步进度，无需重新配置来源、提供凭据或重置进度。
3. 自动同步不依赖交互式登录环境；服务环境与交互式环境不同时，仍应能找到并读取既有状态目录中的凭据。
4. 启动同步失败时，报告可用于定位问题的失败原因，且不泄露凭据。Hub 仍提供已有归档的检索服务，既有客户端可继续通过 HTTPS 检索。
5. 同步失败后再次执行已有同步操作，或因服务再次启动而重新同步时，继续沿用已有进度，不重复导入已归档消息。

## 边界与约束

- 本次交付仅适用于 Linux systemd 用户服务，不包含 Windows 或 macOS 上的 Hub 运行支持。
- Windows、macOS、Linux 本机客户端仍通过既有 HTTPS 协议访问 Hub，客户端行为与配置不变。
- 本次仅将已有的一次同步操作接入服务启动后的生命周期，不改变同步算法、API、CLI/MCP、客户端程序或配置格式。
- 凭据继续保存在既有用户状态目录中，仅由相应 Linux 服务账号读取，不扩大读取权限。
- 不引入定时同步或新的自动重试策略。失败后再次同步时，仍须满足消息不重复导入的要求。
- 当前 macOS 开发环境能够运行共用逻辑测试，但不能验证 Linux systemd 生命周期。现有材料没有本次 Linux 服务启动或机器重启后的执行记录，因此不能据此认定 Linux 验收已通过。

## 设计决策

以下事项仍需维护者确认：

- **机器重启后的启动前提**：本次是否包含 systemd 用户服务随机器启动所需的部署配置，还是以部署环境已保证该用户服务自动启动为前提。无论选择哪种方式，都需明确使“机器重启后自动同步”成立的条件。
- **同步失败的报告入口**：失败原因通过何种既有日志或状态入口供维护者查看，以及如何辨识失败来源。该入口须适用于服务环境，并避免泄露凭据。

## 验收条件

1. 在 Linux systemd 用户服务已配置来源且存在待同步新对话的情况下，启动服务后，无需手动运行同步命令，新对话被导入并可检索。
2. 按维护者确认的部署前提重启 Linux 机器后，用户服务自动启动，并自动导入来源中的新对话，无需交互式登录或手动触发同步。
3. 服务启动时使用原有状态目录中的凭据及数据库进度；无需重新配置来源或重置进度，已归档消息不重复导入。
4. 在服务环境缺少交互式登录环境变量的情况下，只要既有凭据对服务账号可读，自动同步仍能使用这些凭据。
5. 启动同步发生失败时，可从确认的报告入口获得失败原因，输出不包含凭据；已有归档仍可通过既有 HTTPS 接口检索。
6. 一次同步在部分消息已导入后失败，再次执行同步或重启服务后，已导入消息不重复，尚未导入的新消息可继续导入。
7. 既有 API、CLI/MCP、三种平台客户端及配置格式保持兼容，原有手动同步入口仍可使用。
8. Linux 服务启动及机器重启场景均须有实际执行结果支持验收；仅通过 macOS 上的共用逻辑测试不构成这两项验收通过的依据。
