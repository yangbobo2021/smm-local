# 规格：Hub 自动归档 VibeInsight 历史与项目关联检索

本规格依据同目录已确认的 [intent.md](intent.md) 及现有项目承诺起草。未明确的接口、来源识别规则及环境配置决定列为待维护者确认，不据此缩减交付范围。

## 预期行为

### 来源配置与自动恢复

1. 维护者通过 Hub CLI 提供 VibeInsight PostgreSQL 连接信息，并验证、保存来源配置。必要信息包括服务器地址、端口、数据库、读取账号、密码，以及 Hub 服务可执行的 `psql` 位置。这些值由来源数据库管理方和 Hub 服务部署维护者提供或确认；读取账号的权限决定本次可同步的项目范围。
2. 配置验证须确认连接可用、能够读取同步所需数据，并确认长期运行的 Hub 服务能够使用所保存的连接信息、秘密文件及 `psql`。CLI 账号下连接成功不能单独代表服务配置有效。
3. 新配置通过验证后才替换原有效配置。连接失败、凭据无效、读取权限不足或服务无法使用该配置时，CLI 明确报告失败，原有效配置保持可用。
4. 保存成功后，Hub 自动同步来源中全部可读取项目的历史。Hub 按既有服务方式重启后，无需维护者再次输入密码即可继续同步。
5. 密码原值不出现在 CLI 输出、日志或对话数据库中。

### 历史同步与故障恢复

1. 首次同步覆盖来源当前可读取的全部项目和历史会话；持续同步新增会话及旧会话追加的轮次。
2. 来源后来新增可读取项目时，Hub 补齐该项目全部可读取历史，包括时间早于既有同步进度的数据。
3. 重复读取事件、近期事件回查及失败重试均不产生重复归档消息。
4. 批次归档与对应进度共同提交。未成功提交的批次不能使进度越过尚未归档的数据；重启后从已提交位置继续。
5. 来源连接或读取失败时，已有归档仍可通过现有 CLI/MCP 检索和读取。来源恢复后，Hub 自动重试此前未成功同步的数据。
6. 首版仅发现新增会话事件和追加轮次；没有新增事件的历史正文原地改写不在发现范围内。

### 项目身份与关联

1. 本机端上传时补传项目归属，CLI/MCP 发起项目查询时携带当前项目身份。同名项目必须可区分，不能仅按显示名称合并。
2. Hub 维护者统一管理项目关联，可建立、查看和解除设备项目与 VibeInsight 项目之间、不同设备项目之间的关联。
3. 建立关联时，维护者从 Hub 可识别的项目中选择双方身份；选择信息须足以区分来源、设备及同名项目。
4. 关联双向生效，查询仅扩展到当前项目的直接关联项目。例如 A—B、B—C 存在时，从 A 查询覆盖 A 和 B，不因 B—C 自动包含 C；从 B 查询覆盖 B、A 和 C。
5. 解除关联后，后续项目查询不再通过该关系扩展，已归档内容保持保存和可读取。

### 检索、原文与回退

1. 用户通过现有 CLI/MCP 检索本机上传和 VibeInsight 归档内容。项目查询覆盖当前项目及其直接关联项目。
2. CLI/MCP 检索结果返回来源、项目、原会话身份和消息位置，调用方能够据此精确读取对应原文；不同来源或同名项目中的会话不能混淆。
3. 既有原文引用继续可用，不因补传项目归属、来源接入或关联变更而失效。
4. 旧客户端未提供项目身份时，继续执行原有全局查询。
5. Hub 不可用时，本机端沿用现有本机全局回退行为。

## 边界与约束

- 首版为单用户，不新增多用户授权或租户隔离要求。
- Hub 和本机端继续支持 Windows、Linux、macOS，不改变既有服务方式：
  - Windows Hub：LocalService 系统服务。
  - Linux Hub：systemd 用户服务。
  - macOS Hub：launchd 系统服务。
- 来源读取由 Hub 服务调用外部 `psql` 完成，仅执行只读查询，不修改 VibeInsight 数据。
- CLI 配置账号与服务运行账号可能不同。服务使用的可执行文件路径、环境、配置访问和秘密文件权限均属于本次交付范围。
- 连接参数保存在 Hub 配置文件，密码保存在服务状态目录的专用秘密文件。运行账号必须能够读取秘密文件，其他未授权普通账号不能读取。
- 同步范围以来源实际读取权限为准，不推断或访问账号无权读取的项目。
- 自动同步的轮询周期、失败重试周期及可接受的同步延迟尚未确认，须在实施前明确，作为“持续同步”和“恢复后重试”的可判定时间边界。

## 设计决策

### 已选设计

1. 采用外部 `psql`，因此须显式解决服务环境中的可执行文件发现及调用。不能以 CLI 的交互式 PATH、开发电脑环境或 wheel 构建成功证明服务可用。
2. 配置采用验证成功后替换机制。替换失败或过程中断后，不能留下连接参数与秘密文件不匹配的有效配置。
3. 同步进度与归档在 Hub 数据库中共同提交，并通过近期事件回查去重。项目发现和历史补齐不能仅依赖全局时间水位，否则会遗漏后来获得读取权限的旧项目。
4. 项目关联由 Hub 保存，查询时按直接邻接关系扩展一层。关联变更不承担归档删除职责。
5. 原文定位须保持稳定，不能依赖项目显示名称或关联关系。

### 待维护者确认

- Hub CLI 的具体命令、连接参数输入方式、`psql` 路径配置入口，以及如何指定目标服务实例和状态目录。
- VibeInsight 的受支持数据结构、项目及会话稳定标识、事件排序与分页依据、消息位置含义，以及如何发现后来新增的可读项目。
- 本机项目稳定身份与历史无项目归属数据的兼容处理；无法确定项目归属时不得猜测或错误合并。
- CLI/MCP 新增定位字段的具体结构，以及旧原文引用的解析兼容方式。
- 各平台如何在实际服务身份下验证配置并安全写入秘密文件；安装或缺失 `psql` 时的操作指引和错误反馈。
- 自动同步、重试和新项目发现的时间边界，以及近期事件回查范围。

这些决定影响配置入口、数据完整性和验收判据，须在实施前确认，不能留给 `plan.md` 决定交付范围。

## 验收条件

### 环境覆盖要求

1. 以下服务相关验收须分别取得真实运行证据：
   - Windows：Hub 以 LocalService 系统服务运行。
   - Linux：Hub 以 systemd 用户服务运行。
   - macOS：Hub 以 launchd 系统服务运行。

   每个平台均须覆盖下述配置保存、秘密文件权限、服务重启续传、来源故障恢复及 `psql` 服务环境差异。只验证服务启动不算通过。

2. 本机端须在 Windows、Linux、macOS 分别验证项目身份上传、当前项目 CLI/MCP 查询、旧客户端全局查询及 Hub 不可用时的本机全局回退。
3. 来源分页、去重、项目关联和引用解析等共用逻辑可使用合成事件验证，并由一次完整集成验证连接至实际入口；这些证据不能替代各平台的服务身份、文件权限和外部进程调用证据。
4. 来源集成可使用独立、可控的 PostgreSQL 数据集，无需在真实 VibeInsight 服务器造数。默认回归可使用合成事件，但不能仅以合成来源证明 `psql` 读取及实际来源结构兼容。
5. 当前仅有 macOS 开发能力信息，尚无 Windows/Linux 本次执行证据。必需平台证据缺失时，交付验收仍未完成。

### 配置与服务运行

以下判据适用于上述三个 Hub 服务环境：

1. 在 CLI 与服务账号或环境不同的条件下，维护者保存有效连接；服务能读取所需配置、秘密文件并调用指定 `psql`，完成来源读取。
2. 保存前已有有效配置时，分别提交错误密码、不可读来源和服务不可执行的 `psql` 配置；操作失败且反馈可定位问题，原配置仍能同步。
3. 保存成功后重启既有类型的服务，无需输入密码即可继续同步。
4. 服务运行账号能读取秘密文件，另一个未授权普通账号读取失败；CLI 输出、日志及对话数据库中不存在测试密码原值。
5. CLI 环境能够调用 `psql`、服务环境不能直接发现该程序时，配置入口能够明确失败或通过已确认的路径配置使服务成功读取，不能误报配置有效。

### 同步完整性与恢复

以下判据须在每个实际 Hub 服务环境中覆盖；各环境可复用同一数据集和判据：

1. 来源包含多个项目、新旧会话和多轮消息时，首次同步后全部可读历史可检索且原文完整。
2. 已完成首次同步后，新增会话并向旧会话追加轮次；在确认的同步时间边界内，两类新增内容均被归档，原归档不重复。
3. 新增可读项目，其历史时间早于已提交进度；在确认的新项目发现和补齐时间边界内，该项目历史完整可查。
4. 在批次提交前中断服务，重启后补齐该批次；在提交后重启并回查近期事件，归档无丢失、无重复，进度与归档一致。
5. 来源中断期间，已有归档仍能检索并精确读取；恢复后在确认的重试时间边界内补齐中断期间新增内容，重复读取不产生重复消息。
6. 来源账号保持只读权限时同步成功，来源数据未被修改。

### 项目关联与精确读取

1. 创建同名但身份不同的设备项目和 VibeInsight 项目；CLI/MCP 能区分它们，并正确呈现上传或归档内容的项目归属。
2. 建立 A—B、B—C 关联后，分别从 A、B、C 查询，结果严格符合双向一层扩展规则。覆盖设备项目与来源项目关联、不同设备项目关联。
3. 解除 A—B 后，A 的后续项目查询不再包含经该关系取得的 B 内容；原归档及既有原文引用仍可读取。
4. 对本机上传和 VibeInsight 归档的检索结果，使用返回的来源、项目、原会话及消息位置读取原文，得到准确会话和消息；覆盖同名项目及不同来源中相同显示标识的情况。
5. 本机端三个支持平台均须经现有 CLI/MCP 实际完成当前项目查询及结果原文读取，确认项目身份和定位信息在入口间完整传递。
6. 旧客户端不提供项目身份时仍获得原有全局查询行为；Hub 不可用时，三个平台均按既有方式完成本机全局查询和本机原文读取。

### 首版范围确认

无新增事件的历史正文原地改写不要求被发现；验收报告须明确此范围，不能据此声称支持来源正文变更同步。具体机器、测试命令、实施顺序和 CI 配置另写入 `plan.md`。
