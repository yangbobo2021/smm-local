# 规格：Hub 重启后自动恢复同步

依据：[已确认意图](intent.md)。本规格为维护者审阅草稿；操作系统、后台运行方式、部署账号与凭据存储方案尚待确认，相关决定阻塞交付验收。

## 预期行为

1. 用户完成数据来源配置、凭据持久化及开机自动运行配置后，机器重启，Hub 无须用户登录交互式终端、手动启动同步或重新输入凭据，即可继续同步已配置的数据来源。是否需要用户登录才能运行，须在后台运行方案确认时明确；若该方案不能满足机器重启后自动继续同步的意图，须由维护者重新确认要求。

2. 自动恢复同步沿用重启前的数据来源配置、现有归档与已保存进度，不清空归档、不重置进度，也不将已导入内容再次导入。

3. 数据来源不可达时，Hub 保留已有归档及其可检索能力，报告该来源的同步失败，并保留可供恢复同步使用的进度。失败报告须能区分受影响来源与失败原因；报告的查看入口待确认。

4. 数据来源恢复可达后，Hub 自动重试并继续同步，无须重新配置来源或输入凭据。恢复同步后，既有归档仍可检索，新内容可被导入及检索，已导入内容不重复出现。重试间隔、退避与上限待确认。

5. 原前台同步命令通过环境变量取得凭据的使用方式继续有效。新增后台运行与凭据持久化不得使原有调用方被迫迁移。

6. 后台配置入口必须向用户说明并允许确认以下信息，不能依赖交互式终端中偶然存在的状态：
   - 自动同步的数据来源及其既有配置。
   - 后台进程使用的运行账号，以及该账号访问归档、进度和凭据的权限。
   - 归档与进度的位置，确保后台进程沿用现有数据。
   - 持久化凭据的配置方式、适用来源，以及更新和移除方式。
   - 自动运行是否已启用、同步失败信息的查看方式。

   具体入口与操作形式待维护者确认；确认后须补齐可供用户完成配置的说明。

## 边界与约束

- 已知运行要求仅为 Python 3.11+。现有资料未声明操作系统、服务类型或部署账号，不能据此认定支持 macOS、Windows 或 Linux。
- macOS 开发电脑上的交互式前台运行记录，不能证明开机后台运行、持久化凭据读取或其他平台兼容性。
- 本次没有仅支持 macOS 的授权，也没有新增 Windows/Linux 支持的确认。前台命令与新增后台组件的支持范围须分别明确，不得将后台组件的范围默认为整个项目的支持范围。
- 来源暂时不可达不得导致既有归档丢失、不可检索或已保存进度被清空。
- 凭据持久化必须使所选后台账号在启动时能够读取所需凭据，不能仅依赖用户交互式终端的环境变量。存储位置、访问控制及是否存在登录或解锁前提尚待确认。
- 自动同步与归档检索的进程关系尚不明确。若检索依赖独立进程，须明确重启后如何恢复检索入口，才能验收“保留可检索的归档”。
- 不得在缺少必需运行环境证据时判定交付通过。

## 设计决策

以下决定须在实施前由维护者确认：

| 待确认事项 | 对交付与验收的影响 |
| --- | --- |
| 前台命令与后台组件各自支持的操作系统及部署方式 | 决定交付范围、后台启动机制与必须取得证据的实际环境 |
| 后台账号、是否要求无人登录运行及进程生命周期 | 决定重启后能否自动运行，以及文件与凭据访问权限 |
| 凭据持久化机制及配置、更新、移除入口 | 决定后台启动时是否需要人工输入、登录或解锁，以及凭据验收状态 |
| 既有归档、来源配置与进度的定位及沿用方式 | 决定后台账号能否继续使用原有数据，避免意外创建空归档或重新导入 |
| 检索入口及其启动方式 | 决定来源失败和重启后如何验证归档仍可检索 |
| 失败报告入口与重试策略 | 决定用户如何发现故障，以及恢复后自动重试的可判定时间范围 |
| 前台与后台同时启动时的处理方式 | 决定如何避免并发写入、进度冲突与重复导入 |

操作系统的启动机制、账号环境、文件权限和凭据可用状态会直接影响核心承诺。因此，共用逻辑测试与包构建只能提供部分证据，不能替代实际重启及后台运行验证。

## 验收条件

1. **范围与配置可审阅**
   
   上述待确认事项均有明确决定，并与 `intent.md` 一致。用户能够根据最终配置说明完成来源绑定、凭据持久化、既有数据定位及自动运行启用，能够查看启用状态和失败信息。未确认支持范围或必要配置入口时，本规格仍为未完成草稿。

2. **实际环境覆盖要求**
   
   对最终承诺的每种后台操作系统与部署方式，必须在对应实际环境、选定后台账号及约定登录状态下，取得以下第 3—6 项的通过证据。若承诺包含不同凭据访问或账号状态，须覆盖会改变启动、读写或恢复结果的状态。不得以某个平台能启动替代其后续同步、检索和恢复结果。

3. **重启后自动继续同步**
   
   预先配置有效来源及持久化凭据，已有可检索归档和保存进度，并准备尚未导入的来源内容。机器实际重启后，Hub 按约定登录状态自动运行，无须手动启动或输入凭据；继续使用原配置、归档与进度，导入新内容且可检索，既有内容保持可检索且不重复导入。

4. **来源不可达时保留归档**
   
   在已有归档和进度的条件下，使来源不可达并实际重启机器。后台运行恢复后，用户可从约定入口查看对应来源的失败及原因；原有归档仍可检索，已保存进度未被清空，归档未被破坏。

5. **来源恢复后自动重试**
   
   延续第 4 项的失败状态，恢复来源并提供新内容。Hub 在已确认重试策略规定的范围内自动继续同步，无须人工重新配置或输入凭据；新内容导入后可检索，既有内容仍可检索，恢复前已导入内容不重复出现。

6. **后台身份与持久化数据有效**
   
   第 3—5 项均须使用最终交付的后台账号与凭据机制完成，证明其实际具有来源配置、归档、进度和凭据所需权限。仅在开发者交互式终端中成功读取环境变量不算通过。

7. **既有前台方式兼容**
   
   在最终确认的前台支持范围内，原命令仍能通过环境变量取得凭据并完成同步。前台与后台并存时，按确认的并发处理规则运行，不发生归档损坏、进度冲突或重复导入。若依赖平台特有的进程协调或文件机制，须在对应实际环境验证。

8. **证据边界明确**
   
   来源失败处理、进度恢复和重复导入判定等共用逻辑可复用同一套测试判据；但这些结果不能被表述为其他平台已实际运行通过。必要平台或运行状态缺少第 3—7 项对应证据时，交付仍未完成。具体机器、命令、测试步骤及实施顺序写入 `plan.md`。
