# 规格：Hub 自动同步 VibeInsight 历史与项目关联检索

本规格依据同目录下已确认的 [intent.md](intent.md) 及项目现有承诺起草。材料尚未确定的操作接口、来源字段及环境配置决定在下文标明，需维护者审阅确认。

## 预期行为

### 来源连接配置

1. 维护者通过 Hub CLI 提供 VibeInsight PostgreSQL 来源的连接信息，并验证、保存配置。必要信息包括数据库地址、端口、数据库名、读取账号、密码及 Hub 服务可调用的 `psql` 路径。各值应由来源管理员或 Hub 部署维护者提供、确认；读取账号应具备读取本次同步所需全部项目、会话、消息和事件数据的权限。
2. CLI 应说明配置作用于哪个 Hub、配置文件和服务状态目录，并明确验证所使用的服务运行身份与执行环境。CLI 当前账号能连接来源，不能单独作为长期运行服务可连接的依据。
3. 新配置只有验证成功后才能替换有效配置。验证失败应返回可诊断且不泄露密码的错误，原有效配置及其可用性保持不变；首次配置失败时不得留下已生效的来源配置。
4. 连接参数保存在 Hub 配置文件，密码保存在服务状态目录的专用秘密文件。服务运行账号能够读取密码，其他未授权普通账号不能读取。CLI 输出、日志和对话数据库不得包含密码原值。
5. 保存成功后，Hub 自动同步；Hub 或服务重启后使用已保存配置继续运行，无需再次输入密码。

### 自动归档与恢复

1. Hub 自动发现并归档来源账号可读取的全部项目历史，不要求用户逐个选择项目或手动触发会话导入。
2. 首次同步补齐可读历史；后续持续同步新增会话及已有会话追加的轮次。同步结果保留可识别的来源、项目、原会话和消息位置。
3. 来源后来新增可读项目时，应补齐该项目的全部可读历史，包括早于其他项目已保存同步进度的数据。
4. 来源暂时不可用、读取失败或凭据失效时，已有归档仍可通过现有 CLI/MCP 查询和读取。来源恢复后，Hub 自动重试未成功归档的数据。
5. 批次归档和同步进度一同提交。重启后从已提交位置继续，并通过近期事件回查去重；重复读取不得产生重复会话或消息，也不得跳过未成功归档的数据。
6. 首版只处理新增会话事件和追加轮次。没有新增事件的历史正文原地修改，不在自动发现范围内。

### 项目关联与查询

1. 项目关联由 Hub 维护者统一管理，支持设备项目与 VibeInsight 项目关联，也支持不同设备项目之间关联。维护入口应能列出带来源及稳定身份的项目，避免仅凭同名项目作选择。
2. 关联双向生效，仅扩展一层。若 A 与 B 关联、B 与 C 关联，查询 A 时包含 A、B，不因 B 与 C 的关系自动包含 C。
3. 解除关联后，后续项目查询不再通过该关系扩展；已归档数据不删除，已有原文引用仍可读取。
4. 本机端补传项目归属；CLI/MCP 发起项目查询时携带当前项目身份。Hub 据此查询当前项目及直接关联项目，同名但身份不同的项目保持可区分。
5. 现有 CLI/MCP 能检索同步归档，并返回来源、项目、原会话和消息位置；调用方可以根据返回引用精确读取对应原文，原文内容与位置一致。
6. 旧客户端的全局查询继续可用，不因缺少项目身份而报错或被隐式限制到某个项目。
7. Hub 不可用时，沿用现有本机全局回退行为；不得将本机回退结果表述为已覆盖 Hub 中全部归档。

## 边界与约束

- 首版为单用户，不引入多用户授权和隔离。
- Hub 和本机端继续支持 Windows、Linux、macOS，不缩减现有发行范围。
- Hub 保持既有运行方式：Windows 系统服务使用 LocalService；Linux 使用 systemd 用户服务；macOS 使用 launchd 系统服务。
- 来源读取由 Hub 服务调用外部 `psql`，仅执行只读查询，不修改 VibeInsight 数据，不要求在真实来源服务器造数。
- `psql` 的安装位置、可执行权限、服务环境、来源网络可达性和秘密文件权限均属于本次交付边界。开发终端能够执行 `psql` 不代表后台服务能够执行。
- 同步范围受来源账号读取权限限制；“全部历史”指该账号可读取的数据。新增可读项目必须能被发现，不能仅依赖一个全局时间游标。
- 已有原文引用、现有全局查询及本机回退保持兼容；新增项目归属和来源信息不得破坏旧引用解析。
- 目前只有 macOS 开发环境具备已知执行条件；Windows、Linux 尚无本次执行记录。这不构成缩减支持范围或免除必要验收的依据。

## 设计决策

1. **配置以服务实际使用为准。** CLI 配置流程必须确保保存位置、秘密文件权限和 `psql` 执行条件适用于目标 Hub 服务。Windows LocalService、Linux 用户服务及 macOS 系统服务的账号与环境差异，必须分别取得实际运行证据。
2. **密码与普通连接参数分离。** 沿用专用秘密文件设计，通过各平台有效的权限机制保护密码；不能仅检查配置文件中未出现密码而忽略秘密文件的可读范围。
3. **归档与进度原子提交。** 批次失败不得推进对应进度；批次成功后重启不得重复归档。近期回查与稳定身份去重共同覆盖重读和追加轮次。
4. **项目发现与历史补齐不能受既有全局进度截断。** 实现需支持新增可读项目从其历史起点补齐；具体进度结构写入 plan.md。
5. **来源身份与项目身份必须稳定。** 同名项目、不同设备项目及来源会话不能仅按展示名称合并。引用定位应在重启、重复同步和解除关联后保持有效。

以下事项需维护者在实施前确认：

- 来源数据库的表或视图、读取权限、稳定项目／会话／消息／事件标识，以及事件顺序和追加轮次的判定方式。这些决定影响只读查询、去重、精确引用及历史补齐能否成立。
- CLI 的配置、状态查看和关联管理命令，以及 MCP 项目身份和原文定位字段的具体契约；应提供必要值的说明、项目身份的列举与选择途径、可执行示例。
- 各平台 `psql` 的部署责任、路径配置方式，以及 CLI 在目标服务身份下验证连接、保存配置和检查权限的方式。
- 自动同步周期、近期回查窗口和失败重试规则，以便为“持续同步”和“恢复后自动重试”建立可判定的时间边界。

上述决定不得改变已确认的平台、服务类型、凭据保护及兼容承诺；若来源无法提供所需稳定标识或事件信息，应先确认意图调整，不能在实现中静默降低保证。

## 验收条件

### 共用行为判据

1. 在可控 PostgreSQL 来源中准备多个项目、已有会话及多轮消息。完成有效配置后，全部可读历史通过现有 CLI/MCP 可检索；返回的来源、项目、原会话和消息位置正确，按引用读取的原文完整且对应准确。
2. 初次同步完成后，分别新增会话、向旧会话追加轮次。两者均在已确认的同步时限内归档，已有消息不重复。
3. 已有同步进度后新增一个可读项目，其历史事件早于该进度。该项目历史仍全部补齐，后续追加也能继续同步。
4. 在批次提交前中断并重启，未提交数据能够重试；在提交后重启，已提交数据不重复。近期事件重复读取后，归档条数、内容和引用均保持正确。
5. 来源中断时，已有归档仍可查询和读取；中断期间产生的未归档数据在恢复后自动补齐，无遗漏和重复。
6. 以有效配置运行后提交无效凭据，CLI 返回不含密码的失败信息，原配置继续可用；首次提交无效配置时，无有效来源配置被激活。
7. 建立 A—B、B—C 关联，验证双向查询和单层扩展：A 包含 B、排除仅经 B 可达的 C；B 包含 A、C。设备—来源项目、设备—设备项目两类关系均通过。同名不同身份项目不误合并。
8. 解除关联后，项目查询不再经该关系扩展，归档数据仍存在，解除前取得的原文引用仍可读取。
9. 新本机端补传的项目归属与 CLI/MCP 当前项目身份一致；旧客户端全局查询继续返回全局结果，旧原文引用继续可读。
10. Hub 不可用时，CLI/MCP 按既有行为回退到本机全局查询，结果范围和错误表现与现有兼容承诺一致。
11. 对没有新增事件的历史正文原地修改，不要求自动发现；该范围限制在使用说明中明确。

### 必须取得的平台与运行环境证据

下列验收须分别在 Windows LocalService 系统服务、Linux systemd 用户服务、macOS launchd 系统服务中实际通过。各环境可复用同一来源夹具和判据，但结果必须注明平台、服务身份及动作前状态：

- 从 CLI 保存有效配置后，实际后台服务能找到并执行配置的 `psql`、连接来源并完成首次归档及精确原文读取。
- 在同一服务持续运行状态下，新增会话、旧会话追加轮次及晚发现项目的早期历史均成功归档，符合共用判据 2、3。
- 服务停止并重启后无需输入密码，继续同步且不重复；来源中断、恢复及失败数据补齐符合共用判据 4、5。
- 服务具有读取秘密文件的权限；另一个未授权普通账号无法读取。CLI 输出、服务日志和对话数据库中没有密码原值。
- 已有有效配置时提交无效凭据，原配置继续供该服务使用；配置验证不能仅以 CLI 当前账号的连接成功代替。

本机端在 Windows、Linux、macOS 的现有支持运行方式下，分别取得项目归属补传、当前项目身份传递、旧客户端全局查询与旧引用兼容、Hub 不可用时本机全局回退的通过证据。

项目关联图的单层扩展、去重规则、引用编码及事务逻辑可使用共用自动化测试验证，并在实际 Hub 集成环境中按共用判据完成端到端验证；无需在每个平台重复全部图关系组合。但共用测试不能替代上述服务调用、凭据权限、重启恢复及本机端兼容行为的平台证据。

来源数据可使用独立 PostgreSQL 测试环境中的合成事件，无需在真实服务器造数；涉及 `psql` 的服务集成验收必须实际调用外部客户端，不能仅使用模拟来源替代。Python 测试通过、独立 Hub 启动或两个 wheel 安装成功，仅证明对应局部行为。

所有必要平台证据齐备、共用行为判据通过且待确认决定已解决，方可判定交付通过。Windows 或 Linux 必要证据缺失时，交付仍未完成。具体机器、实施位置、命令、测试步骤及 CI 配置写入 plan.md。
