# 规格：Hub 在 Linux systemd 用户服务启动后自动同步

依据：[已确认意图](intent.md)。

## 预期行为

1. Hub 的 Linux systemd 用户服务每次启动后，自动执行一次已有同步操作，拉取已配置来源的新对话，无需用户手动运行同步命令。机器重启后，服务应自动启动并触发该同步。
2. 启动同步使用相应 Linux 服务账号的 Hub 用户状态目录，沿用其中已有的来源凭据和数据库同步进度。用户无需重新提供凭据，也无需迁移配置。该目录应与现有 Hub 配置所确定的状态目录一致；实际路径及服务账号须依据现有部署配置确认。
3. 同步成功后，新对话可通过现有检索入口查询，已有归档继续可检索。
4. 启动同步失败时，报告可定位的失败原因，且不泄露凭据；已有归档仍可通过现有入口检索。失败不得清空归档或重置数据库进度。
5. 失败后再次执行已有同步操作，包括通过服务再次启动触发同步时，沿用数据库进度，不重复导入已经归档的消息。

## 边界与约束

- 本次 Hub 交付范围仅为 Linux systemd 用户服务，不支持或验收 Windows/macOS 上的 Hub 运行方式。
- Windows、macOS、Linux 本机客户端继续通过既有 HTTPS 协议访问 Hub。本次不修改客户端程序、协议、API、CLI/MCP、配置格式或同步算法。
- 本次仅将已有的一次同步操作接入服务启动后的生命周期，不新增周期同步或自动重试策略。既有重试入口继续可用。
- 服务必须以能够读取既有状态目录凭据的相应 Linux 服务账号运行，不能依赖交互式登录会话临时提供的环境变量、工作目录或权限。
- 启动同步失败不得导致已有归档失去检索能力。
- 当前 macOS 开发环境只能验证共用逻辑，不能提供 Linux systemd 服务启动、机器重启及服务账号权限行为的实际通过证据。

## 设计决策

- 启动生命周期复用已有同步操作及其进度、去重机制，避免引入另一套同步语义。
- 同步失败与 Hub 检索可用性分离；失败应可观察，同时允许 Hub 继续提供已有归档的检索服务。

以下事项仍需维护者确认，且须在实施前落实：

1. **机器重启后的用户服务启动机制。** 明确是否要求服务账号未交互登录时即自动启动，以及采用的 systemd 用户服务启用方式和必要前提。该决定影响重启验收的登录状态；仅手动启动服务不能证明满足机器重启后的自动同步意图。
2. **状态目录的服务环境解析方式。** 根据现有部署确认服务账号、状态目录实际位置及必要环境，保证服务启动时读取与既有同步命令相同的凭据和进度，不新增配置格式。
3. **失败报告入口。** 确认沿用的日志或状态入口及查看方式。失败报告至少应能识别失败来源和原因，并避免输出凭据；该入口须用于实际服务环境的失败验收。

## 验收条件

以下第 1—5 项必须在实际 Linux systemd 用户服务环境取得通过证据，使用已确认的服务账号、状态目录和启动配置。共用单测、包构建或 macOS 上直接调用同步操作不能替代这些证据。

1. **服务启动触发同步：** 状态目录已有有效来源凭据和数据库进度，来源存在尚未归档的新对话。启动用户服务后，无需手动执行同步命令，即可通过现有检索入口查询到新对话；已有归档仍可检索，原有进度被沿用。
2. **机器重启后自动同步：** 在已确认的自动启动配置和登录状态下，来源存在新增对话。机器重启后，无需手动启动服务或运行同步命令，Hub 自动运行并导入新增对话，现有 HTTPS 检索入口可查询新增及已有归档。若承诺无需交互登录，本项须在服务账号未交互登录时完成。
3. **服务环境读取凭据：** 在不依赖交互式登录环境的服务启动条件下，相应服务账号能够读取既有状态目录，完成同步并保留原有进度。不能仅以交互式终端执行成功作为通过依据。
4. **失败报告及检索连续性：** 分别在来源访问失败和服务无法读取凭据的状态下启动服务。已确认的报告入口能显示可定位原因且不泄露凭据；Hub 仍通过现有 HTTPS 入口提供已有归档检索，归档和进度未被清空或重置。
5. **失败后重试及去重：** 在已有归档和同步进度的状态下触发同步失败，恢复失败条件后再次启动服务。新增消息成功归档，已有消息不重复导入；随后再次启动服务，同一批消息的归档数量保持不变。若同步可能在部分导入后失败，须覆盖该状态下的恢复结果。
6. **兼容性与共用逻辑：** 在当前 macOS 环境可验证启动触发逻辑、错误传播以及既有同步的进度和去重行为。由于客户端和 HTTPS 协议未修改，本次无需在三个客户端平台重复完整测试；但 Linux 服务实际成功、失败及恢复后的 HTTPS 检索结果，必须由第 1—5 项提供证据。macOS 共用逻辑通过不得表述为 Linux systemd 已通过。
7. **交付判定：** 待确认事项须已形成明确决定，且上述必要证据齐备后才能判定交付通过。目前缺少 Linux 服务启动和机器重启后的执行记录，相关验收仍属未完成项。
