# 规格：Hub 服务启动后自动同步对话

以同目录下已确认的 [intent.md](intent.md) 为依据。启动同步的触发时点、失败后的自动重试策略及失败报告方式仍需维护者确认。

## 预期行为

1. Linux systemd 用户服务每次启动后，Hub 自动执行已有的一次同步操作，从已配置来源拉取新对话，无需用户手动执行同步命令。机器重启后服务启动时同样适用。
2. 启动同步沿用相应 Linux 服务账号在 Hub 用户状态目录中的已有来源凭据，并从数据库保存的进度继续同步，不要求重新配置凭据或重置进度。
3. 启动同步失败时，报告可定位问题的失败原因；失败不阻止已有归档继续被检索。
4. 失败后再次执行同步时，继续遵循已有同步操作的进度与去重行为，不重复导入已归档消息。
5. Windows、macOS、Linux 本机客户端继续通过既有 HTTPS 协议访问 Hub；此次变更不要求客户端调整。

## 边界与约束

- 本次交付仅覆盖 Linux systemd 用户服务中的 Hub，不支持或扩展 Hub 在 Windows、macOS 上的运行方式。
- 仅将已有的一次同步操作接入服务启动生命周期。同步算法、API、CLI/MCP、客户端程序及配置格式保持不变。
- 服务环境可能不同于交互式登录环境。启动同步必须能以服务账号定位并读取已有状态目录中的凭据，不能依赖交互式登录环境才能完成同步。
- 凭据继续仅由相应 Linux 服务账号读取，不因自动同步扩大读取权限。
- 凭据读取或来源同步失败时，均适用失败报告及已有归档可检索的要求。
- 当前 macOS 开发环境可运行共用逻辑测试，但不能验证 Linux systemd 生命周期。现有材料没有本次 Linux 服务启动或机器重启后的执行记录，不能据此宣称该场景已通过验收。

## 设计决策

- 复用已有的一次同步操作，保留现有同步、进度及去重语义，以限制变更范围。
- 以下事项需维护者在实施前确认：
  - 自动同步相对于 Hub 可提供检索服务的具体触发时点，以及是否阻塞启动就绪。
  - 同步失败后是否自动重试；若需要，其触发条件、间隔和次数。本规格不预设新增自动重试机制。
  - 失败原因的报告渠道与必要信息，确保维护者能在服务运行环境中查看并定位问题。

## 验收条件

1. 已配置来源存在新对话时，启动 Linux systemd 用户服务，无需手动同步即可将新对话归档并检索。
2. 机器重启后，systemd 用户服务启动并自动同步，新增对话可被检索，无需手动执行同步命令。
3. 已有凭据和数据库进度存在时，服务启动同步复用这些状态，无需重新配置，并从已有进度继续处理。
4. 服务不具备交互式登录环境中的变量时，仍能以服务账号使用已有凭据；凭据读取权限没有扩大。
5. 启动同步因凭据读取或来源同步问题失败时，可通过确认后的报告渠道查看对应失败原因，已有归档仍可通过既有接口检索。
6. 同步失败后再次执行同步，已导入消息不重复出现；反复启动服务也不产生重复消息。
7. Windows、macOS、Linux 本机客户端仍能通过既有 HTTPS 协议访问 Hub，API、CLI/MCP 及配置格式保持兼容。
8. Linux systemd 服务启动和机器重启场景须有对应的实际执行结果才能判定通过；仅有 macOS 共用逻辑测试结果不满足这两项验收条件。
