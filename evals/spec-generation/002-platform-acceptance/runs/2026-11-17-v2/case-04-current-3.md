# 规格：Hub 启动时自动同步已配置来源

以同目录下已确认的 [intent.md](intent.md) 为依据。尚需维护者决定的事项见「设计决策」。

## 预期行为

1. Linux systemd 用户服务启动后，Hub 自动执行已有的一次同步操作，拉取已配置来源的新对话，无需手动运行同步命令。机器重启后该用户服务启动时，同样触发同步。
2. 自动同步沿用 Hub 用户状态目录中的已有来源凭据和数据库同步进度，不要求重新配置凭据，也不从头导入已归档消息。
3. 自动同步成功后，新拉取的对话可通过既有检索入口访问。
4. 自动同步失败时，报告可用于定位问题的失败原因，且不泄露凭据。已有归档仍可通过既有入口检索。
5. 失败后再次执行同步，或服务再次启动触发同步时，沿用已有进度，不重复导入已归档消息。

## 边界与约束

- 本次交付仅覆盖 Linux systemd 用户服务，不增加或承诺 Windows、macOS 上的 Hub 运行支持。
- Windows、macOS、Linux 本机客户端继续通过既有 HTTPS 协议访问 Hub，其使用方式保持兼容。
- 本次仅将已有的一次同步操作接入服务启动后的生命周期；同步算法、API、CLI/MCP、客户端程序及配置格式不变。
- 自动同步使用相应 Linux 服务账号可读取的已有状态和凭据，不得依赖仅存在于交互式登录环境中的变量或配置，也不得扩大凭据读取权限。
- 没有已配置来源时，无需新增配置即可启动服务，已有归档仍可检索。
- 本次不引入周期同步要求；失败后的自动重试策略尚待维护者确认。
- 当前 macOS 开发环境可验证共用逻辑，但不能证明 Linux systemd 生命周期行为已通过验收。现有材料没有本次 Linux 服务启动或机器重启后的执行记录。

## 设计决策

以下事项需维护者在实施前确认：

- **失败报告入口**：是否使用 systemd 用户服务日志承载失败原因，是否另需既有状态入口展示。报告应能识别失败来源及原因，并避免输出凭据。
- **失败重试策略**：是否仅依靠后续服务启动及既有手动同步入口重试，或需要自动重试；若需要，需明确触发条件、间隔与停止条件。
- **开机启动前提**：本次是否包含确保用户服务在机器重启后无需交互式登录即可启动的配置交付。无论采用何种方式，机器重启后自动拉取的验收均须覆盖实际服务启动。
- **启动同步与服务就绪的关系**：同步执行期间是否允许检索，以及如何判定服务就绪。同步失败不得导致已有归档持续不可检索。

## 验收条件

1. 在已配置来源和凭据的 Linux 环境中，机器重启后，systemd 用户服务自动启动并触发同步；无需手动命令，新对话最终可检索。
2. 单独重新启动该服务，也会触发已有的一次同步操作。
3. 自动同步使用原有凭据和数据库进度；不要求重新授权，不重新导入已归档消息。
4. 服务不具备交互式登录环境中的专用变量时，仍能读取服务账号有权访问的已有凭据和进度并完成同步。
5. 使启动同步发生失败后，能从维护者确认的报告入口获得失败原因，报告不包含凭据，已有归档仍可检索。
6. 在同步部分完成后发生失败，再次同步能继续处理剩余内容；已成功导入的消息不产生重复记录。
7. 来源无新增消息时，多次启动服务不会增加重复消息。
8. 未配置来源时，服务仍可启动，已有归档仍可检索。
9. 既有 HTTPS 客户端访问、API、CLI/MCP、配置格式及手动同步行为保持兼容。
10. Linux systemd 启动及机器重启行为具有实际执行证据；仅通过 macOS 共用逻辑测试不视为满足上述生命周期验收条件。
