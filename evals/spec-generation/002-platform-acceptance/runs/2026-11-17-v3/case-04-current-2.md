# 规格：Linux Hub 用户服务启动后自动同步

本规格依据同目录下已确认的 [intent.md](intent.md)。仍需维护者决定的事项列于「设计决策」。

## 预期行为

1. 已配置来源的 Linux Hub systemd 用户服务每次启动后，自动执行已有的一次同步操作，无需用户手动运行同步命令。机器重启后，当该用户服务启动时，同样触发同步。
2. 自动同步沿用 Hub 用户状态目录中的已有来源凭据和数据库同步进度，不要求重新配置来源或从头导入。
3. 自动同步成功时，新对话进入已有归档，并可通过既有检索入口访问。
4. 自动同步失败时，报告可用于定位问题的失败原因；Hub 继续提供既有归档的检索能力。
5. 失败后再次执行同步时，沿用已有进度，不重复导入已经归档的消息。该要求同时适用于后续服务启动触发的同步和既有手动同步入口。

## 边界与约束

- 本次交付仅适用于 Linux systemd 用户服务，不支持或扩展 Hub 在 Windows、macOS 上的运行方式。
- Windows、macOS、Linux 本机客户端继续通过既有 HTTPS 协议访问 Hub，客户端行为与协议不变。
- 本次仅将已有的一次同步操作接入服务启动后的生命周期，不改变同步算法、API、CLI/MCP、客户端程序或配置格式。
- 自动同步使用相应 Linux 服务账号可读取的已有凭据。服务环境可能与交互式登录环境不同，不能以交互式终端中同步成功替代服务环境下的可用性要求。
- 自动同步失败不得导致已有归档不可检索；失败报告不得泄露凭据。
- 本次不引入周期同步或新的自动重试策略。重试去重要求不代表新增自动重试机制。
- 当前仅具备 macOS 开发环境，共用逻辑测试不能证明 Linux systemd 生命周期接入有效。目前缺少本次 Linux 服务启动及机器重启后的执行记录，相关验收仍待完成。

## 设计决策

- 自动同步作为服务启动后的附加操作，其成功与否不作为已有归档可检索的前提，以满足同步失败时仍可使用归档的意图。
- **待维护者确认：**机器重启后，该用户服务自动启动所需的启用状态、用户会话或 lingering 等前置条件，由本次交付负责配置，还是作为部署前提。无论采用哪种方式，都应明确保证目标部署中机器重启后无需手动启动服务或执行同步命令。
- **待维护者确认：**启动同步失败的报告入口及最低诊断信息。报告应使维护者能够识别失败的启动同步及其原因，同时避免暴露凭据内容。

## 验收条件

1. 在已配置来源和有效凭据的 Linux systemd 用户服务环境中，启动服务后无需手动同步，新对话能够进入归档并通过既有入口检索。
2. 在维护者确认的部署前提下重启机器，无需手动启动服务或执行同步命令，Hub 能自动同步来源中的新对话。
3. 已有数据库包含同步进度时，启动同步沿用该进度及已有凭据，不要求重新授权、重新配置来源或清空归档。
4. 启动同步因凭据不可读取或来源访问失败而失败时，能够从确认的报告入口获知失败原因，报告中不包含凭据内容，且已有归档仍可检索。
5. 同步失败后再次同步，已归档消息不重复导入；存在尚未归档的新消息时，后续成功同步能够将其归档。
6. 无新消息时重复启动服务，不增加重复归档消息。
7. 既有 API、CLI/MCP、客户端 HTTPS 访问及配置格式保持兼容，无需因本次变更调整调用方式。
8. Linux 服务启动与机器重启场景均有实际执行证据后，方可判定对应验收条件通过；仅有 macOS 共用逻辑测试结果不足以通过这两项验收。
