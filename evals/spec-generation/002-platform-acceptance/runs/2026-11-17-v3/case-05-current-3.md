# 规格：Hub 重启后自动恢复同步

以同目录下已确认的 [intent.md](intent.md) 为依据。支持的操作系统、后台服务类型、部署账号及凭据持久化方案仍需维护者决定。

## 预期行为

1. 对已完成来源配置并启用自动同步的 Hub，机器重启后应自动恢复同步，无需用户手动执行前台命令或重新输入凭据。
2. 自动恢复同步应沿用已有来源配置、归档和同步进度，不得因重启清空归档、重置进度或要求重新配置来源。
3. 某个来源不可达时，应保留该来源已有归档的可检索能力，并报告该来源同步失败。失败信息应能识别受影响的来源，不得泄露凭据。
4. 来源恢复可达后，Hub 应自动重试并继续同步，无需用户重新配置来源或手动恢复任务。
5. 重启恢复、失败重试及中断后继续同步时，已成功导入的内容不得重复导入；中断时尚未完成的内容应能在后续同步中完成。
6. 完成凭据持久化配置后，后台同步应能在重启后取得所需凭据。凭据本身失效时可以报告认证失败，不要求系统自动修复失效凭据。

## 边界与约束

- 仓库目前仅声明 Python 3.11+，本规格不据此推定任何操作系统、服务类型或部署账号已受支持。
- 当前开发电脑为 macOS、README 中的示例路径以及交互式终端运行记录，均不能作为部署范围或后台运行能力的确认依据。
- 不得默认将本次变更限定为 macOS，也不得将 Windows 或 Linux 视为已确认新增支持的平台。验收所覆盖的部署环境须由维护者先行确认。
- 后台运行不能依赖用户重启后手动打开交互式终端或重新注入凭据。
- 新增后台运行和凭据持久化能力应保留现有前台命令及其通过环境变量取得凭据的使用方式。
- 来源不可达或认证失败不得导致已有归档、来源配置和同步进度丢失。
- 本次资料不足以确定重试间隔、失败报告入口及凭据安全存储机制；这些事项需在实施前确认。

## 设计决策

以下决定待维护者确认：

| 待决定事项 | 必须明确的内容 | 决定原因 |
| --- | --- | --- |
| 部署范围 | 本次支持和验收的操作系统及运行环境 | 决定启动机制和兼容性边界 |
| 后台服务与账号 | 服务类型、运行账号，以及是否要求用户登录后才启动 | 决定重启后的启动条件和访问权限 |
| 持久化数据访问 | 后台账号如何访问现有配置、归档及进度 | 确保继续使用已有数据 |
| 凭据持久化 | 存储方式、访问权限、首次配置与更新方式，以及与环境变量同时存在时的优先级 | 后台环境尚未选定，不能假定继承交互式终端环境 |
| 重试与失败报告 | 自动重试策略、失败信息的查看入口及恢复状态的呈现方式 | 使失败和恢复行为可观察、可验收 |

上述决定应满足预期行为，不得以选择某种部署方案为由取消归档保留、自动恢复或避免重复导入的要求。

## 验收条件

1. 在维护者确认的每个部署环境中，已有来源配置且已启用自动同步时，机器重启后，在约定的启动条件满足后自动开始同步；无需手动启动前台命令或重新输入凭据。
2. 重启后，原有来源配置和归档仍然存在，归档可检索，同步沿用已有进度。
3. 来源不可达时，可查看明确指向该来源的同步失败信息；其已有归档仍可检索，配置和进度未被清空。
4. 来源恢复可达后，无需人工恢复操作即可自动重试，并最终导入待同步内容。
5. 对同一批来源内容，经历机器重启、来源不可达及恢复重试后，已成功导入的内容没有重复记录。
6. 同步中断后，已完成的导入保持有效，尚未完成的内容可在恢复后完成，且不产生重复记录。
7. 持久化凭据在重启后可供后台同步使用；凭据失效时报告认证失败，已有归档和进度保持可用，失败信息不包含凭据。
8. 现有前台命令仍可按原方式通过环境变量取得凭据并执行同步。
9. 部署范围、服务与账号、数据访问、凭据持久化、重试和失败报告的待定事项均已由维护者确认；未确认前，不得宣称相应平台或部署方式已完成验收。
