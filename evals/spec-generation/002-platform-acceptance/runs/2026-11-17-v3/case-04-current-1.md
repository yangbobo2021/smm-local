# 规格：Hub 服务启动后自动同步已配置来源

意图依据：[intent.md](intent.md)。

## 预期行为

1. Linux systemd 用户服务每次启动后，Hub 自动执行已有的一次同步操作，拉取已配置来源的新对话，无需用户手动运行同步命令。机器重启后，只要该用户服务已自动启动，同样触发同步。
2. 启动同步沿用 Hub 用户状态目录中的已有来源凭据及数据库保存的同步进度。服务环境与交互式登录环境不同，不应导致 Hub 忽略已有凭据、使用另一份数据库或从头导入。
3. 启动同步成功后，新导入的对话可通过既有检索入口检索，已有归档继续可用。
4. 启动同步失败时，Hub 报告可用于定位问题的失败原因；失败不得使已有归档无法检索，也不得泄露凭据内容。
5. 同步失败后再次执行已有同步操作，或服务再次启动触发同步时，继续沿用数据库进度，不重复导入已归档消息。

## 边界与约束

- 本次交付仅覆盖 Linux systemd 用户服务，不支持或扩展 Hub 在 Windows、macOS 上的运行方式。
- Windows、macOS、Linux 本机客户端继续通过既有 HTTPS 协议访问 Hub，客户端行为不变。
- 本次仅将已有的一次同步操作接入服务启动后的生命周期；同步算法、API、CLI/MCP、客户端程序及配置格式均不变。
- 凭据继续由相应 Linux 服务账号读取，不扩大现有读取权限。
- 本次不引入周期同步或自动重试策略。再次启动或通过既有入口重试时，保持已有同步语义。
- 机器重启后的自动同步以 systemd 用户服务能够自动启动为前提；现有资料未说明该前提是否已经具备。
- macOS 上的共用逻辑测试不能替代 Linux systemd 服务启动及重启场景的验收。目前没有这些场景的执行记录。

## 设计决策

- 启动同步失败与归档检索可用性分离：同步失败须可观察，但不阻断已有归档的检索，以满足失败时仍可使用归档的意图。
- 以下事项仍需维护者确认：
  - 是否需要在本次交付中补齐机器重启后 systemd 用户服务自动启动的配置，以及其适用的登录条件。
  - 启动同步失败原因的报告入口和必要信息。
  - 启动同步期间，检索服务何时开始对外可用。
  - 启动同步与既有手动同步入口同时触发时，是否沿用已有并发控制；若没有，应采用何种协调行为。

## 验收条件

1. Linux systemd 用户服务启动后，无需手动同步即可触发已有同步操作；已配置来源中存在新对话时，新对话最终可被既有检索入口检索。
2. 机器重启且用户服务自动启动后，自动触发同步并导入新对话。仅完成手动启动场景，不算通过此项。
3. 在服务环境与交互式登录环境不同的情况下，启动同步仍使用相应服务账号已有的凭据和数据库进度，无需重新配置来源。
4. 来源中已有消息已归档时，启动同步只补充尚未归档的消息，已有归档不产生重复记录。
5. 启动同步失败时，可从维护者确认的报告入口获知失败原因，报告中不包含凭据内容；已有归档仍可通过既有入口检索。
6. 同步部分完成后失败，再通过既有入口重试或重启服务，最终不重复导入已归档消息，并能继续处理尚未归档的消息。
7. 既有 API、CLI/MCP、配置格式及三种平台客户端的 HTTPS 访问行为保持兼容。
8. Linux systemd 启动及机器重启场景须有实际执行结果后，才能认定相关验收项通过；当前资料不足以认定通过。
