# 规格：Hub 重启后自动恢复同步

本规格依据同目录下已确认的 [intent.md](intent.md)。操作系统、后台运行方式、部署账号及凭据持久化方案仍需维护者确认；当前 macOS 开发环境不能代替这些决定。

## 预期行为

1. 用户完成来源配置及后台运行配置后，机器重启应自动启动 Hub，并继续同步已配置的数据来源，无需用户登录交互式终端、手动运行同步命令或重新输入凭据。是否要求在无人登录时运行，以及启动所需网络等前提，应随后台运行方式一并确认。
2. 自动恢复同步应使用原有来源配置、归档和进度，不清空已有数据，不从头重复导入已完成的内容。恢复后新增内容应可检索。
3. 来源不可达时，Hub 应保留已有归档及有效进度，已有归档仍可检索，并提供可查看的同步失败状态。失败信息应能识别受影响来源，不泄露凭据。
4. 来源恢复可达后，Hub 应自动重试并从有效进度继续同步，无需重新配置来源或输入凭据；重试不得重复导入已有内容。
5. 现有前台同步命令应继续可用。后台与前台访问同一份配置、归档及进度时，应避免并发同步造成重复导入、进度覆盖或数据损坏；具体互斥行为须在实施前确认。
6. 用户应有明确途径完成后台运行配置、首次凭据持久化及失败状态查看。交付说明必须明确：
   - 适用的操作系统、后台运行方式及运行账号。
   - 每个来源所需凭据的含义、获取途径，以及首次录入和更新方式；沿用现有环境变量时，应说明其与持久化凭据的关系。
   - 运行账号如何访问现有配置、归档、进度及凭据。
   - 如何确认自动启动已配置成功，以及在哪里查看来源同步失败状态。

## 边界与约束

- 已知运行要求仅为 Python 3.11+，不能据此推断支持 macOS、Windows 或 Linux，也不能从 README 示例路径推断部署范围。
- 本次后台组件支持的操作系统及运行方式尚未确定。维护者既未授权仅支持 macOS，也未确认新增 Windows/Linux 支持。须先确认本次交付范围，再据此确定实现及实际环境验收覆盖。
- 现有前台命令的跨平台承诺同样没有资料支持；本次应保持其现有调用方式及环境变量凭据入口兼容，不宣称未经确认的平台支持。
- 凭据持久化是本次新增行为。不得假定后台进程能够继承交互式终端环境变量、访问当前用户的文件或解锁当前用户的凭据存储。
- 来源不可达不能导致已有归档被删除、失去检索能力，或导致进度被错误推进。失败状态不得被呈现为同步成功。
- 无需重新输入凭据适用于有效凭据在重启后的复用；凭据撤销、过期或权限变化时，应明确报告认证失败并提供更新途径。
- 实际验证前不得宣称重启恢复已通过。当前仅在 macOS 交互式终端运行过前台命令的记录，不构成后台运行、凭据持久化或重启恢复的通过证据。

## 设计决策

以下事项须在实施前由维护者确认：

| 待确认事项 | 对交付和验收的影响 |
| --- | --- |
| 本次支持的操作系统及部署方式 | 决定后台启动机制及必须取得证据的实际运行环境；不得默认仅交付 macOS，也不得默认覆盖三个系统。 |
| 后台运行账号、是否要求无人登录运行 | 决定启动时机、文件权限及凭据可用性；若要求无人登录，验收必须覆盖重启后无人登录状态。 |
| 凭据持久化方式及首次配置入口 | 决定凭据如何安全保存、更新并供后台账号读取；依赖用户会话或解锁状态的方案须明确其是否满足自动恢复要求。 |
| 配置、归档及进度的位置与权限 | 决定后台是否能复用原数据；账号变化不能使 Hub 意外使用空目录或新进度。 |
| 失败状态查看入口及自动重试策略 | 决定用户如何获知失败，以及来源恢复后何时应继续同步；重试触发规则和等待上限须可明确判定。 |
| 前后台并发访问策略 | 决定冲突时拒绝、等待或其他可观察行为，并保证归档和进度一致。 |

启动后台进程本身不足以证明意图成立。验收必须覆盖后台账号读取持久化凭据、访问原数据、恢复进度，以及失败后的检索和重试结果。上述决定尚缺，当前草稿不能据此判定交付完成。

## 验收条件

1. **覆盖范围确定**
   
   维护者已确认上述必要决定，规格明确列出后台组件支持的操作系统、运行方式、账号及登录状态要求。每一种已承诺且存在启动、凭据访问或文件权限差异的实际运行环境，均须取得下列适用行为的通过证据。

2. **首次配置与状态查看**
   
   在每种已确认的后台运行环境中，用户能依据交付说明完成来源配置、凭据持久化及自动启动配置，并通过指定入口确认配置结果、查看同步状态。配置项含义、凭据获取途径及账号访问要求完整，无需自行猜测。

3. **机器重启后继续同步**
   
   在上述每种环境中，预先建立包含可检索归档及有效进度的来源，并完成凭据持久化。机器实际重启后，在约定的登录状态和运行账号下，Hub 自动恢复同步，无需手动启动或重新输入凭据；原归档仍可检索，原进度被复用，来源中的新增内容最终可检索，已导入内容没有重复记录。

4. **不可达、恢复与自动重试**
   
   在上述每种环境及约定账号、登录状态下，分别覆盖启动时来源不可达和同步期间来源变为不可达：
   - Hub 在指定入口报告对应来源失败，已有归档保持可检索，进度没有错误推进。
   - 来源恢复后，Hub 按已确认策略自动重试并继续同步，无需重新配置或输入凭据。
   - 重试完成后，新增内容可检索，原有内容没有重复导入。
   
   此项须覆盖后台运行中的实际检索入口及同步结果，不能仅以进程仍在运行作为通过依据。

5. **凭据及文件访问**
   
   每种已确认后台环境均有实际证据表明：重启后指定账号能够读取有效的持久化凭据并访问原配置、归档及进度。凭据无效或必要文件不可访问时，Hub 给出可识别的失败状态，不误报同步成功、不覆盖原数据，状态信息不泄露凭据。用户能通过说明中的入口更新凭据并恢复同步。

6. **前台兼容与并发保护**
   
   现有前台命令仍能按原调用方式使用环境变量凭据完成同步。在每种本次承诺前后台共用数据的环境中，实际验证同时发起同步时符合已确认的并发策略，最终归档无重复或损坏，进度一致。

7. **证据充分性**
   
   共用逻辑验证可用于归档保留、进度恢复及去重规则，但不能替代实际平台上的自动启动、后台账号权限、凭据可用性及故障恢复证据。不同环境可复用以上行为判据；只有已确认不存在环境差异的共用部分可以合并验证，并须说明依据和覆盖边界。任何必需环境缺少证据时，交付仍未完成。
