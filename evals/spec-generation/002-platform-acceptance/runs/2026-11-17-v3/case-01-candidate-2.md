# 规格：Hub 自动归档 VibeInsight 历史与项目关联检索

已确认意图：[intent.md](intent.md)。本规格沿用 Hub 与本机端现有的 Windows、Linux、macOS 支持范围及服务运行方式。尚缺的来源连接细节、项目管理接口和重试策略列为维护者待确认项。

## 预期行为

### 来源连接配置

1. 维护者通过 Hub CLI 提供 VibeInsight PostgreSQL 来源的连接信息和凭据，验证成功后保存。必要信息须涵盖数据库地址、端口、数据库名、读取账号、密码，以及服务定位 `psql` 所需的信息；若来源要求 TLS，还须提供相应连接要求与证书信息。
   - 数据库连接值、账号及读取权限由 VibeInsight 数据库维护方提供或确认。
   - `psql` 必须能由 Hub 长期运行服务的账号定位并执行；仅 CLI 所在交互环境可执行不算配置有效。
   - 具体 CLI 命令、参数、TLS 支持要求及配置查看方式待维护者确认，确认后须使维护者能够从该入口完成配置。

2. 验证须确认长期运行服务能够读取保存后的配置和秘密文件、执行 `psql`，并对来源执行所需只读查询。验证成功后才替换当前有效配置；连接失败、凭据无效、权限不足或服务无法使用配置时，保留原有效配置，并返回可定位问题且不泄露密码的错误。

3. 保存成功后，Hub 自动开始同步。Hub 服务重启后直接使用已保存配置继续，无需维护者重新输入密码。

### 自动同步与故障恢复

1. Hub 自动发现并归档配置账号可读取的全部 VibeInsight 项目历史，不要求逐个项目启用。持续同步新增会话及已有会话追加的轮次。

2. 来源后来新增可读项目时，Hub 补齐该项目可读取的历史，包括早于其他项目当前同步进度的数据。

3. 同一来源数据被重复读取、近期事件被回查或失败批次被重试时，不产生重复会话或轮次。不同项目或来源中的同名项目、同名会话不能因此合并。

4. 来源不可用、凭据失效或 `psql` 执行失败时，已有归档继续可检索、可读取。未成功归档的数据不得被进度跳过；来源恢复后自动重试并补齐。

5. Hub 重启或同步中断后，从已提交进度继续。每个批次的归档与进度共同提交，不出现进度已推进但对应归档缺失的状态。

### 项目归属与关联管理

1. 本机端补传设备项目归属。CLI/MCP 发起项目查询时携带当前项目身份，Hub 据此确定查询范围；项目身份不得只依赖显示名称。

2. Hub 维护者统一管理项目关联，可建立、查看和解除：
   - 设备项目与 VibeInsight 项目的关联；
   - 不同设备项目之间的关联。

   管理入口的具体命令和项目标识呈现方式待确认。入口须使维护者能够区分同名项目，明确选择关联双方并确认结果。

3. 关联双向生效，查询范围只扩展一层。例如 A 关联 B、B 关联 C 时，查询 A 包含 A、B，不因 B 的关联进一步包含 C；查询 B 包含 B、A、C。同一归档被多个关联路径命中时只返回一次。

4. 解除关联后，后续项目查询停止通过该关系扩展范围；已经归档的数据保留，仍可通过其所属项目、全局查询及已有原文引用访问。

### CLI/MCP 检索与原文读取

1. 用户通过现有 CLI 和 MCP 检索设备上传历史及 VibeInsight 归档。项目查询应用当前项目身份及一层关联规则。

2. 两种入口的结果均包含足以定位原文的来源、项目、原会话及消息位置。用户可使用返回的引用精确读取对应原文；同名项目、不同来源及相同局部会话标识之间不得串读。

3. 增加来源和项目身份后，已有原文引用继续可用。旧客户端未携带项目身份的全局查询保持兼容，不被隐式收窄到某一项目。

4. Hub 不可用时，CLI/MCP 沿用现有本机全局回退行为。本机回退的具体结果范围沿用既有承诺，不据此承诺离线可读取仅保存在 Hub 的归档。

## 边界与约束

- 首版仅面向单用户，不增加多用户授权或租户隔离。
- 来源读取只执行只读查询，不修改 VibeInsight 数据。
- 首版支持新增会话事件和追加轮次；不发现没有新增事件的历史正文原地改写。
- Hub 和本机端继续支持 Windows、Linux、macOS，不因当前开发环境或 wheel 构建成功缩减支持范围。
- Hub 保持现有服务类型：Windows 系统服务使用 LocalService，Linux 使用 systemd 用户服务，macOS 使用 launchd 系统服务。
- CLI 配置账号与服务账号可能不同。配置成功的判据包含服务实际可用性，不能仅依据配置者能够连接数据库。
- 密码保存在服务状态目录的专用秘密文件中。运行账号能够读取，其他未授权普通账号不能读取；CLI 输出、日志及对话数据库均不得包含密码原值。
- 来源暂时失败和解除项目关联均不删除归档。来源项目失去读取权限后的既有归档保留策略如需区别处理，须另行确认；本次不据此引入删除行为。

## 设计决策

### 已确定设计

- 由 Hub 服务调用外部 `psql`。连接参数保存在 Hub 配置文件，密码保存在服务状态目录的专用秘密文件。
- 新配置通过验证后才替换有效配置。配置与秘密文件的替换须保持一致，失败时原有效连接仍可使用。
- 同步进度保存在 Hub 数据库，批次归档与进度一同提交；重启后继续已提交进度，并回查近期事件去重。
- 项目发现和历史补齐不能仅依赖跨项目的单一时间进度，否则后来可读项目的较早历史可能遗漏。
- 来源、项目、会话和消息位置共同承担原文定位职责；显示名称不能作为唯一身份。

### 待维护者确认

1. **来源数据契约**：VibeInsight 的项目枚举、会话与轮次读取方式、稳定标识、事件顺序和分页边界。该契约须支持完整历史读取、追加发现、去重及精确原文定位，否则相关行为无法验收。
2. **配置与管理接口**：连接配置、`psql` 定位、TLS、项目标识查看及关联管理的具体 CLI 约定，以及现有 CLI/MCP 返回结构如何兼容扩展。
3. **同步时效**：自动发现和重试的触发周期、退避规则、近期事件回查窗口及可接受完成时限。验收须采用确认后的可观察时限，不能无限等待后宣称通过。
4. **跨账号文件交接**：三种既有服务方式下，配置者如何将配置及秘密文件交付给服务账号，并设置正确访问权限。不得以改用交互账号运行 Hub 代替。
5. **外部客户端依赖**：支持的 `psql` 版本范围、安装与定位方式，以及缺失、不可执行时的错误反馈。

这些决定直接影响交付接口、同步完整性和验收判据，须在实施前确认，不能留作 PLAN 自行决定。

## 验收条件

### 1. 必需环境与证据范围

以下服务集成验收必须分别取得实际运行证据：

| 平台 | 必须使用的 Hub 运行方式 |
|---|---|
| Windows | LocalService 系统服务 |
| Linux | systemd 用户服务 |
| macOS | launchd 系统服务 |

每个平台均须覆盖下述第 2、3 项的完整结果，不能只验证服务启动。至少覆盖配置 CLI 与服务账号或环境不同的状态，证明服务不依赖配置者的交互环境。

本机端新增的项目归属补传、CLI/MCP 项目查询和本机回退，须在 Windows、Linux、macOS 实际运行并取得第 5 项所列结果；可连接共用测试 Hub，无须重复所有 Hub 服务组合。

共用同步、关联和定位逻辑可使用合成事件在一个环境完整验证第 4 项，依据是其数据契约与规则不依赖操作系统。该证据不替代三平台的服务账号、外部进程、秘密文件及本机入口证据。

### 2. 配置、秘密与服务重启

在每种规定服务环境中，分别验证：

- 从未配置状态经 Hub CLI 保存有效连接后，服务能够执行 `psql` 只读查询并归档来源数据；服务重启后无需输入密码即可继续。
- 已有有效连接时，提交错误密码、不可访问的来源或服务无法执行的 `psql` 配置，操作明确失败，原配置仍可连接并继续同步。
- 保存后的秘密文件可由服务账号读取，未授权普通账号无法读取；CLI 输出、日志和对话数据库中检索不到密码原值。
- 配置者退出或其交互环境不再存在后，服务仍能定位 `psql` 并使用已保存凭据。

### 3. 服务中的同步、故障与恢复

在每种规定服务环境中，以可查询的 PostgreSQL 测试来源验证以下连续过程，可使用合成数据：

1. 来源已有多个可读项目及历史，配置成功后全部归档。
2. 新增会话、向旧会话追加轮次，均在确认的同步时限内可检索并精确读取。
3. 后来增加一个可读项目，其历史早于当前进度，该历史仍被补齐。
4. 中断来源访问，已有归档仍可检索和读取；恢复后，失败期间新增及追加的数据自动补齐且不重复。
5. 在批次处理期间中断并重启服务，恢复后数据无遗漏、无重复，不存在已推进进度对应归档缺失的状态。
6. 返回的来源、项目、原会话和消息位置能够读取预期原文。

无需在真实生产服务器造数，但仅以替身模拟 `psql` 不能替代这些服务集成证据。

### 4. 共用行为完整性

使用可判定的合成历史与项目关系验证：

- 全部可读项目历史、分页边界、追加轮次、重复事件及近期回查均无遗漏或重复。
- A—B—C 关系符合双向、一层扩展规则；多路径命中同一归档只返回一次。
- 设备项目与 VibeInsight 项目、不同设备项目均可建立、查看和解除关联，展示足以区分同名项目。
- 解除关联后查询范围立即符合新关系，归档保留，原有引用继续可读取。
- 不同来源、同名项目和相同局部会话标识均可区分，精确引用不串读。
- 未携带项目身份的旧客户端全局查询仍返回既有范围内结果。
- 无新增事件的正文原地改写不作为本版必须发现的更新。

### 5. 三平台本机端与 CLI/MCP

在每个平台安装本次本机端发行包，分别通过 CLI 和 MCP 验证：

- 本机端补传项目归属后，项目查询携带正确身份；两个同名项目的结果保持可区分。
- 已配置一层关联时，项目查询返回当前项目及直接关联项目的数据，不包含仅经二层关系可达的数据。
- 检索结果提供完整定位信息，通过各入口读取的原文与预期来源消息一致；已有原文引用仍可用。
- Hub 不可用时进入现有本机全局回退，返回范围与既有行为一致。
- 旧客户端全局查询兼容性可在共用协议验收中取得证据，不要求每个平台重复运行相同旧客户端用例。

### 6. 交付通过判定

所有待确认决定须已解决，且上述必要证据齐备，方可判定交付通过。当前 macOS 开发环境中的 Python 测试、独立 Hub 或两个 wheel 安装结果，只能证明其实际覆盖的内容，不能证明规定服务方式或其他平台已经通过。

Windows、Linux 本次执行记录尚不存在，属于未完成的必需验收项。具体机器、实现位置、实施顺序、测试步骤、命令及 CI 配置写入 plan.md。
