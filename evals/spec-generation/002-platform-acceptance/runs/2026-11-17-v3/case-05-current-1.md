# 规格：Hub 重启后自动恢复同步

以同目录下已确认的 [intent.md](intent.md) 为依据。支持的部署范围、后台服务方式、运行账号及凭据持久化方案仍需维护者确认。

## 预期行为

1. 在已确认支持的部署环境中，完成后台运行配置后，机器重启应自动启动 Hub，同步此前已配置的数据来源，无需用户手动执行前台命令或重新输入凭据。
2. 自动启动后，Hub 应保留并使用已有来源配置、归档和同步进度，继续同步，不因重启清空数据或从头重复导入。
3. 某个来源不可达时，Hub 应保留其已有归档并使其仍可检索，同时报告该来源的同步失败，且不得将失败记录为同步成功。
4. 来源恢复可达后，Hub 应自动重试，从已有进度继续同步；重试不得重复导入已经归档的数据。
5. 后台运行所需凭据应能在机器重启后继续使用，不依赖用户重新打开交互式终端或重新设置环境变量。

## 边界与约束

- 已知运行要求仅为 Python 3.11+，不能据此推定支持的操作系统、服务类型或部署账号。
- 当前 macOS 开发环境及 README 示例路径均不足以确定部署范围。本规格不将范围限定为 macOS，也不承诺新增 Windows 或 Linux 支持。
- 自动启动与凭据持久化的适用范围，须在维护者确认部署环境后明确。
- 本次变更应保留现有归档和同步进度，不要求用户通过重新配置来源或重新导入数据完成迁移。
- 现有前台同步命令及其通过环境变量取得凭据的使用方式应保持兼容。
- 来源不可达不得导致已有归档被删除或失去检索能力。
- 自动重试须保持去重效果；具体重试间隔和策略尚待确认。

## 设计决策

以下事项须由维护者在实施前确认：

1. **部署范围**：明确本次支持的操作系统及部署形态。现有资料不足以选择平台，也没有其他平台的验证依据。
2. **后台服务与运行账号**：确定自动启动方式、服务运行账号及其权限，并明确该账号如何访问现有配置、归档和进度，避免账号变化导致数据不可见。
3. **凭据持久化**：确定凭据存储方式、访问权限，以及现有环境变量凭据进入持久化存储的配置流程。持久化后的凭据须能供选定的后台账号在重启后使用。
4. **失败报告与重试**：确定用户查看来源失败状态的入口，以及自动重试的触发方式和间隔。失败报告不得泄露凭据。

## 验收条件

1. 维护者已明确支持的部署范围、后台服务方式、运行账号、凭据持久化方案、失败报告入口及重试策略。
2. 在确认支持的环境中，完成一次后台运行配置后重启机器，Hub 能自动启动并同步已有来源，无需手动执行命令、重新输入凭据或恢复交互式终端环境。
3. 重启前已有的来源配置、归档和同步进度在重启后仍然可用；同步能继续获取新增数据，已归档数据不会因重启被重复导入。
4. 来源不可达时，其已有归档仍可检索，指定入口能显示对应来源同步失败，且不会显示为同步成功。
5. 来源恢复后，无需用户手动触发，Hub 能按确认的策略重试并继续同步；恢复过程不会重复导入已有数据。
6. 后台运行账号能够访问所需的现有数据及持久化凭据，失败报告中不包含凭据内容。
7. 现有前台同步命令仍可通过环境变量取得凭据并执行同步。
