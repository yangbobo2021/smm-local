# 规格：Hub 在 systemd 用户服务启动后自动同步对话

依据：[已确认意图](./intent.md)。

## 预期行为

1. Linux systemd 用户服务启动后，Hub 自动对已配置来源执行已有的一次同步操作，无需维护者手动运行同步命令。机器重启后，该用户服务自动启动时同样触发同步。
2. 启动同步沿用 Hub 用户状态目录中的已有来源凭据和数据库同步进度，不要求重新配置凭据，也不重置进度。
3. 启动同步成功后，新拉取的对话进入既有归档，并可通过现有检索入口检索。
4. 启动同步失败时，报告可用于定位问题的失败原因，不泄露凭据。同步失败不阻止 Hub 提供已有归档的检索服务。
5. 同步失败后再次执行同步，包括再次启动服务触发同步，仍沿用数据库进度；重复拉取或重试不得重复导入消息。

## 边界与约束

- 本次交付仅支持 Linux systemd 用户服务。Windows/macOS 上运行 Hub 不在支持或验收范围内。
- Windows、macOS、Linux 本机客户端继续通过既有 HTTPS 协议访问 Hub，客户端行为和兼容性保持不变。
- 本次仅将 Hub 已有的一次同步操作接入服务启动后的生命周期；同步算法、API、CLI/MCP、客户端程序及配置格式不变，不新增周期同步机制。
- 凭据继续由相应 Linux 服务账号从既有用户状态目录读取，不扩大读取权限。服务环境可能不同于交互式登录环境，启动同步不得依赖手动登录后才具备的环境状态。
- 未配置来源时，沿用已有一次同步操作的行为，不新增配置要求。
- 本次不承诺启动同步失败后自动重试；是否需要自动重试及其策略，仍需维护者决定。
- 当前 macOS 开发环境可验证共用逻辑，但不能据此确认 Linux systemd 服务启动或机器重启后的实际行为。现有材料没有相应执行记录。

## 设计决策

- 自动同步由 Linux systemd 用户服务启动生命周期触发，复用现有同步能力及其进度、去重语义，避免形成另一套同步流程。
- 启动同步失败与已有归档检索的可用性分离，确保来源故障或凭据读取失败时仍能检索已有数据。
- 以下事项仍需维护者确认：
  - systemd 用户服务如何在机器重启后自动启动，以及是否要求用户登录前即可运行。机器重启后的自动拉取依赖该启动条件成立。
  - 同步失败原因的报告入口及必要信息。
  - 是否需要失败后的自动重试；若需要，确定重试条件与策略。

## 验收条件

1. 在支持的 Linux 环境启动 systemd 用户服务后，无需手动执行同步命令，即可触发对已配置来源的一次同步。
2. 按维护者确认的用户服务自启动条件重启机器后，Hub 自动启动并触发同步，能够拉取来源中新增加的对话。
3. 使用已有凭据和数据库进度启动服务时，无需重新配置；同步继续使用既有进度，已有归档得到保留。
4. 启动同步成功后，新增对话可通过现有检索入口检索。
5. 来源不可达、凭据不可读或同步操作失败时，可在确认的报告入口获得失败原因，且报告不包含凭据内容；已有归档仍可通过现有入口检索。
6. 同步部分完成后失败，再次执行同步或重启服务时，不重复导入已写入的消息；重复同步同一批来源数据后，归档中不存在因此产生的重复消息。
7. 在服务账号及其服务环境下，无需交互式登录补充环境即可读取既有状态并触发同步；凭据读取权限未扩大。
8. 未配置来源时，服务启动触发同步的结果与既有一次同步操作一致。
9. 现有 HTTPS 客户端访问、API、CLI/MCP 及配置格式保持兼容。
10. Linux systemd 启动及机器重启场景须有实际执行证据后方可判定通过；仅有 macOS 共用逻辑测试结果不满足这两项验收条件。
