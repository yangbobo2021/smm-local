# 规格：Linux Hub 用户服务启动后自动同步

依据同目录下已确认的 [intent.md](intent.md) 及项目现有承诺起草。启动同步的触发时机、机器重启后的用户服务启动前提及失败报告渠道仍需维护者确认。

## 预期行为

1. Linux systemd 用户服务每次启动后，Hub 自动执行一次已有同步操作，拉取已配置来源的新对话，无需用户手动执行同步命令。机器重启后，该用户服务自动启动时同样触发同步。
2. 自动同步沿用相应 Linux 服务账号的 Hub 用户状态目录中的已有来源凭据和数据库进度，不要求重新提供凭据、重置进度或更改配置格式。适用来源为 Hub 已配置的来源；凭据和进度由现有配置与状态管理方式提供。
3. 同步成功后，新导入的对话可通过既有检索路径获取，已有归档继续可检索。
4. 启动同步失败时，Hub 报告可用于定位问题的失败原因，已有归档仍可通过既有 HTTPS 检索路径访问。失败不应导致 Hub 持续不可用。
5. 同步失败后再次执行已有同步操作，或后续服务启动再次触发同步时，沿用数据库中已有进度，不重复导入消息，包括前次失败前已写入的消息。
6. 自动同步不改变既有手动同步入口及其行为，不引入新的配置必填项。

## 边界与约束

- 本次仅适用于 Linux systemd 用户服务，将 Hub 已有的一次同步操作接入服务启动后的生命周期。
- Hub 在 Windows、macOS 上的运行方式不受支持，也不纳入本次交付或验收。
- Windows、macOS、Linux 本机客户端继续通过既有 HTTPS 协议访问 Hub；客户端程序、协议、API、CLI/MCP、同步算法及配置格式均不变。
- 凭据仅相应 Linux 服务账号可读。自动同步必须使用该账号可访问的既有状态目录，不能依赖交互式登录会话提供的临时环境。
- 本次不增加周期同步或自动失败重试策略；失败后的重试沿用既有同步操作或下一次服务启动触发。若需新增自动重试，须另行确认。
- 当前 macOS 开发环境只能提供共用逻辑验证，不能提供 Linux systemd 启动或机器重启后的实际运行证据。现有材料尚无此类证据。

## 设计决策

- 复用已有同步操作和进度管理，以保持来源处理及去重语义一致；此次新增职责限于生命周期触发与失败报告。
- 启动同步失败必须与归档检索可用性隔离。同步执行方式应满足这一结果，不得因失败使服务反复退出、无法提供检索。
- 服务环境可能缺少交互式登录环境中的路径、环境变量或其他依赖。验收必须覆盖真实服务账号、状态目录访问权限和非交互式启动环境，不能以手动运行同步成功替代。

实施前需维护者确认：

1. **同步触发时机及就绪关系**：在服务启动生命周期中的哪个节点触发，以及同步进行时检索是否必须可用。该决定影响启动完成和同步期间可用性的验收；同步失败后的既有归档可检索是已确认要求。
2. **机器重启后的自动启动前提**：现有部署是否已保证用户服务无需交互式登录即可启动；若没有，应明确本次是否包含必要部署设置及其确认方式。缺少这一条件，不能承诺机器重启后自动拉取。
3. **失败报告渠道**：明确维护者从哪个既有入口查看失败原因，以及报告应包含的来源和错误信息。该入口必须在非交互式服务环境中可用，并避免泄露凭据。

## 验收条件

以下涉及生命周期、凭据访问及失败后可用性的条件，必须在实际 Linux systemd 用户服务环境取得通过证据。缺少必要 Linux 证据时，本次交付仍未完成。

1. **用户服务启动触发同步**  
   在相应 Linux 服务账号下，已有来源配置、可读凭据及数据库进度，且来源存在尚未归档的新对话。启动用户服务后，无需手动同步即执行已有同步操作；新对话可检索，原有归档仍可检索，进度得到沿用和更新。

2. **机器重启后自动同步**  
   在维护者确认的自动启动配置下，保留已有凭据和进度，并使来源存在新对话。实际重启 Linux 机器后，无需交互式登录或手动同步，用户服务自动启动并完成同步；新旧归档均可通过既有 HTTPS 检索路径访问。仅重启服务不能替代此项证据。

3. **服务环境中的凭据与进度复用**  
   上述启动和机器重启验收均须使用真实服务账号及其已有状态目录，不额外注入仅交互式登录才具备的凭据或临时环境。同步能够读取已有凭据和进度，无需重新配置或重置数据库。

4. **启动同步失败后的报告与检索**  
   在实际 Linux 用户服务环境中，分别覆盖来源访问失败，以及服务环境无法读取必要凭据或状态目录的情况。服务启动触发同步后，通过已确认渠道获得可定位的失败原因且不泄露凭据；Hub 不因该同步失败持续不可用，已有归档可通过既有 HTTPS 路径检索。

5. **失败后重试不重复导入**  
   在实际 Linux 用户服务环境中，使一次启动同步在已写入部分消息后失败。恢复必要条件后，分别通过既有同步入口和后续服务启动重试，均能补齐待导入消息，已写入消息不重复，已有归档仍可检索。两条重试路径可使用等价的独立数据状态验证。

6. **触发时机与失败报告决定落实**  
   按维护者确认的触发节点、同步期间检索要求及失败报告渠道，在实际 Linux 用户服务环境验证对应结果。上述决定未确认或未取得对应证据时，相关验收不得判定通过。

7. **兼容性与共用逻辑验证**  
   既有手动同步行为、配置格式及 HTTPS 检索契约保持兼容。macOS 上的共用逻辑测试可验证触发调用、错误传播和既有同步逻辑回归，但不能替代上述 Linux 实际环境证据。客户端程序和协议未变，本次不要求 Windows、macOS、Linux 客户端分别重复完整测试；通过既有 HTTPS 路径验证 Linux Hub 同步结果及失败后的归档可用性即可覆盖本次相关访问契约。

具体机器、实施位置、执行步骤、命令及 CI 配置写入 plan.md。
