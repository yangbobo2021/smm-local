# 规格：Hub 重启后自动恢复同步

以同目录下已确认的 [intent.md](intent.md) 为依据。支持的操作系统、后台服务类型、部署账号及凭据持久化方案仍需维护者决定；当前 macOS 开发环境和 README 示例路径不构成部署范围的确认。

## 预期行为

1. 完成后台运行与凭据持久化配置后，机器重启，Hub 自动启动并继续同步已配置的数据来源，无需用户手动运行前台命令或重新输入凭据。
2. 重启后，Hub 保留并使用已有归档和同步进度，不因后台启动而清空归档、重置进度或要求重新配置来源。
3. 某个数据来源不可达时，Hub 保留该来源已有归档的可检索性，并报告该来源的同步失败，不将失败呈现为同步成功。
4. 来源恢复可达后，Hub 自动重试同步，依据保留的进度继续处理；重启、失败和重试均不得导致同一数据重复导入。
5. 后台运行无法取得或使用已持久化的凭据时，Hub 报告凭据相关失败，保留已有归档和进度，不等待交互式输入。

## 边界与约束

- 本变更适用于已配置数据来源的自动恢复同步，不承诺自动发现或新增数据来源。
- Python 3.11+ 是当前唯一明确的运行环境要求，不能据此推定支持任何操作系统或服务管理机制。
- 当前资料不足以确定部署平台。不得默认仅支持 macOS，也不得将 Windows 或 Linux 支持写为已确认范围。
- 后台运行不得依赖重启前交互式终端的存续或其临时环境变量。
- 保留现有前台同步命令通过环境变量取得凭据的使用方式。
- 凭据不得出现在普通日志、失败报告或可检索归档中。
- 来源不可达或凭据失败不得破坏已有归档和进度；恢复同步时不得跳过尚未成功导入的数据。
- 归档可检索性须在既有检索功能可用时保持；机器关机期间的检索可用性不在本变更范围内。

## 设计决策

以下事项仍需维护者在实施前确认：

- **部署范围与启动机制**：支持哪些操作系统、采用何种后台服务，以及由哪个账号运行。现有开发环境和验证记录不足以作出选择。
- **凭据持久化**：凭据的保存位置、访问保护、首次配置和更新方式，以及与现有环境变量的取值优先级。该决定须保证选定服务账号在重启后可取得凭据。
- **归档与进度访问**：后台服务如何定位并访问现有数据，避免因账号或工作目录变化而使用空归档或新进度。
- **失败报告与重试策略**：失败的查看入口、必要的诊断信息，以及自动重试的间隔与退避规则。报告须能区分来源不可达与凭据失败。
- **并发运行规则**：后台同步与现有前台命令同时启动时如何协调，保证归档和进度一致且不重复导入。

## 验收条件

1. 在维护者确认的部署环境中完成配置并重启机器后，无需手动启动同步或再次输入凭据，Hub 自动同步已配置来源。
2. 重启前已有的归档在重启后仍可检索；已保存的同步进度被继续使用，尚未导入的数据能够继续导入。
3. 来源不可达时，可查看明确归属于该来源的同步失败报告；其已有归档仍可检索，归档和进度不被清空或重置。
4. 来源恢复可达后，无需人工触发，Hub 按确认的策略自动重试，并导入故障期间新增且尚未导入的数据。
5. 对已经成功导入的数据经历机器重启、来源失败及多次重试后，归档中不出现由这些操作造成的重复记录。
6. 后台凭据缺失或不可用时，Hub 报告凭据失败，不等待交互式输入，不破坏已有归档和进度，报告中不暴露凭据。
7. 现有前台同步命令仍能通过环境变量取得凭据并执行同步；与后台同步并发启动时符合确认的协调规则，不损坏数据或重复导入。
8. 支持平台、服务类型、部署账号及上述待定方案均得到维护者确认；验收结论仅覆盖已确认并完成验证的部署范围。
