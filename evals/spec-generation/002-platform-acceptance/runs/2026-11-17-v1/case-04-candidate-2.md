# 规格：Hub 在 Linux 用户服务启动后自动同步

以同目录下已确认的 [intent.md](intent.md) 和现有项目承诺为依据。尚需维护者决定的服务启动条件及失败重试策略列于下文。

## 预期行为

1. Linux systemd 用户服务启动后，Hub 自动执行已有的一次同步操作，拉取已配置来源的新对话，无需用户手动执行同步命令。机器重启后，在该用户服务能够自动启动的前提下，同样触发同步。
2. 自动同步使用相应 Linux 服务账号已有的用户状态目录、来源凭据及数据库进度，不要求重新配置来源，也不从头导入已有消息。
3. 启动同步失败时，Hub 报告可诊断的失败原因，且不泄露凭据。同步失败不应使已有归档失去检索能力；客户端仍可通过既有 HTTPS 协议检索已有内容。
4. 失败后的再次同步沿用数据库中已保存的进度，不重复导入消息；部分同步成功后失败的情况同样适用。
5. 同步算法、API、CLI/MCP、客户端程序和配置格式保持现有行为与兼容性。

## 边界与约束

- 本次 Hub 交付仅支持 Linux systemd 用户服务，不新增 Windows 或 macOS Hub 运行方式。
- Windows、macOS、Linux 本机客户端继续通过既有 HTTPS 协议访问 Hub；客户端不新增自动同步职责。
- 本次仅将已有的一次同步操作接入服务启动生命周期，不扩展同步算法或来源能力。
- 服务必须以能读取现有凭据和数据库的相应 Linux 服务账号运行。不得假定交互式登录环境中的环境变量、工作目录或文件访问条件会自动存在于服务环境中。
- 当前 macOS 开发环境只能支持共用逻辑验证，不能提供 Linux systemd 用户服务启动或机器重启后的实际运行证据。现有材料中没有此类证据。

## 设计决策

- 自动同步由 Hub 服务启动生命周期触发，并复用已有同步入口及进度管理，避免形成另一套导入和去重逻辑。
- 启动同步失败应与归档检索服务的可用性隔离。失败报告的具体载体待维护者确认，但必须能在非交互式服务环境中查看并定位失败原因。
- 服务环境中的状态目录解析、服务账号权限及外部来源访问条件会影响同步是否成功，必须纳入 Linux 实际服务验收，不能仅用交互式命令运行结果替代。
- 以下事项待维护者确认，确认前不能判定完整交付：
  - 机器重启后是否要求用户未登录时即启动 Hub，以及现有用户服务是否已具备对应启动条件。该决定影响服务部署要求和重启验收状态。
  - 启动同步失败后是否自动重试，以及重试触发条件。无论采用何种策略，再次同步均须满足不重复导入的要求。
  - 同步与检索服务就绪的先后关系，以及已有同步仍在运行时再次触发的处理方式。该决定必须保证同步失败不阻断已有归档检索，且不会产生重复导入。

## 验收条件

1. 在实际 Linux systemd 用户服务环境中，使用已配置来源、已有凭据和数据库进度启动服务，能够自动导入来源中的新对话，无需手动同步；已有消息不重复。
2. 在实际 Linux 机器重启后，按维护者确认的登录状态和服务启动条件，用户服务自动启动并完成上述同步，取得可核查的执行与结果证据。仅重启 Hub 进程不能替代机器重启证据。
3. 在实际 Linux 服务账号及非交互式服务环境中，确认自动同步读取的是现有状态目录、凭据和数据库进度，不依赖仅存在于交互式登录环境的条件。
4. 在实际 Linux systemd 用户服务环境中制造启动同步失败，能够查看可诊断且不泄露凭据的原因；通过既有 HTTPS 检索入口仍能取得已有归档。
5. 覆盖同步部分成功后失败、随后再次同步的情况：已导入消息不重复，剩余消息能够继续导入。共用逻辑测试可验证进度与去重逻辑；Linux 实际服务运行还须证明生命周期接入正确复用该逻辑。
6. 对确认后的自动重试策略、同步与检索就绪关系及重叠触发处理，分别取得符合设计决定的通过证据；涉及服务生命周期的行为须在实际 Linux systemd 用户服务中验证。
7. 确认 API、CLI/MCP、客户端程序及配置格式保持兼容。此次未改动客户端和 HTTPS 协议，可用共用协议及回归验证支撑兼容性，不要求三个客户端平台重复完整测试，也不得据此声称已在三个平台实际运行通过。
8. macOS 上的共用逻辑测试或包构建不能替代上述 Linux 服务启动、失败隔离及机器重启证据。必要决定未确认或必要 Linux 证据缺失时，本次交付仍未完成。
