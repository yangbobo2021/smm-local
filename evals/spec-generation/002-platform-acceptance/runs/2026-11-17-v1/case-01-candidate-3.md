# 规格：Hub 自动同步 VibeInsight 历史与统一项目检索

意图依据：[已确认意图](intent.md)。本规格沿用 Hub 与本机端现有的平台和服务运行方式承诺；尚未确定且影响实施或验收的事项列于下文。

## 预期行为

### 来源配置与恢复

- 维护者通过 Hub CLI 提交 VibeInsight 连接参数与凭据时，必须验证连接和只读访问成功后，才保存为有效配置。
- 新配置验证失败时，CLI 返回可诊断的失败结果，原有效配置与凭据保持可用；失败配置不得替换原配置。
- 有效配置保存后，Hub 服务能够使用该配置自动同步。Hub 重启后无需再次输入密码，自动恢复来源连接与同步。
- 来源连接、凭据或读取过程失败时，Hub 保留已有归档及已提交进度，已有归档仍可通过 CLI/MCP 查询和读取。来源恢复后，自动重试未成功归档的数据。

### 历史与增量同步

- Hub 自动发现并同步 VibeInsight 当前可读取的全部项目历史，无需维护者逐项目建立关联后才同步。
- 新会话产生事件或已有会话追加轮次后，Hub 持续同步相应新增内容。
- 来源后来新增可读取项目时，即使其历史事件早于现有同步进度，Hub 仍补齐该项目的可读历史。
- 重复读取、近期事件回查、失败重试和重启恢复不得形成重复归档。
- 每批归档与对应进度共同提交。批次失败不得留下进度已推进但对应内容未归档的状态。
- 首版不主动发现没有新增事件的历史正文原地改写。

### 项目关联与查询

- Hub 维护者统一建立和解除项目关联，支持设备项目与 VibeInsight 项目关联，也支持不同设备项目之间关联。
- 关联双向生效，项目查询仅扩展到直接关联项目。例如 A—B、B—C 存在时，查询 A 包含 A 与 B，不因该关系包含 C；查询 B 包含 B、A 与 C。
- 解除关联后，项目查询不再通过该关系扩展，但不删除任何已归档内容；相关内容仍可通过其所属项目或有效原文引用访问。
- 本机端补传项目归属；CLI/MCP 的项目查询携带当前项目身份。不同设备或来源中的同名项目保持可区分，不因名称相同自动合并。
- CLI/MCP 能检索已同步内容，并返回来源、项目、原会话和消息位置，使调用方能够精确读取对应归档原文。
- 已有原文引用继续可用，不因新增来源或项目关联而指向其他内容。
- Hub 不可用时，沿用本机全局回退行为。旧客户端的全局查询保持兼容，不要求其提供项目身份。

## 边界与约束

- 首版为单用户，不引入多用户权限、租户隔离或来源内容写回。
- 对 VibeInsight 仅执行只读查询；同步范围受来源账号实际可读权限约束。
- 项目关联决定项目查询的扩展范围，不限制来源历史的自动归档范围。
- Hub 与本机端继续支持 Windows、Linux、macOS，不得以当前仅有 macOS 开发环境为依据缩减范围。
- Hub 保持既有运行方式：
  - Windows：以 LocalService 运行的系统服务。
  - Linux：systemd 用户服务。
  - macOS：launchd 系统服务。
- Hub 服务调用外部 PostgreSQL 客户端 `psql`。CLI 所在账号能够执行 `psql` 或访问配置，不代表服务账号具备相同能力。
- 连接参数保存在 Hub 配置文件；密码保存在服务状态目录的专用秘密文件。运行账号须可读取，其他未授权普通账号不得读取。CLI 输出、日志和对话数据库不得包含密码原值。
- 来源不可用时保证已归档内容可读；尚未归档的内容须在来源恢复后补齐。

## 设计决策

### 配置与服务账号

沿用“配置文件保存连接参数、专用秘密文件保存密码”的设计。验证和保存流程必须考虑 CLI 与长期运行服务账号、环境及文件访问权限不同，确保保存成功的配置实际可被既有服务使用。

新配置仅在验证成功后替换有效配置。验证失败或替换过程失败，不得破坏原有效配置与凭据的配对关系。

`psql` 的可执行文件定位不能仅依赖交互式终端环境。各平台必须在既有服务运行方式下证明能够定位并执行所需客户端。

### 同步状态与身份

同步进度存入 Hub 数据库，批次归档与进度共同提交，并在恢复时回查近期事件去重。进度设计必须同时支持已知项目增量推进与新可读项目的历史补齐，不能只依赖单一全局事件位置跳过旧历史。

项目、会话和消息身份须保留来源及设备边界，支撑同名项目区分、重复读取去重和稳定原文定位。关联查询以当前项目的直接关系计算，不递归扩展。

### 待维护者确认

- `psql` 的交付责任、支持版本及服务可见的定位方式尚未确定。这会影响三平台安装前提、配置诊断及服务启动验收。
- 自动发现、增量同步、失败重试的时间要求，以及近期事件回查范围尚未确定。需在实施前明确可判定的时限与范围，否则无法验收“持续同步”和“恢复后重试”的及时性。
- 项目关联管理的具体 CLI 接口及项目身份呈现形式尚未给出。需确认维护者如何准确选择同名项目、查看关系和解除关系。
- 来源事件的稳定身份、排序及分页边界资料尚未提供。需确认其足以支撑去重、追加轮次读取与历史补齐；若存在限制，须明确处理规则后再确认交付承诺。

## 验收条件

### 功能与一致性

1. 有效来源配置保存后，Hub 自动归档来源账号可读取的全部项目历史；无需逐项目配置关联。
2. 新会话及旧会话追加轮次均在确认的同步时限内可检索、可读取；重复读取同一批事件后，归档数量与原文定位保持稳定。
3. 新增可读项目包含早于已有进度的事件时，其历史仍被完整补齐，不影响其他项目的增量同步。
4. 在批次提交前后分别发生中断时，恢复结果均无遗漏、无重复，且进度不越过未归档内容。
5. 来源失败期间，已有归档可检索和读取；恢复后，在确认的重试时限内补齐未成功的数据。
6. 无效配置提交被拒绝，原有效配置继续可用；有效配置替换成功后，服务使用新配置。
7. 使用设备项目与来源项目、不同设备项目分别验证关联。双向查询结果符合直接关联规则，A—B—C 场景不发生递归扩展。
8. 解除关联后查询范围收缩，归档仍保留，既有有效原文引用仍可读取。
9. 同名项目保持可区分；本机补传内容具有正确项目归属。CLI 与 MCP 项目查询均使用当前项目身份。
10. CLI/MCP 检索结果包含来源、项目、原会话和消息位置，按返回位置读取的原文与归档内容一致；旧原文引用继续有效。
11. Hub 不可用时，本机全局回退与既有行为一致；不提供项目身份的旧客户端仍可执行全局查询。
12. 不把无新增事件的正文原地改写作为首版必须发现的同步内容。

### 必须取得的实际环境证据

Windows、Linux、macOS 均须取得以下证据，且 Hub 分别运行于 LocalService 系统服务、systemd 用户服务和 launchd 系统服务：

- 由维护者 CLI 验证并保存配置后，服务账号能够读取所需配置和秘密文件，实际调用外部 `psql` 完成只读来源访问与一次归档。
- 在 CLI 与服务账号或环境存在差异的条件下，配置仍可使用；服务重启后无需输入密码，能够继续同步。
- 秘密文件允许运行账号读取，并拒绝未授权普通账号读取；CLI 输出、服务日志及对话数据库中不存在密码原值。
- 无效配置不会覆盖有效配置；来源失败后已有归档可读，恢复后服务继续同步。
- 本机端在该平台完成项目归属补传、CLI/MCP 项目查询、原文读取及 Hub 不可用时的全局回退兼容验证。

上述平台覆盖聚焦服务环境、外部进程、文件权限与本机接口集成，不要求每个平台重复完整的同步算法组合。

历史补齐、去重、批次原子性、关联扩展和身份区分等共用逻辑，可在当前 macOS 环境通过合成事件完成完整组合验证，前提是覆盖生产使用的同一逻辑路径。合成事件不能替代三平台实际服务调用 `psql`、凭据访问和重启恢复的证据；来源集成可使用独立测试来源，无需在真实生产服务器造数。

当前 Windows/Linux 尚无执行记录，相关证据属于交付未完成项。Python 测试通过、独立 Hub 可运行或两个 wheel 安装成功，均不能替代这些实际环境证据。待确认事项须形成明确决定并满足对应验收条件后，方可判定整体交付通过。
