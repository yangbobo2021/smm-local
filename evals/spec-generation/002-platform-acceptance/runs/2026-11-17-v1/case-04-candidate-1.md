# 规格：Hub 在 systemd 用户服务启动后自动同步

依据同目录下已确认的 [intent.md](intent.md) 及项目现有承诺起草。尚需维护者决定的事项在下文标明。

## 预期行为

1. Linux systemd 用户服务每次启动后，Hub 自动对已配置来源执行已有的一次同步操作，无需用户手动运行同步命令。机器重启导致服务启动时，同样触发自动同步。
2. 自动同步使用相应 Linux 服务账号用户状态目录中的已有来源凭据，并从数据库中保存的同步进度继续，不要求重新配置凭据或重置进度。
3. 启动同步失败时，Hub 报告可用于定位问题的失败原因，且不泄露凭据。已有归档仍可通过既有检索入口访问。
4. 同步失败后再次执行同步，包括服务重新启动触发的同步，沿用已有进度与去重语义，不重复导入已存在的消息。

## 边界与约束

- 本次 Hub 交付范围仅为 Linux systemd 用户服务；不承诺 Windows 或 macOS 上的 Hub 运行方式。
- Windows、macOS、Linux 本机客户端继续通过既有 HTTPS 协议访问 Hub。本次不修改客户端、协议、API、CLI/MCP、配置格式或同步算法。
- 本次仅将已有的一次同步操作接入服务启动生命周期，不新增周期同步或自动重试策略。
- 服务必须在真实 systemd 用户服务环境中正确定位用户状态目录，并使用服务账号能够读取的凭据；不能依赖交互式登录环境中才存在的变量或权限。
- 当前 macOS 开发环境只能提供共用逻辑验证，不能提供 Linux systemd 服务启动或机器重启后的运行通过证据。
- 待确认：systemd 用户服务在机器重启后、用户尚未交互式登录时是否必须自动启动，以及现有部署是否已保证这一点。该决定影响用户服务生命周期配置及重启场景的验收；不能默认用户服务随机器启动。

## 设计决策

- 启动同步复用既有一次同步能力及其凭据读取、进度恢复和去重逻辑，以保持现有同步语义。
- 启动同步失败不得导致归档检索服务退出或持续不可用。同步执行方式须满足这一故障隔离要求；具体实现位置写入 plan.md。
- 待确认：启动同步失败的报告渠道及最少诊断信息。必须使维护者能够获知失败来源和原因，且不得输出凭据。
- 凭据权限、状态目录定位、服务环境和用户服务启动时机均可能与交互式运行不同，因此必须在实际 Linux systemd 用户服务中验收，不能以 macOS 共用测试或包构建替代。

## 验收条件

1. 在实际 Linux systemd 用户服务环境中，配置已有来源并启动服务后，无需手动同步，新对话被自动归档且可检索。
2. 在实际 Linux 机器重启后，按维护者确认的用户服务启动条件，取得服务自动启动及随后自动同步成功的证据。若要求登录前启动，证据必须覆盖尚未交互式登录的状态。
3. 在实际服务账号及 systemd 服务环境中，使用已有用户状态目录中的凭据和数据库进度完成同步，无需重新配置；新增消息被导入，已有消息不重复。
4. 在实际 Linux systemd 用户服务中触发启动同步失败，能够通过确认的报告渠道获知失败原因，报告不包含凭据；同步失败后，已有归档仍可通过既有 HTTPS 检索入口访问。
5. 在上述失败后恢复来源访问并重新启动服务，同步能够继续完成；包括失败前可能已写入的消息在内，归档消息不重复。
6. 共用逻辑测试可在 macOS 验证启动触发、错误处理及既有同步调用的衔接，但其结果仅覆盖共用逻辑，不代表 Linux systemd 实际运行通过。
7. 本次不修改客户端或 HTTPS 协议，无需三个客户端平台重复完整测试；通过既有 HTTPS 入口验证归档可检索，覆盖本次服务生命周期变更对调用方的影响。
8. 以上必要 Linux 运行证据缺失时，本次交付不得判定通过。当前材料尚无这些记录；待确认事项须在实施及最终验收前明确。
