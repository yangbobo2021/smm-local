# 规格：Hub 自动同步 VibeInsight 历史与项目关联检索

已确认意图见同目录 [intent.md](intent.md)。本规格沿用 Hub 与本机端现有的平台和服务运行承诺；仍需维护者决定的事项在下文列明。

## 预期行为

### 来源配置与持续同步

1. 维护者通过 Hub CLI 提交 VibeInsight 来源连接参数和凭据时，Hub 验证连接及只读查询能力。验证成功后保存配置；验证失败时返回可定位原因的错误，保留原有效配置和同步进度。
2. 配置生效后，Hub 自动归档该来源可读取的全部项目历史，并持续同步新增会话及旧会话追加的轮次，无需逐项目手动启动。
3. 来源后来新增可读项目时，Hub 自动发现并补齐其历史，即使这些历史早于其他项目已有的同步进度。
4. Hub 重启后，服务使用已保存的连接参数和凭据自动继续同步，无需维护者重新输入密码。
5. 来源连接、凭据或查询发生故障时，已有归档仍可检索和读取。来源恢复后，Hub 自动重试未成功归档的数据。
6. 同一来源事件被重复读取或在重启后回查时，不产生重复归档。只有已成功提交的归档才推进同步进度。

### 项目关联与查询

1. Hub 维护者统一管理项目关联，可建立和解除设备项目与 VibeInsight 项目之间、不同设备项目之间的关联。
2. 项目关系双向生效。以某项目发起查询时，查询范围包含该项目和与其直接关联的项目，只扩展一层。例如 A 关联 B、B 关联 C 时，从 A 查询不因这两条关系自动包含 C。
3. 解除关联后，后续项目查询不再通过该关系扩展范围，但已归档会话、消息及原文引用仍然保留。
4. 本机端上传时补传项目归属；CLI/MCP 发起项目查询时携带当前项目身份。同名项目仍可区分，不因名称相同而合并。
5. 用户通过现有 CLI/MCP 检索归档时，结果提供来源、项目、原会话和消息位置，并可据此精确读取对应原文。项目关联变化不使已有原文引用失效。
6. Hub 不可用时，客户端沿用现有本机全局回退行为。旧客户端的全局查询继续可用，不强制要求其提供项目身份。

## 边界与约束

- 首版为单用户，不引入多用户权限或租户隔离。
- 同步覆盖新增会话事件和追加轮次；不发现没有新增事件的历史正文原地改写。
- VibeInsight 仅接受只读查询，不因验证、同步或恢复操作而修改来源数据。
- Hub 与本机端继续支持 Windows、Linux、macOS，不得因当前开发环境为 macOS 而缩减交付范围。
- Hub 服务运行方式保持不变：
  - Windows：以 LocalService 运行的系统服务。
  - Linux：systemd 用户服务。
  - macOS：launchd 系统服务。
- Hub 服务调用外部 PostgreSQL 客户端 `psql`。不能以交互式终端能执行 `psql`、CLI 配置成功或 wheel 构建成功，推定长期运行服务具有相同的路径、文件权限和执行环境。
- CLI 配置账号与服务账号可能不同。保存后的凭据必须能被实际服务账号读取，其他未授权普通账号不能读取。
- 密码原值不得出现在 CLI 输出、日志或对话数据库中。

待维护者确认：

- 三个平台中 `psql` 的安装供给方式、可执行文件定位规则及不可执行时的提示契约。该决定影响部署准备和服务环境验收，不能默认服务继承配置终端的环境。
- 服务状态目录及秘密文件的创建、授权和更新方式，尤其是跨账号配置时的职责。该决定必须保证配置持久化和服务访问同时成立。
- 自动发现、持续同步及故障重试的时效标准。材料未给出时间上限，需在验收前确认可独立判定的期限。

## 设计决策

1. **配置与秘密分离保存。** 连接参数存于 Hub 配置文件，密码存于服务状态目录的专用秘密文件。权限以实际服务账号为依据；不能仅依赖配置 CLI 所属账号的默认权限。
2. **新配置验证后替换。** 验证失败不得覆盖原有效配置。配置与秘密的替换应保持一致，避免服务读取到新旧不匹配的组合。验证必须覆盖服务最终使用连接所需的条件；仅在 CLI 账号下连接成功不足以证明服务可用。
3. **归档与进度共同提交。** 同步进度保存在 Hub 数据库，每批归档与其进度在同一事务提交。失败后从已提交位置继续，并回查近期事件去重，避免遗漏或重复。
4. **发现项目不受既有进度截断。** 项目发现及历史补齐不能只依赖来源的单一最新时间位置，必须能够覆盖后来变为可读的旧项目。
5. **项目身份与原文定位保持稳定。** 项目关联用于扩展查询范围，不改变归档的来源身份或原文定位。项目名称不作为唯一身份，关联解除不删除归档。
6. **验收区分共用语义与环境风险。** 项目扩展、去重、进度提交等共用逻辑可集中验证；`psql` 调用、服务身份、秘密文件权限及重启恢复受平台和运行方式影响，必须取得各平台实际服务运行证据。

## 验收条件

1. **配置替换与保密**
   - 有效配置可通过 CLI 验证并保存；无效连接或凭据验证失败后，原配置仍能同步。
   - 保存配置后，实际 Hub 服务账号可读取并使用秘密文件；另一个未授权普通账号不能读取密码。
   - CLI 输出、相关日志及对话数据库中均无密码原值。

2. **完整同步与增量同步**
   - 多个可读项目的既有历史全部归档，新增会话和旧会话追加轮次均在确认的时效内出现。
   - 来源新增一个历史早于当前进度的可读项目后，其历史仍被完整补齐。
   - 重复提供同一事件及近期事件回查后，归档无重复。

3. **故障与恢复**
   - 来源不可用期间，已有归档仍可检索并读取原文。
   - 在批次提交前发生失败时，归档和进度不出现部分提交；恢复后补齐未成功数据。
   - 已提交后重启，服务无需重新输入密码即可继续同步，最终无遗漏或重复。

4. **项目关联**
   - 设备项目与来源项目、不同设备项目均可建立双向关联。
   - A—B—C 的关系中，从 A 查询包含 A、B，不因传递关系包含 C；从 B 查询可包含其直接关联的 A、C。
   - 解除关系后，查询范围相应变化，归档及已有原文引用仍可用。
   - 同名项目的数据和查询范围保持可区分。

5. **CLI/MCP 与兼容性**
   - CLI 和 MCP 的项目查询均携带当前项目身份并遵守一层关联范围。
   - 两个入口返回的来源、项目、原会话及消息位置均能精确定位并读取对应原文。
   - 本机端上传的项目归属可被 Hub 正确识别。
   - 旧客户端全局查询继续成功；Hub 不可用时，本机全局回退行为保持兼容。

6. **实际平台与运行环境覆盖**
   - Windows LocalService 系统服务、Linux systemd 用户服务、macOS launchd 系统服务，均须取得以下通过证据：服务能定位并执行 `psql`、使用 CLI 保存的凭据完成真实只读来源查询和归档、落实秘密文件访问限制、重启后自动继续，以及来源故障恢复后继续同步。
   - 跨账号配置须覆盖 CLI 配置账号与服务账号不同的情形；各平台均须证明服务可用不依赖配置终端的临时环境。
   - Windows、Linux、macOS 本机端均须取得项目归属上传、CLI/MCP 项目查询与原文读取、旧客户端全局查询和 Hub 不可用时回退的实际运行证据。

7. **共用验证的适用边界**
   - 全量补齐、追加同步、重复事件、事务中断、项目关系和稳定引用等共用语义，可在一个环境使用合成事件集中验证；依据是这些判定针对共用数据处理规则，不依赖操作系统服务身份或外部进程环境。
   - 合成事件可作为后续默认回归，无需在真实来源服务器造数；但不能替代各平台真实服务调用 `psql`、凭据权限及来源查询的证据。
   - 当前 macOS 的 Python 测试、独立 Hub 或两个 wheel 安装结果只能证明对应覆盖内容，不能代表 Windows/Linux 已实际运行通过。上述必需平台证据缺失或待确认决定尚未落实时，本次交付不能判定通过。

具体机器、实现位置、实施顺序、测试步骤、命令及 CI 配置写入 `plan.md`。
