# 规格：Hub 启动后自动同步已配置来源

依据：[已确认意图](intent.md)。

## 预期行为

1. 在 Linux systemd 用户服务启动后，Hub 自动执行已有的一次同步操作，拉取已配置来源中的新对话，无需用户手动执行同步命令。机器重启后该用户服务启动时，同样执行此行为。
2. 启动同步沿用 Hub 用户状态目录中已有的来源凭据和数据库同步进度，不要求重新配置凭据，也不重置同步进度。
3. 启动同步成功后，新导入的对话可通过既有检索能力访问。
4. 启动同步失败时，报告可用于定位问题的失败原因；Hub 已有归档仍可通过既有入口检索，检索能力不以本次同步成功为前提。
5. 同步失败后再次执行已有同步操作，或再次启动服务触发同步时，继续沿用已有数据库进度，不重复导入已经归档的消息。

## 边界与约束

- 本次交付仅适用于 Linux systemd 用户服务，不包含 Windows 或 macOS 上的 Hub 运行支持。
- Windows、macOS 和 Linux 本机客户端继续通过既有 HTTPS 协议访问 Hub，客户端行为不变。
- 变更仅将已有的一次同步操作接入服务启动后的生命周期；不改变同步算法、API、CLI/MCP、客户端程序及配置格式，不引入持续轮询或新的自动重试机制。
- 服务必须在实际 systemd 服务环境中使用对应 Linux 服务账号可读的现有凭据，不得以交互式登录环境必然存在为前提，也不得扩大凭据读取权限。
- 失败报告不得泄露来源凭据。
- 没有已配置来源时，不要求用户补充配置即可保持已有归档可检索；空来源同步的结果沿用已有一次同步操作的语义。

## 设计决策

- 启动同步复用已有一次同步操作，使启动触发与既有手动触发保持相同的同步及去重语义。
- 启动同步失败不得使已有归档失去检索能力。
- 以下事项仍需维护者确认：
  - 失败原因的具体报告入口，以及是否需要除 systemd 服务日志以外的提示。
  - 用户服务是否已具备机器重启后、无需交互式登录即可启动的配置；若尚未具备，需明确本次交付是否包含相应配置及其管理责任。

## 验收条件

1. 在 Linux 实际 systemd 用户服务环境中，来源存在尚未归档的新对话时，启动服务后无需执行手动同步命令，新对话即可被检索。
2. 在机器重启后，用户服务按已确认的启动配置自动启动并触发同步，新对话可被检索，无需手动同步。
3. 启动同步使用已有来源凭据及数据库进度完成同步，无需重新配置，不重置进度；已归档消息不被重复导入。
4. 服务环境与交互式登录环境不同时，只要现有凭据对相应服务账号可读，启动同步仍能使用这些凭据，且未扩大凭据读取权限。
5. 启动同步失败时，已确认的报告入口可查看失败原因，报告不包含凭据；已有归档仍可通过既有入口检索。
6. 同步失败后再次执行同步，以及再次启动服务触发同步，均不会重复导入此前已经归档的消息。
7. 未配置来源时，服务保持已有归档可检索，空来源同步结果与已有一次同步操作一致。
8. 既有 API、CLI/MCP、配置格式，以及三个平台客户端通过 HTTPS 访问 Hub 的行为保持兼容。
9. Linux 服务启动和机器重启两项验收须有实际 Linux systemd 环境的执行证据。当前材料未提供此类记录，不能据此判定通过；macOS 上的共用逻辑测试不能替代这两项验收。
