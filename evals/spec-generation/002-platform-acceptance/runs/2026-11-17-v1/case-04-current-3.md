# 规格：Linux Hub 服务启动后自动同步对话

以同目录下已确认的 [intent.md](intent.md) 为依据。启动同步与服务就绪的先后关系、失败后的自动重试策略仍需维护者决定，详见「设计决策」。

## 预期行为

1. 已配置来源的 Linux Hub systemd 用户服务每次启动后，自动执行 Hub 已有的一次同步操作，无需用户手动运行同步命令。机器重启后该用户服务启动时，同样触发此行为。
2. 启动同步沿用 Hub 用户状态目录中已有的来源凭据和数据库同步进度，不要求重新登录、重新配置来源或重置进度。
3. 启动同步成功时，按已有同步行为归档来源中的新对话，归档结果可通过现有检索入口访问。
4. 启动同步失败时，报告可定位的失败原因；失败不得阻断已有归档的检索。
5. 失败后再次同步时，继续遵循已有同步进度和去重行为，不重复导入已归档的消息。服务再次启动触发同步时也适用此要求。
6. 未配置来源时，不要求用户为启动服务补充来源配置；维持已有一次同步操作对该状态的处理行为。

## 边界与约束

- 本次交付仅适用于 Linux systemd 用户服务，不包含 Windows 或 macOS 上的 Hub 运行支持。
- 本次仅将已有一次同步操作接入服务启动后的生命周期，不改变同步算法、API、CLI/MCP、客户端程序及配置格式。
- Windows、macOS、Linux 本机客户端继续通过既有 HTTPS 协议访问 Hub，无需因本次变更调整使用方式。
- 服务应在对应 Linux 服务账号的权限范围内读取已有凭据，不扩大凭据读取权限。
- 服务环境可能不同于交互式登录环境。读取已有凭据和数据库进度不得依赖仅在交互式登录环境中成立的状态；读取失败时应报告原因，并保持已有归档可检索。
- 本次不新增周期同步要求，也不改变机器重启后 systemd 用户服务是否会被启动的现有配置规则。
- 当前 macOS 开发环境只能验证共用逻辑，不能据此认定 Linux systemd 服务启动或重启行为已通过验收。目前缺少相应 Linux 执行记录。

## 设计决策

以下事项需维护者在实施前确认：

1. **同步与服务就绪的关系**：服务是否在同步完成前提供检索。无论采用何种顺序，同步失败均不得使已有归档持续不可检索。
2. **失败后的自动重试策略**：是否在同一次服务运行期间自动重试；若需要，应明确触发条件、间隔及停止条件。无论是否自动重试，再次同步均不得重复导入消息。
3. **失败报告入口**：明确启动同步失败原因的可查看位置，使服务环境下的凭据、状态访问或同步错误能够被维护者定位，同时不得泄露凭据。

## 验收条件

1. 已配置来源存在新对话时，Linux systemd 用户服务启动后，无需运行手动同步命令即可归档新对话，并通过现有检索入口查到。
2. 机器重启且该用户服务启动后，同样自动同步新对话；应有对应 Linux 环境的执行证据。
3. 服务启动同步使用已有来源凭据及数据库进度，无需重新登录、修改配置或重置进度。
4. 在服务环境不同于交互式登录环境的情况下，已有凭据和数据库状态仍能按约定读取；无法读取时，能在确认的报告入口查看失败原因。
5. 启动同步失败后，已有归档仍可通过现有入口检索，失败报告不包含凭据内容。
6. 同步失败后再次执行同步，以及服务再次启动后执行同步，均不会重复导入已归档消息。
7. 未配置来源时，服务保持可用，对该状态的处理与已有一次同步操作一致。
8. 既有 API、CLI/MCP、配置格式及三类本机客户端的 HTTPS 访问行为保持兼容。
9. 服务就绪时序和自动重试行为符合维护者确认后的设计决策。仅有 macOS 共用逻辑验证不能视为 Linux 服务生命周期验收通过。
