# 规格：Hub 在 Linux 用户服务启动后自动同步

意图依据：[intent.md](./intent.md)。

## 预期行为

1. 已配置来源的 Hub Linux systemd 用户服务启动后，自动执行已有的一次同步操作，无需维护者手动运行同步命令。机器重启后，该用户服务启动时也应触发同步。
2. 启动同步沿用 Hub 用户状态目录中的已有来源凭据与数据库进度，不要求重新配置凭据，不重置同步进度。
3. 同步成功后，新对话进入已有归档，并可通过既有检索能力访问。
4. 启动同步失败时，报告可用于定位问题的失败原因；Hub 仍提供已有归档的检索能力。
5. 失败后的重试或后续服务启动再次同步时，不重复导入已归档消息。

## 边界与约束

- 本次 Hub 交付范围仅为 Linux systemd 用户服务，不支持或新增 Windows、macOS 上的 Hub 运行方式。
- Windows、macOS、Linux 本机客户端继续通过既有 HTTPS 协议访问 Hub；客户端程序与协议不变。
- 本次仅将已有一次同步操作接入服务启动后的生命周期。同步算法、API、CLI/MCP、配置格式及既有手动同步行为保持兼容。
- 凭据仍由相应 Linux 服务账号从 Hub 用户状态目录读取，不依赖交互式登录环境提供额外凭据或环境变量。
- 同步失败不得导致已有归档不可检索，也不得通过重置进度或清空归档实现恢复。
- 当前 macOS 开发环境可验证共用逻辑，但不能提供 Linux systemd 用户服务实际启动、机器重启及账号权限行为的通过证据。

## 设计决策

- 自动同步复用既有同步入口及进度机制，避免引入另一套同步算法或状态。
- 同步失败与归档检索服务可用性分离；启动同步不得成为持续提供已有归档检索的成功前提。
- Linux 服务账号、状态目录访问权限及服务环境差异属于本次验收范围，不能以交互式登录后手动同步成功代替。

以下事项仍需维护者确认：

1. **开机启动条件**：是否要求用户未交互登录时，systemd 用户服务也能在机器重启后启动；如要求，需明确相应用户服务管理前提及部署责任。该决定影响重启场景的交付与验收。
2. **重试策略**：是否自动重试，以及触发条件和次数。本规格要求任何实际发生的重试均不重复导入消息，但不据此新增自动重试机制。
3. **失败报告位置**：明确维护者可观察的失败报告渠道。报告应包含失败原因且不泄露凭据，该渠道须在验收前确定。

## 验收条件

1. 在实际 Linux systemd 用户服务环境中，使用已有来源配置启动服务，无需手动同步即可导入来源中的新增对话，并通过既有检索能力查到结果。
2. 在维护者确认的开机启动条件下，实际重启 Linux 机器，服务自动启动并完成新增对话同步，全程无需手动运行同步命令。仅重启服务不能替代此项证据。
3. 在实际服务账号及服务环境中，同步能够读取已有状态目录中的凭据，并沿用数据库进度；无需交互式登录环境补充配置，已有消息不重复导入。
4. 在实际 Linux systemd 用户服务环境中，覆盖来源访问失败和凭据不可读取的情形：确定的报告渠道能观察到相应失败原因且不泄露凭据，已有归档仍可通过既有 HTTPS 访问路径检索。
5. 在失败后恢复来源或凭据访问并再次同步，以及已有成功同步后再次启动服务，两种情况下新增消息均可归档，已归档消息均不重复导入。
6. 共用逻辑测试可用于验证启动触发、错误处理及既有同步入口的复用行为；其通过不能替代上述 Linux 服务环境证据。
7. 本次未修改客户端及 HTTPS 协议，无需在 Windows、macOS、Linux 客户端重复完整回归；通过既有 HTTPS 路径验证归档可检索，覆盖本次对外行为边界，不宣称各平台客户端已实际运行通过。
8. 当前没有 Linux 服务启动或机器重启后的执行记录，上述必需运行证据仍为未完成项；取得证据前不能判定交付通过。
