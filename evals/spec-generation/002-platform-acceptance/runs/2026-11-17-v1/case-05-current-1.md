# 规格：Hub 重启后自动恢复同步

依据同目录下已确认的 [intent.md](intent.md)。操作系统支持范围、后台服务类型、部署账号及凭据持久化方案仍需维护者决定；本草稿不将当前开发电脑的 macOS 环境视为部署范围。

## 预期行为

1. 对于已配置且已完成后台运行设置的数据来源，机器重启后，Hub 自动继续同步，无需用户手动执行原前台同步命令或重新输入凭据。
2. 自动恢复同步时，Hub 保留并使用已有归档和同步进度，继续处理尚未导入的数据，不因重启清空归档、重置进度或重复导入已归档的数据。
3. 某个来源不可达时，Hub 保留该来源已有归档及同步进度，已有归档仍可检索，并向用户报告该来源同步失败。
4. 来源恢复可达后，Hub 自动重试并继续同步，无需用户重新配置来源或凭据；重试不得重复导入已归档的数据。

## 边界与约束

- 本变更覆盖已配置来源的重启恢复、后台同步、凭据持久化、失败报告与恢复重试，不要求用户重新配置已有来源。
- 仓库仅声明 Python 3.11+。现有资料不足以确定操作系统、服务类型或部署账号；README 示例路径及当前 macOS 开发环境均不能作为支持范围的依据。
- 维护者尚未授权仅支持 macOS，也未确认新增 Windows/Linux 支持。平台范围确认前，不承诺任一平台已具备后台启动或凭据持久化能力。
- 原命令通过环境变量取得凭据。新增持久化能力须保留原前台命令通过环境变量取得凭据的行为。
- 来源不可达、机器重启及恢复重试均不得破坏已有归档和进度，也不得使已有归档失去检索能力。
- 当前仅有交互式终端运行原前台命令的经历，不能据此认定后台服务环境已验证。

## 设计决策

以下事项需维护者在实施前确认：

1. **部署范围与运行身份**：明确本次支持的操作系统、后台服务类型和部署账号，以及是否要求无需用户登录即可启动。这些决定影响启动时机、文件访问权限和凭据可用性。
2. **凭据持久化与迁移**：明确存储机制、访问权限，以及现有环境变量凭据如何完成一次性持久化设置。所选方案须让确认的后台运行账号在重启后无需交互即可取得凭据，并防止凭据出现在失败报告中。
3. **失败报告方式**：明确报告入口及至少应包含的来源标识、失败状态和失败原因，使用户能够识别同步失败。
4. **自动重试策略**：明确重试触发条件、间隔及退避规则。策略须满足来源恢复后能够自动继续同步，并避免持续不可达时无间隔重试。

## 验收条件

1. 支持平台、服务类型、部署账号和是否依赖用户登录均已确认；验收结论仅适用于确认的部署范围。
2. 在确认的部署环境中，已配置来源完成一次性后台运行及凭据持久化设置后，机器重启可自动恢复同步，无需手动执行前台命令或重新输入凭据。
3. 重启前已有的归档在重启后仍可检索；同步继续使用已保存的进度，不清空归档或重新导入已归档的数据。
4. 来源不可达时，其已有归档仍可检索，归档及进度保持完整；用户可通过确认的报告入口识别失败来源和失败原因，报告不暴露凭据。
5. 来源恢复可达后，Hub 按确认的策略自动重试并导入尚未归档的数据，无需重新配置来源或凭据。
6. 经历重启、来源不可达及恢复重试后，同一来源中已归档的数据不因上述过程产生重复导入。
7. 原前台同步命令仍可通过环境变量取得凭据并执行同步。
