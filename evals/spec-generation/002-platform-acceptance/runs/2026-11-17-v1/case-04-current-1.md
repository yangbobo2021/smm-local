# 规格：Linux Hub 服务启动时自动同步对话

依据：[已确认意图](./intent.md)。

## 预期行为

1. Linux systemd 用户服务启动 Hub 后，自动触发已有的一次同步操作，拉取已配置来源的新对话，无需用户手动执行同步命令。机器重启后，若该用户服务自动启动，同样触发同步。
2. 启动同步沿用 Hub 用户状态目录中的已有来源凭据和数据库同步进度，不要求重新配置凭据，也不重置进度。
3. 服务环境与交互式登录环境不同时，启动同步仍使用相应 Linux 服务账号可读取的已有凭据和状态，不依赖交互式登录环境才能找到这些数据。
4. 启动同步失败时，报告可供定位问题的失败原因；同步失败不阻止 Hub 提供已有归档的检索能力。
5. 失败后重试同步时，沿用已有同步进度及去重行为，不重复导入已归档消息，包括失败前已成功写入的消息。

## 边界与约束

- 本次交付仅覆盖 Linux systemd 用户服务，不包含 Windows 或 macOS 上的 Hub 运行方式。
- Windows、macOS、Linux 本机客户端继续通过既有 HTTPS 协议访问 Hub，其使用方式保持兼容。
- 本次仅将已有的一次同步操作接入服务启动后的生命周期，不改变同步算法、API、CLI/MCP、客户端程序或配置格式。
- 凭据继续保存在 Hub 用户状态目录，并保持仅相应 Linux 服务账号可读取的权限边界。失败报告不得泄露凭据。
- 本次不引入持续轮询或周期同步要求。
- 当前 macOS 开发环境可验证共用逻辑，但不能据此判定 Linux systemd 服务启动或机器重启场景通过。现有材料未提供这些场景的执行记录。

## 设计决策

以下事项仍需维护者确认：

- **机器重启后的服务启动保障**：是否将 systemd 用户服务在未交互式登录时自动启动所需的部署配置纳入交付。该决定影响“机器重启后自动同步”的成立条件。
- **启动同步的触发时点**：在服务启动生命周期中的具体触发时点，以及同步进行期间检索服务的可用性要求。无论选择何种方式，同步失败后已有归档必须仍可检索。
- **失败报告入口**：失败原因通过何种既有运维入口呈现，以及应包含哪些来源标识和错误信息。
- **重试策略**：是否自动重试及其触发规则。无论采用何种策略，重复执行同步都不得重复导入消息。

## 验收条件

1. 在已配置来源存在新对话的情况下，启动 Linux systemd 用户服务后，无需手动同步即可检索到新增归档。
2. 机器重启后，在维护者确认的服务自动启动条件下，无需手动启动同步即可归档来源中的新对话。
3. 已有凭据和数据库进度存在时，启动同步无需重新配置凭据，且不重置已有进度或丢失归档。
4. 服务环境与交互式登录环境不同时，服务仍能读取其账号有权访问的既有凭据和状态，并完成同步。
5. 启动同步失败时，已确认的报告入口包含可定位失败的原因，且不暴露凭据；既有客户端仍能通过 HTTPS 检索已有归档。
6. 对同步失败后重试及部分消息已写入后重试的情况，每条消息均只保留一份归档；重试成功后可检索到尚未导入的消息。
7. 既有 API、CLI/MCP、客户端使用方式及配置格式保持兼容，同步仍采用已有算法。
8. Linux systemd 服务启动及机器重启场景须取得对应环境的执行证据后方可判定通过；仅有 macOS 共用逻辑测试结果不足以满足这两项验收。
