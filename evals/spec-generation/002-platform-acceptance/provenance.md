# 来源与提取边界

## 真实事件

PR #21 新增 Hub 同步 VibeInsight 对话与关联项目检索。规格覆盖自动同步、凭据持久化、
重启续跑、关联、引用读取、回退和重试，但没有约定这些行为需要在哪些操作系统验收。
实现的已公开执行证据来自 macOS；Windows 专用检查跳过，Linux 没有运行验收记录。
这些是历史观察，不是本评测执行结果，也不构成 Windows/Linux 已发生功能失败的证据。

## 本次确认的 SPEC 职责

维护者于 2026-11-17 在本次对话中提出：

> 在哪些平台验收，不应该是 SPEC 中约定的信息吗？

维护者进一步说明，应根据 SPEC 约定的需求与设计评估跨系统交付风险，判断当前电脑验证是否足够，
还是必须有其他操作系统的通过证据。本评测据此检查 SPEC 中的交付范围和验收要求；
具体机器、操作步骤、命令、执行顺序及 CI 配置仍由 PLAN 落实。

## 样本构造与已知失败

Case 01 从上述事件提取需求和设计，把现有三平台支持及运行方式写成生成者可见的明确前提。
`psql` 选型来自实施方案；在评测中作为要求纳入规格的既定设计输入，不声称它已写在原 SPEC 中。
移除了历史运行结果、原 SPEC 和后来维护者追问，避免生成者直接复述复盘结论。
核心风险不依赖 VibeInsight 名称，涉及服务账号、外部进程、秘密文件及进度跨重启保存。

已知不充分输出包括：七项功能条件完整但未约定验收平台；只列“跨平台兼容”；
把所有平台判断留给 PLAN；以当前机器通过、pure Python/wheel 标记或将其他平台列为未验证，
直接宣布本次三平台交付已满足。

Case 02–05 不是项目现状声明。它们分别改变变更风险、部署范围和已知信息，检验生成者能否据材料
作不同判断。低风险变更不应被强制要求所有操作系统重跑完整套测试；资料不足时应标明待确认，
不能从当前机器或既有包名称猜测支持范围。Case 06 逐字保留旧输入，检查既有规格质量是否退化。

评分规则评价可观察承诺及其依据，不以某个操作系统、CI 工具、固定矩阵样式或文件名作为通用答案。
