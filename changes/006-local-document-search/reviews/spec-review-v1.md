## R1 — P1：重叠来源处于不同采集版本时，项目命中与移除后的正文没有唯一答案

**原文依据**：B3（35–37 行）允许各来源分别绑定项目，并按规范路径合并为同一文件，且“移除或失败一个来源不使其他成功来源的同一文件消失”。B4（43–47 行）规定仅保存最近成功采集快照、不读历史版本、旧引用不能复活，并禁止较早请求覆盖同文件较新已发布版本。B5（51 行）又要求来源元信息和原文引用与所选文件对应。

**无法判定的例子**：来源 A 绑定项目 P，先成功采到文件 v1；来源 B 绑定 Q，随后成功采到相同路径 v2，A 未刷新。此时查 P 应命中 v1、v2，还是暂不命中？再移除 B 或使 B 刷新失败，A 仍是成功来源：应保留 v2、恢复 v1，还是需要刷新 A？三种实现都能援引现有某一条，但它们的原文、采集时间、项目范围和旧引用结果不同。不同来源看到缺失/失败而另一来源仍成功时也有同样问题。

**建议**：明确“版本是文件级还是来源级”“有效来源绑定如何赋予当前版本项目范围”“哪一次成功采集的时间/来源作为正文出处”“来源退出后是否可能回退旧正文”。可以选择一个文件级当前快照加明确来源资格规则，也可以选择来源采集关系；不必在规格规定表结构。不能靠数据库写入顺序或 PLAN 中的实现临时选定。

**通过条件**：在 B3/B4 和 A3/A4/A6 补入上述 A/P/v1、B/Q/v2 时间线，分别写清 P、Q、all 查询返回的版本/来源、A/B 旧引用结果，以及 B 移除、B 失败、A 后续刷新各自的结果。重叠来源去重、单一可读版本与不复活旧引用同时成立。

## R2 — P1：单文件失败与来源累计字节超限的优先关系不明确

**原文依据**：B2（31 行）同时规定“每来源一次最多1000个受支持候选文件及16MiB支持文件累计原始字节”“单文件过大……分别报告失败”“其余……单文件失败不妨碍成功文件索引，来源状态为partial”，而“来源总量超限”又要求整轮失败、旧材料不可读。

**无法判定的例子**：一个 1 字节有效 `.txt` 加一个 17MiB `.txt`。后者既是超过 2MiB 的单文件失败，又使“支持文件累计原始字节”超过 16MiB；究竟允许小文件索引并为 partial，还是整个来源 failed？1000 个候选是否包含超大、不可读、错误编码文件，也尚未明确。若依赖扫描顺序，结果可能跨平台不同。

**建议**：明确两个来源预算的计数集合、计算阶段与优先级；例如字节预算只累计通过单文件大小门槛的候选，或所有支持扩展名的候选都计入并明确整轮超限优先。不可读取/无法取大小的候选和排除/非支持格式也写出是否计数。保留实际失败原因，不把达到哪个门槛交给遍历顺序决定。

**通过条件**：A2 包含混合有效/超大/不可读/编码失败候选，以及候选数与累计字节恰好等于、超过上限的独立预期；给定相同文件集合，枚举顺序变化不改变来源级通过/失败及可检索集合。

## R3 — P2：实际平台矩阵漏写 CLI 检索/读取，并把未受影响 Hub 安装混入 Local 必验前提

**原文依据**：B1/B5/B6 新增 CLI 文档检索与引用读取。A8（94 行）实际运行清单只点明“CLI添加/查看/刷新”，检索/读取归在 Web 与 MCP；其前提却要求三平台“已安装独立Local/Hub包”。B2/B6 的路径、Unicode 和引用经 CLI 参数传递也有平台差异。B73/81 已明确 Hub 没有 006 文档入口、无需重跑 Hub 服务矩阵。模板要求逐一核对新增入口，也不把未受影响组件纳入必验范围。

**建议**：E1 明确每个平台至少实际执行一次 CLI `documents search`，将其返回的引用原样传给 `documents read`，核对 Unicode 文本/坐标与拒绝旧引用；不要求每个平台每入口重复所有故障组合。三平台实际端到端的安装前提写成独立 Local wheel；Hub 独立构建/导入或受影响共用代码回归保留在 A7，真实 Hub 仅用于确实需要连接它的兼容判据，不作为所有 Local 新入口的无条件前提。

**通过条件**：SPEC 给出的各平台入口清单明确覆盖 CLI、Web、真实 stdio MCP 各自新查询/读取路径；Local 核心能力可在无 Hub 安装/配置时完成。Hub 包构建和共用行为兼容仍有明确验证归属。

## R4 — P2：位置契约应补充码点和换行处的行号端点规则

**原文依据**：B5/B6（55、59–61 行）规定 Unicode 字符、字符区间左闭右开、行号从 1 开始，并要求 emoji/末尾换行不得错位，但没有明示“Unicode 字符”是码点、UTF-16 code unit 还是用户感知字素；也没有定义返回行号区间在 `end` 恰落于换行后时的归属。

**影响**：CLI/Python 与 Web/JavaScript 可能对非 BMP emoji 产生不同偏移；文本 `a\nb\n` 的 `[0,2)` 究竟显示第 1 行还是 1–2 行，两个实现都能说自己“按实际字符及行号区间”返回。正文准确仍不足以独立判断位置正确。

**建议及通过条件**：明确规范化文本上的 Unicode 码点索引（如采用其他单位则明确），行号区间的闭合规则及换行归属；A5 用独立预期覆盖非 BMP emoji、组合字符、LF 终止片段、无末尾换行与末尾换行。无需引入字素分割依赖。
