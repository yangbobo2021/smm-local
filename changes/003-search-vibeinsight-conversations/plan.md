依据 [PR #19](https://github.com/yangbobo2021/smm-local/pull/19) 合并的[规格](spec.md)。

## 实施顺序

1. **先建立基线和测试夹具。** 固定一个合并规格时的 Hub 和客户端版本。用该版本生成一份已有设备、对话、原文引用和上传进度的汇总档案副本。准备两套隔离客户端和贴近 VibeInsight 事件字段的合成数据，能控制项目何时可见、事件何时追加以及哪一批失败。为各项目准备共同关键词和各自唯一的文本。
2. **扩展汇总存储和兼容协议。** 在副本上验证可重复执行的数据库迁移。设备项目以设备和稳定的本地项目标识识别，VibeInsight 项目以来源和上游项目标识识别。用独立的归属关系保存同一段去重会话在不同设备上的项目归属。保留已有会话与消息标识，以及旧客户端上传和全局搜索所需的协议字段。通过 Hub 能力标记让新客户端判断何时可以发送项目元数据和项目范围。
3. **补齐设备归属并接通关联检索。** 给项目元数据和会话归属使用独立的补传进度，覆盖升级前已上传的对话，以及没有新增消息的项目改名。增加 Hub CLI 的项目列表、关联查询、建立和解除操作。将双向关联存为一条关系。Hub 先按当前项目及直接关联过滤候选，再做查询排序和结果截取。CLI 和 MCP 用返回的汇总会话与消息引用读取原文。沿用当前的断线回退行为。
4. **接通 VibeInsight 配置和首次拉取。** 复用 Living KB 对 `fact_events` 的只读查询口径。运行时连接使用 `psql`，复用既有查询口径并保持两个 Python 包的依赖独立。把连接、查询执行和结果解析集中在读取上游的代码里，便于独立验证或替换。配置来源时验证服务账号可连接并读取源数据，再发布新配置和受限凭据文件。验证失败时保留上一次有效配置。启用后自动发现连接可读取的项目，按有界批次拉取历史，并保存项目归属和来源位置。
5. **实现增量续跑并接入 Hub 生命周期。** 每轮固定上游位置上界。用 `created_at + id` 比较位置，在上次成功位置附近回查近期事件。按新事件识别新会话和已有会话新增的轮次，按来源身份去重并维持原有归档标识。将同一批的对话、索引和对应进度一起提交，恢复时重试未提交的批次。为新发现的项目安排独立的历史补拉，避免被已有来源进度跳过。绑定 Hub 启停，保存最近成功时间和脱敏后的错误，通过测试确认同步失败期间已有对话仍可检索。
6. **验证常规回归和发行包入口。** 用可控来源逐项执行验收，检查两个 wheel 的独立安装及启动。初次接通上游时单独验证 PostgreSQL 查询。更新使用指南，记录验证结果。

## 验证方法与通过条件

常规 `pytest` 和未来默认 CI 用固定夹具替换 VibeInsight 的读取端。Hub 启动、状态和凭据落盘、SQLite 归档与进度提交、CLI/MCP 检索及读取使用实际实现。测试用新进程和同一状态目录验证重启，用可控事件批次和故障验证恢复。默认回归所需的服务和数据都由测试在本机创建。

| SPEC 验收项 | 怎么验证 | 通过条件 |
| --- | --- | --- |
| 1. 自动拉取全部可读取项目 | 在来源夹具里准备三个项目的历史，配置为起初仅返回两个项目。从 Hub 管理 CLI 配置并启用，等两个项目同步后，再让夹具返回第三个项目。第三个项目的测试事件全部早于已保存的位置。用各项目的唯一文本搜索并读取命中原文，同时核对配置显示、状态输出和日志。 | 开始时两个项目的历史都可查，新可见项目不经单独配置即自动补齐较早历史。测试密码原值未出现在输出、日志或对话数据库中。 |
| 2. 凭据持久与旧会话续写 | 导入三轮后记录汇总会话标识、消息顺序及同步位置，停止 Hub 进程。停机期间追加两轮并写入一段新会话。使用同一状态目录启动新进程，不传数据库密码。同步完成后再运行一轮，并尝试用错误密码替换凭据。 | 启动后自动续跑。原会话标识相同，原有三轮和新增两轮按顺序读回，两轮新内容和新会话均可搜索。重复同步仍只有五轮。错误凭据被拒绝，原配置仍能同步。 |
| 3. 跨设备和跨来源关联 | 客户端甲上传 A，客户端乙上传 B，Hub 从来源夹具拉取 VibeInsight 项目 C 和 D。经 Hub CLI 建立 A–B、A–C、B–D，再重复建立一次 A–B。分别从两套客户端按项目搜索，解除 A–C 后重查 A 及全局。 | A 的有效范围及命中仅为 A、B、C，B 的为 B、A、D。关联列表中 A–B 只有一条。解除后 A 的范围是 A、B，全局仍可查到 C 的原文。 |
| 4. 同名、改名和已有历史 | 用第 1 步的旧版档案升级。两台设备的同名项目各含独有文本，只关联其中一个。让设备在没有新增对话时完成项目归属补传，并改名后重查。升级和补传前后都读取同一条旧引用。 | 同名项目可区分，按关联起点只命中选中的项目。改名后关联仍有效。缺少归属的历史在补传前可通过全局找到，补传后按项目可查。旧引用可读，原会话和设备来源未重复。 |
| 5. 检索入口与引用可追溯 | 用 CLI 和真实 stdio MCP 客户端执行同一项目查询，分别选一条设备上传消息和 VibeInsight 消息，使用每条结果返回的引用进行精确原文读取，与源夹具逐条比对。 | 两个入口都标明汇总端和相同的有效项目集合。每条结果包含正确的来源、项目、原始会话标识及消息位置，读取的角色、正文及顺序与来源一致。 |
| 6. 回退和兼容 | 先用旧版客户端向新版 Hub 上传并执行全局搜索和读取。再停止新版 Hub，在本机两个不同项目放入共同关键词，分别用 CLI、MCP 按一个项目搜索。 | 旧客户端的上传、全局搜索和读取可用。断线查询沿用本机全局回退，两个本机项目都可命中，响应包含本机来源及回退原因。 |
| 7. 失败批次与重读去重 | 在写入某一批时注入可恢复故障，并读取该批前已保存的同步位置及已有对话。恢复后让 Hub 自动重试。再写入一条在本轮回查范围内、入库位置早于当前进度的延迟事件，执行重读。 | 失败批次未造成部分提交或越过尚未归档的记录，状态可见且已有对话可读。恢复后失败批次和延迟事件都能搜到。重复拉取后，同一来源会话和消息各保留一份。 |

另做一条范围回归。在夹具里原地改写一条已归档的历史消息，保持事件 ID 和入库位置，随后向同一会话追加一轮。验证新增轮次可查，旧消息仍读回原先归档的内容。

### PostgreSQL 查询验证（单独运行）

在隔离 PostgreSQL 中用少量合成事件执行实际读取代码，核对只读账号能查询、项目和会话标识正确、时间与事件 ID 边界正确分页，以及追加轮次和窗口内延迟事件能够被选中。初次接通上游和以后修改查询或连接方式时执行，可由开发者本机按需运行。默认 CI 无需安装 `psql`、启动 PostgreSQL 或连接 VibeInsight。后续如需自动化，可独立配置带临时 PostgreSQL 的 CI 任务。

### 回归与构建命令

先运行 `pytest -q tests/test_federation.py tests/test_vibeinsight_sync.py tests/test_cli_help.py tests/test_service_startup.py`，再运行 `pytest -q`。运行 `python3 scripts/build_packages.py`，将两个 wheel 分别装到干净环境，验证 Hub 能读取配置并运行同步，本机端能通过 CLI 和 MCP 查询。用发行版 Hub 执行首次 PostgreSQL 查询验证，检查连接依赖和服务账号环境。

实现 PR 按上述 7 项逐条记录通过、失败或未验证，并附脱敏的 CLI/MCP 响应、同步进度对比、测试和构建结果。交维护者审查前，在干净上下文按仓库的 [PR Review Prompt](../_templates/pr-review.prompt.md) 审查实现与验收证据，将结论写入实现 PR。
