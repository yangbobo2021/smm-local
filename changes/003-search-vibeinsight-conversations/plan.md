## 1. 与原计划的调整及原因

- 新 SPEC 要求三个系统的实际 Hub 服务及本机 CLI/MCP 证据。原计划的本机进程、模拟来源及可选 SQL 探针仍有价值，但不足以替代服务身份、依赖执行和重启验收。
- 采用 SPEC 已定的外部 `psql`，删除原计划“也可改用 Python 驱动”的备选。保留 PR #21 的固定上界只读 COPY 流、逐项目批次提交及可中断读取，不退回反复扫描全历史的实现。
- 默认回归继续使用固定来源夹具；另建立可重复运行的平台验收任务。PostgreSQL 仅在独立验收层使用，不让每次默认 CI 依赖真实 VibeInsight、私有网络或人工准备的数据。
- `serve-hub` 必须使用相同的配置/凭据目录参与自动同步。PR #21 此入口尚未挂接同步生命周期，列为实际代码工作，不能只靠补报告完成。
- 原七项索引保留为历史证据，新增以新 SPEC 五节及具体场景编号组织的索引。不得重写旧记录的版本、环境或通过范围。

### 自行管理进程的实现方案

拟为 `smm-hub serve-hub` 增加可选 `--state-dir <目录>`，读取由 `smm-hub hub --state-dir <同目录> vibeinsight configure` 保存的配置和凭据，并将 `VibeInsightSettings.lifespan` 传入 `create_hub`。
指定目录时默认使用 `<目录>/smm-hub.sqlite3`；同时给 `--db` 但指向另一数据库时拒绝启动并说明冲突，避免配置、进度和查询落在不同档案。
不指定新参数时保留旧 `--db`、Token/TLS 参数及无来源运行方式。该方案不注册系统服务，也不新增来源启停开关。
帮助和指南须明确新参数；此处命令为待实现方案，不能拿 #21 当前帮助当作已经支持。

### 拟新增验收入口与执行方式

- `scripts/acceptance/vibeinsight_fixture.py`：在 Q 的任务专用目录创建/关闭临时 PostgreSQL，生成合成清单和测试读账号；造数仅接受它自己生成且核对过实例标记的清单，不接受真实 VibeInsight 的 DSN。夹具控制器保留写权限，传给 Hub 的连接配置只有读权限。
- `scripts/acceptance/vibeinsight_platform.py`：提供 `hub`、`client`、`self-managed` 场景入口，编排 H、C、P 并输出第 7 节证据格式；实际系统操作分平台实现。可在 Mac 通过 SSH 编排远程机，但被测 Hub、CLI、stdio MCP、psql 必须在目标系统执行，返回目标系统原始退出码。
- `scripts/acceptance/README.md`：补预检、依赖安装位置、测试账户/提升权限要求、清单的准备方式、以下参数含义及清理命令。私有目标配置只记录机器/目录与连接方法，不作为公开证据上传。

拟定调用形态如下，**这些是待 S3 实现的入口，当前不能直接运行**：

```text
python scripts/acceptance/vibeinsight_platform.py hub --target-config <平台私有配置> --fixture-manifest <合成清单> --output <run-id>/<平台>/hub
python scripts/acceptance/vibeinsight_platform.py client --target-config <平台私有配置> --fixture-manifest <合成清单> --output <run-id>/<平台>/client
python scripts/acceptance/vibeinsight_platform.py self-managed --target-config <单平台私有配置> --fixture-manifest <合成清单> --output <run-id>/self-managed
```

每个平台的 `client` 同时执行 CLI/MCP 两种入口并分别输出；平台 `hub` 负责真实服务而不是启动一个替代前台进程。场景超时和预检失败都必须以非零退出及失败报告结束，`finally` 只清理本任务资源；保留失败日志。实现若选择拆分脚本或调整参数，在提交时同步本计划和重跑说明，不改变验收判据。

| --- | --- | --- |

| W-H / W-C | 家庭 ESXi Windows 11 测试机；Hub 为 `NT AUTHORITY\LocalService`，客户端为普通登录账户，安装/控制服务用提升权限的终端 | H1–H9；C1–C6。管理员能运行 psql 不代表 LocalService 能运行。 |

Q 可部署在可达的测试机或独立临时环境，无需三个系统各装 PostgreSQL 服务器；每个 Hub 必须在本机实际调用本机 `psql` 连接 Q，不能由 SSH 隧道末端的别处 Hub 代跑。为每次运行/平台创建独立数据库或夹具命名空间，防止并行造数影响其他验收。只开放所需测试网段与短期端口，使用完关闭本任务资源。TLS/Hub Token 使用测试专用值；不复用现有用户档案或服务。

### 固定夹具及独立期望

- 两个设备档案分别产生项目 A、B（含同名显示名），VibeInsight 来源产生 C、D；四项目有共同词和各自唯一词。关联固定为 A—B、A—C、B—D，查询上限足以容纳全部预期命中。
- 每次生命周期测试准备 C 内旧会话 T 的 3 轮，即 6 条 user/assistant 消息；停机追加 2 轮后为 10 条消息，并创建新会话 N。事件 ID、角色、来源位置、正文和预期顺序从独立夹具清单取得，不从 Hub 查询结果反向生成预期。
- 保存真实旧版本生成的设备归档、Hub 档案与引用；旧消息上传游标已提交，但缺少新版项目元数据。无新增消息时补归属，验证不是被新消息顺带触发。
- 额外准备：后来可见且早于既有进度的项目、行权限不可见项目、同时间多事件、相同事件重读、窗口内/外迟到、超过 24 小时停服、缺列权限账号、同目标的替换读账号、第二来源目标及三个仓库身份变化样本。
- 所有 Hub 来源查询（验证、发现、上界、分页、COPY）均须走显式只读事务。通过共用测试核对事务包装，并用真实 SQL/服务会话观察确认不是只在交互探针设置。夹具控制器的写事务与 Hub 读事务分开标记。

## 5. 三个平台实际 Hub 服务验收

### 每个平台必跑 H1–H9

每个平台均使用已安装包执行；以下“服务”指 systemd/launchd/SCM 的真实服务。服务生成的配置、日志、PID 与实际进程身份必须相互对应，不能只提交注册文件。

| 场景 | 步骤 | 必须取得的结果与证据 |
| --- | --- | --- |
| H1 配置和首次自动拉取 | 配置独立 HTTPS Hub。先在裁剪 PATH 的配置终端尝试默认 psql，确认缺依赖可识别；实际服务的搜索路径也不含任务专用 psql 目录。再用 `vibeinsight configure --psql <绝对路径>`、正确连接和读账号保存。启动或保持实际服务运行；不用测试程序直接调用同步函数。 | CLI 命令/退出码、脱敏配置、服务配置/实际 PID/账户、psql 版本、绝对路径及服务搜索路径必要字段；服务自行归档可读历史，`last_success` 与实际归档一致。保存服务调用真实 psql 的进程父子关系或等价进程审计与只读 SQL 观察。 |
| H2 周期及输入校验 | 从省略 `--interval` 的配置核对默认 300；记录下一次自动轮次或同步完成后的调度时刻。再设有效短周期，写新事件并等待至少两次自动轮次。分别提交 0、负数、非整数。 | 默认/自定义均继续调度；周期是轮次间隔而非导入耗时 SLA。非法值非零退出，原配置与凭据引用不变。状态时间、造数时刻、服务轮次及可检索新消息的时间对照。 |
| H3 错误配置替换 | 已有有效配置和档案时，分别用连接不可达目标、错误密码、缺必需列读取权限的账户尝试替换；随后在原来源追加事件。 | 每次失败给可辨认原因，配置和已有进度未被替换；原档案可读，原来源继续自动同步。保存失败前后配置/进度摘要、错误响应及后续命中。 |
| H4 服务中的依赖/连接故障 | 只对本任务的 psql 副本临时移走或撤销执行权限；分别制造“缺失”和“不可执行”。再停止 Q 的测试访问或拒绝测试连接；每项恢复后等待服务自行重试。 | 服务状态提供可识别的依赖/连接失败原因，最近成功时间不冒进，已有档案可读；恢复后增量可查。记录实际服务错误与恢复时间，不能用配置时的校验失败代替运行中失败。不得改动系统共用 psql。 |
| H5 换凭据和重启 | 在同 host/port/database 上换一个获同等读取权限的账号/密码；配置成功后停止服务并移除临时输入密码文件，使用原状态目录重新启动，既有专用凭据文件保留。 | 不再次输入密码即可自动同步；来源身份和进度延续，旧归档/引用可用。留配置前后非秘密字段、来源标识别名、进度和服务重启 PID。 |
| H6 停服后 3→5 轮续跑 | 确认 T 的 6 条消息已提交，保存 Hub 会话 ID、引用、项目进度和状态目录标识；真正停止服务。夹具控制器在停机期间向 T 追加 4 条消息并创建 N。用现有服务入口恢复，不重新 configure；完成后再等一次自动轮次。 | 同一 T 的 Hub ID；完整 10 条消息/5 轮顺序、角色、正文与独立清单一致；新轮次及 N 都可搜索并精确读取；重复轮次仍为 10 条。保存停止证据、造数清单、重启证据、前/后/再读的原文和进度，不只记总数。 |
| H7 无新增重启 | 已提交后不再造数，记录状态目录、T/N 及旧引用；停止/重启实际服务。 | 不出现空档案或换目录；旧内容与引用可读，来源及归档保留。不要求正常空轮次的游标数值完全不变，但必须仍是合法已提交位置。 |
| H8 未提交批次失败并恢复 | 在独立 Hub SQLite 夹具库安装只针对合成标记的临时触发器，使同一项目同批第二条待归档消息写入时 `RAISE(ABORT)`；触发条件同时要求本事务中第一条标记消息已存在，再让实际服务自动拉取。取一致性快照后移除触发器并等下一轮。 | 失败批次两条消息都未提交，游标未越过缺失记录，之前归档仍可读；状态有失败。恢复后两条均可查且只一份。保存触发器定义/目标表与标记、批次边界、失败前后及恢复后快照。触发器只作用于验收 Hub，不在产品代码加故障入口，也不接触真实来源。 |
| H9 凭据保护及脱敏 | 对专用凭据文件及父目录做所有者、权限/ACL 和实际拒绝读取检查；在服务正常同步的同时，让非授权测试身份尝试读取。扫描命令输出、日志及对话数据库的合成秘密原值。 | 服务身份可读、非授权身份不能读；秘密不出现在 argv、公开响应、日志或对话数据库。提交权限规则、身份/访问结果及秘密扫描“0 命中”，不提交秘密、凭据文件或完整敏感进程环境。失败和恢复日志同样检查。 |

任务专用 psql 采用可运行的完整客户端目录及所需动态库，不只复制一个可能无法加载依赖的可执行文件。H4 只修改这个目录中的测试副本或权限，恢复原权限后复验。

H8 的触发器须按实际 SQLite schema 生成并在预演中验证确实造成同批事务中止；如果现有批次安排不足以稳定命中，先修订夹具与探针并记录，不能把数据库连接失败冒充批中回滚。快照通过 SQLite backup/一致性只读事务取得，不复制活跃 WAL 文件当作完整快照。

### 各平台的具体服务操作及附加证据

共同配置命令形态：`smm-hub hub --state-dir <独立目录> setup ...`、`vibeinsight configure ...`、`vibeinsight status`；保持每条命令的同一目录。使用 `--password-file` 时只放测试秘密，配置后删除输入文件。HTTPS 地址、测试证书及 Token 由夹具提供，公开记录用稳定别名代替。

**Linux（L-H）**

1. 用普通测试账户安装 Hub，检查 `systemctl --user show-environment` 与 `loginctl show-user <账户> -p Linger`；准备可由该账户绑定的端口及受限目录。执行 setup，服务名取 CLI 状态返回值，不写死已有服务名。
2. 保存 `systemctl --user cat <unit>`、`systemctl --user show <unit> -p User -p MainPID -p ExecStart -p ActiveState`，并用 `ps` 核对 PID 的实际 UID、启动时间及命令。用户单元的 `User` 字段可为空，不能据此推断为 root。
3. H1–H9 均通过该单元执行。H6/H7 停止和恢复使用 `hub disable` / `hub enable`，辅以 `systemctl --user` 的停止/启动状态；H4 保存本任务 `hub.log` 及适用的 `journalctl --user -u <unit>` 脱敏节选。
4. 用 `stat`/`getfacl`（若有）记录目录及秘密文件权限；用不同普通测试 UID 做拒绝读取。执行后只停用本任务单元，保留必要公开证据，清理任务夹具。

**macOS（M-H）**

1. 以普通管理员账户安装和配置，setup 单独请求 sudo；不以 `sudo smm-hub ...` 把整个配置变成 root 所有。使用 `/Library/LaunchDaemons` 的任务独有 plist，核对 `UserName` 是配置账户。
2. 保存 `plutil -p <plist>` 的必要字段、`sudo launchctl print system/<label>` 及 `ps -o user,pid,ppid,lstart,command -p <pid>`。系统级 launchd + 普通账户的真实进程必须同时证明，不能仅给终端 UID。
3. 在无交互 shell 初始化和无开发 PATH 的环境下跑 H1–H9，确认配置的绝对 psql 路径可由该进程执行。H6/H7 用 `hub disable` / `hub enable` 卸载并重新装载任务，记录旧 PID 消失及新 PID；保存任务 `hub.log` 与 `launchd-error.log` 的必要节选。
4. 保存 `ls -lde`/`stat` 的权限/ACL；用另一个非授权测试身份读取失败。完成后停用任务独有 LaunchDaemon，保留用户原服务。

**Windows（W-H）**

1. 用提升权限的终端安装/配置；将候选 Python、工具环境和 psql 放在管理员管理、LocalService 可读取执行的任务目录，状态目录独立。执行前按技能核对测试 VM 身份。记录原生命令的 `$LASTEXITCODE`；日志统一 UTF-8，禁止把 PowerShell 进度输出当 JSON。
2. 保存 `sc.exe qc <service>`、`sc.exe queryex <service>`，并通过 `Get-CimInstance Win32_Service` 及对应进程查询核对 `StartName`、PID、ImagePath、实际运行账户。必须为 `NT AUTHORITY\LocalService`，不能用管理员前台启动替代。
3. 保存 `icacls.exe <运行目录>`、`icacls.exe <状态目录>` 及专用秘密文件 ACL；有效访问检查证明 LocalService 可执行 Python/psql 和读取秘密，非授权普通身份不能读取。管理员/SYSTEM 的维护权限不当作泄露。
4. 通过现有服务入口执行 H1–H9；H6/H7 用 `hub disable` / `hub enable`，结合 SCM 的 STOPPED/RUNNING 和 PID 变化。保留真实服务 `hub.log`、SCM 必要事件及依赖故障响应，不把 Windows 专用单测的通过当作这些结果。
5. 结束只停本任务服务/关闭本任务规则；清理任务运行目录与合成数据库，取回日志和退出码。测试 VM 的其他服务及回退 VM 不动。

### P：自行管理的 `serve-hub`（至少一个系统）

在 S2 实现新参数后，先用 `hub --state-dir <P目录> vibeinsight configure` 配置，不调用 setup/enable 注册服务。
用已安装包执行 `smm-hub serve-hub --state-dir <P目录> --token-file <测试Token> --tls-cert <证书> --tls-key <私钥> ...`。
按 H1/H2 的结果检查自动首次与周期同步，按 H6/H7 检查同目录重启、3→5 轮、不输入密码、旧引用及去重；再提交冲突 `--db`，确认启动被拒绝且档案不变。
另执行一次旧的无 `--state-dir`/无来源启动、全局查询及停止，确认旧行为保留。留完整启动命令（无秘密）、PID、退出码、配置/档案对应关系与响应；不能以 `hub run` 替代这个公开入口。

### 每次执行的证据包

以新运行 ID 建立 `evidence/<run-id>/`；历史文件保持原样。拟包含：

- `manifest.json`：UTC 起止时间、SPEC/PLAN Git 提交及摘要、候选源码 HEAD/脏树状态、安装模块和 wheel SHA-256、探针版本、OS/架构/Python/psql/PostgreSQL 版本、服务类型/实际账户、脱敏环境别名。实际运行与候选文件不符则拒绝开始，不在事后填候选 HEAD。
- `coverage.md`：新 SPEC 每一项映射 H/G/C/P 场景，分平台/入口列“通过/失败/未验证/有条件复用”，链接具体断言和响应。必要项未验证或失败则总状态为未完成。
- `commands.jsonl` 与 UTF-8 日志：顺序、工作目录别名、无秘密命令/工具参数、实际退出码、开始/结束时间、超时及输出文件；PowerShell 保存原生退出码后显式返回。预期失败和意外失败分开。
- 每平台 `service.json` / 权限报告：服务配置必要字段、PID/账户/状态目录、启动停止时刻、psql 的实际执行和配置终端差异、最小 ACL/所有权及有效访问检查。文件存在或注册成功不足以判通过。
- `responses/`、`checkpoints/`、`fixture-manifest.json`：同步前/失败后/恢复后/重复轮次的只读快照，稳定的项目/会话/事件别名映射，完整合成原文及独立预期比较，CLI/MCP 两入口的生效集合和引用。
- `reuse.md` 与 `SHA256SUMS`：逐文件说明旧证据绑定的提交、相关文件是否字节一致、环境与可覆盖行为；公开材料自校验。产品或依赖改变时重跑受影响项，不能只因 wheel 名称相同复用。

原始秘密、用户私有正文、连接地址/账号、证书私钥、Token、完整凭据文件不进仓库或 PR。合成数据可保留正文与事件别名，确保可独立核对；真实来源回执继续按原有脱敏边界，不以正文相等布尔值冒充可公开逐字复算。失败报告也须输出已完成步骤及日志，禁止残留上一次成功 JSON。

## 9. 回归、CI 与交付判定

### 日常回归

先跑定向用例，再跑全量：

```sh
python -m pytest -q tests/test_federation.py tests/test_vibeinsight_sync.py tests/test_cli_help.py tests/test_service_startup.py
python -m pytest -q
python3 scripts/build_packages.py
```

Windows 使用对应安装环境的 `python`。所有命令在候选检出目录执行，记录实际解释器，不能从其他 worktree 跑入旧代码。定向通过且没有后续修改时，全量仅跑一轮；修复后按影响重跑。构建后检查两个 wheel 并独立安装；源码单测不替代安装包路径。

拟新增 `.github/workflows/tests.yml`：push/PR 时三个系统运行不依赖 PostgreSQL 的回归，产出 JUnit/日志，验证安装包 CLI/MCP 基本入口；Windows 专用测试在 Windows 实际执行。失败或不适用的测试须明确原因，禁止为拿绿灯跳过必要平台。工作流中的运行器版本/依赖版本在实现时固定并记录，不把托管 runner 的管理员身份当作 LocalService。

### 独立集成与平台验收

- 拟新增 `.github/workflows/vibeinsight-integration.yml` 的手动触发任务：真实 SQL 共用集成使用可丢弃 PostgreSQL，在有客户端/服务器工具的环境运行，不作为默认 pytest 前置，也不携带 staging 秘密。旧 `vibeinsight_postgres.py`/`vibeinsight_upgrade.py` 在对应改造完成前按原说明运行，不能宣传其已支持 Windows。
- 三平台实际服务验收由上述 Mac/ESXi 任务独有环境运行并导出同一种报告。使用普通 hosted CI 无法证明 systemd 用户服务、系统级 launchd 或 LocalService 时，只报告它实际覆盖的层次；本轮由这些真实环境补齐，后续可用具备权限的专用 runner 调用相同脚本。
- 不以创建 CI YAML 代替实际验收，不要求发布 PyPI 或改变用户现有 Hub。隔离来源允许自动造数，真实 VibeInsight 永远不作为测试写入目标。

**收尾条件：** 新 SPEC 每条必需项都有实际通过证据或经逐文件/环境核对的有限复用依据；三个 Hub 服务、三个本机端的两入口及一个自行管理入口齐备，独立审查问题已闭环，使用文档与实际命令一致，PR #21 正文明确新结论对应的新版本及仍不承诺的历史改写/窗口外迟到边界。
若环境不具备、必要项失败或证据不足，保留“交付未完成”并列出具体缺口，不以本机通过推断其他平台通过。

## 10. 本轮实施调整

- 平台控制器按职责拆为 fixture / platform / client / shared，另用小型 stdio 退出码包装及权限验证、Windows 普通 token 启动器；接口与 H/G/C/P 判据保持对应。来源合成批次用单条原子 INSERT 发布，防止服务在造数中途只看到半批。
- TCP PostgreSQL 由 Mac 独立临时实例提供，各平台在本机执行 psql。Hub 只使用读账户；测试控制器持有夹具管理权限。真实 VibeInsight 不参与造数。源码与安装包以实际模块和 wheel 摘要绑定，预演失败和正式证据分别保留。
- Windows 通过任务独有目录的实际文件 ACL 修复安装环境访问前提。缓存硬链接文件的受保护 ACL 可能不继承目录的 RX 规则，因此核对叶子文件及真实 LocalService 结果；不扩大凭据目录权限。普通客户端通过当前已登录用户的交互会话 Limited 任务运行，避开 SSH 服务桌面的 DLL 初始化限制；凭据拒绝读取另用临时非授权普通账户，测试后删除。
- 远程网络下载不可用时，在全新环境中复用现有的第三方依赖文件，移除旧 SMM 包后用本次 wheel 单独安装 Hub/Local，执行依赖相容性与全部候选模块字节核对。未修改旧任务环境，也不把复制依赖本身作为产品安装通过证据。
- G4 的主机、端口、库名三种变化均由默认参数化测试验证。实际服务的 SQL 端到端切换库名，覆盖同一来源键构造路径的新来源早期历史与旧档案保留；避免三次重复搭建等价连接目标，三个字段的判据不减。具体运行结果及必要项缺口写入本轮证据，不用这些方法调整代替未执行的平台验收。

- Ubuntu 维护者确认本轮没有管理员认证方式；无可用 `newuidmap`/容器执行器可切换到另一宿主 UID。Linux H9 改为实际服务读凭据 + 原文件/目录所有者、模式、完整数字 POSIX ACL 核验：要求服务 UID 所有、无组/其他权限且无命名或默认 ACL 授权。结合 Linux DAC 判定其他非特权 UID 不可读，报告注明该判断为权限审计推论、没有执行跨 UID open；交独立审查判断是否足以支持相同 SPEC 条件。macOS/Windows 仍做实际另一身份拒绝读取。此项只调整验证方法，不扩大秘密访问范围或改变产品权限行为。

- 默认 CI 的 macOS runner 改用 `macos-15`。首轮实际执行返回 `macos-14-arm64-us-default is not supported`；核对 [GitHub runner-images 官方清单](https://github.com/actions/runner-images/blob/main/README.md)，macOS 14 已于 2026-11-02 退役。保留首轮失败记录，使用可用 runner 复跑。此调整不替代本机系统级 launchd 验收。

- 首次全系统 CI 暴露测试夹具使用 JSON 字符串替换 Windows 路径、手写未转义反斜杠的问题；改由 `json.dumps` 生成路径，不更改产品解析器。CI 明确使用 UTF-8 Python/stdio，与对话协议及平台探针环境一致，并关闭 checkout 的自动 CRLF 转换以保持 EVAL 的冻结源码摘要。此 CI 结果不证明旧式 ANSI 控制台的字符编码兼容性；公开证据保留实际编码环境与首轮失败。

- 三平台 pytest 在修正夹具后均实际通过；Windows 独立安装步骤另发现传给 `uv --python` 的路径必须显式带 `.exe`，已按系统选择真实解释器文件。此为 CI 命令修正，包代码不变。

- 首轮独立验收设计审查要求补强 H/P/G/C 的断言与原始证据，产品行为和 SPEC 判据不变：重启后逐个读取全部已提交原文及旧消息引用；无新增时完整游标不变；坏配置同时核对配置、凭据、进度和已归档消息；每类故障恢复后导入独立新增内容；新轮次用独有内容检索；P 保存实际 argv/PID/退出码。C 各关联目标逐一命中、两入口沿自身引用读取、实际改变并核对显示名、记录 MCP schema。G 核对动作前 K 与独立基线、重复关系唯一、解除后的实际命中。原调试与审查记录保留，修订候选重新调试、独立复审后再正式执行。
- 原生记录工具单条命令上限 300 秒，而默认调度必须实际观察完整 300 秒。H 的控制器不缩短或替换产品时钟：后台执行固定源码的完整服务探针，用“首次导入观察”和“同轮完整生命周期结果”两个有依赖的有界用例取证；保存控制器与服务 PID、源码快照和最终退出码。三套来源和状态独立，允许并行运行；正式结论要求同一轮完整结果及服务实际调用证据，不以启动后台任务本身认定通过。
