## 1. 当前实现与本次改动

当前本机 `federation.push_pending` 使用设备级消息游标，仅传 Codex、Claude Code；项目元数据跟随上传进度。`search_archive` 在线主要返回 Hub，失败会把项目范围改成全部本机；Web 直接调用本机 `Archive.search/read`。这些路径都需要实际改动，不能通过新增配置字段或验收报告完成本项。

既有 SQLite 使用 WAL，`Archive._write_lock` 仅在单个进程有效；CLI、MCP、本机服务和 Hub 管理命令可能是不同进程。新规则和正文发送的协调必须使用持久版本及跨进程锁，不能依赖一个 Python 线程锁。Hub 的归档与规则判定须在同一 SQLite 写事务提交，不采用两个 WAL 数据库“依次提交”来假定原子性。

已有 003 平台控制器可复用独立 wheel 核验、服务管理、UTF-8 日志和证据导出；其中的 PostgreSQL、来源造数及旧回退断言不直接用于 005。既有验收证据仅用于确定工具和环境，不能记作本次已通过。

## 3. 关键实现方案

### 3.1 本机状态、项目归属与发送边界

- 本机归档新增版本化表：项目类型与持久键、人工会话归属覆盖、按 `(hub_id, device_id)` 的完整期望规则/本机修改序号/提交标识/Hub 已确认版本，以及按原消息和内容版本的接收账本。项目类型不复用 Hub 现有的 `device/vibeinsight` 来源类型。
- 全局项目通过类型唯一约束保证一个档案至多一个；名称仍可显示为“全局项目”，不靠名称判断类型。内建及插件导入都先尊重显式归属覆盖，再采用已确认路径映射；无依据保持待定。现有导入不能因相同源文件重放而清除人工全局归属。
- 将 `map_path`、`merge_projects`、新会话归属操作纳入“预览—确认”流程：预览保存受影响身份、前后允许集合及规则/归属版本；确认绑定该预览，不重新计算后直接扩大允许范围。变更项目、规则或源会话后旧确认失效。普通/全局身份不能合并。
- 新的每批发送先在短事务内校验当前规则、项目身份和暂停状态，并登记开始发送的不可变批次及本机序号；网络调用不持有长期 SQLite 写事务。保存停止与派发使用相同跨进程协调边界；未开始的任务全部重新判断，已开始的明确记作在途。收到响应后只更新该批次账本，不反向覆盖新规则。
- 把项目/策略控制调度从正文队列分离：全局暂停时仍能确认限制和登记最小项目资料，正文不发送。正文队列按项目轮转，每轮设工作上限、失败项目后退，不能让一项反复失败阻止其他允许项目推进；用户查询不等待历史队列清空。
- 设备级扫描游标仅加快发现。未确认候选须能由消息身份账本重新枚举，允许 A 时不依赖 B 或旧游标的位置。批次只有取得匹配目标/代次/版本的整批确认才标记成功；未知按同一身份核实或重试。

提取消息身份函数时保持与 0.4.0 已存 Hub `source_key` 的指纹规则兼容；迁移核对先按该来源键及内容版本识别既有消息，不以新的编码形式给全部旧消息另建副本。只有同源关系可证实时归并；无法证实时保留不同证据，不使用文本相等作身份替代。

### 3.2 Hub 原子判定与恢复保护

Hub 在归档数据库内保存策略、设备已迁移标志、提交幂等记录及接收回执。策略 CAS 与正文处理都使用 `BEGIN IMMEDIATE`，在同一写事务中核验 Hub/设备身份、控制代次、策略版本、项目是否允许及消息身份，再同时提交归档和回执。混合项目批次任一项不合法则整批拒绝；本机拆分及重试不能据部分计数推进整批。

另设不随归档数据库恢复的保护文件，拟采用 `<数据库路径>.upload-guard.json` 及相邻锁文件。本机也使用相应命名的保护文件。`prepare-restore` 的输出逐项列出归档、配套配置/规则、保护文件及锁文件，区分须恢复与不得覆盖的部分；配置目录、独立 `--db` 和 `--state-dir` 都据实际解析路径生成，不能另开一份默认位置。

保护文件包含格式版本、档案身份、控制代次、已迁移设备标记，以及最新完整规则/摘要/恢复阻断状态，不含对话正文。采用同目录临时写、flush/fsync、原子替换并在支持的平台刷新父目录；跨进程使用固定锁顺序“保护锁→SQLite 写事务”。Windows 须验证实际锁与替换，不能假设 POSIX 行为直接成立。

涉及策略变更时，先持久写入带提交标识的保护屏障，再提交 SQLite 规则，再完成保护检查点，最后回复确认。正文事务在同一保护锁内检查保护文件与库内版本完全一致，无待恢复屏障才可接收。任一崩溃窗口存在差异时先停止正文，读取持久提交标识判断是否已提交；只有能证明同一提交已完成才自动完成检查点，否则要求对账。两份存储不宣称具有跨文件原子提交。

正常新建或尚未迁移的旧 Hub 可明确初始化控制状态；发现已采用策略的数据库却没有保护文件时不能重建成允许。Hub 保护文件保留迁移标记，恢复旧数据库后也不能把该设备重新视为旧式不受管设备。控制文件与数据库同回滚的受支持流程依靠预先写入且排除于恢复清单的恢复标记；绕过流程连标记一起手工回滚仍按 SPEC 排除。

`prepare-restore` 在该边界写入恢复代次/阻断后才返回成功。Hub 升级失败的 `restore()` 在还原前走同一逻辑；原来直接 `backup()` 回写的路径不能绕过。重新启动后先由对账解除阻断，再按当前许可重建接收确认，不能使用旧允许规则自动解锁。

### 3.3 协议、范围与精确引用

计划增加能力标志和以下内部路由，仍采用现有 HTTPS/Bearer 验证：`/v1/upload-policy/status`、`/v1/upload-policy/set`、`/v1/query-scope`。现有 `/v1/upload` 增量接收代次/策略版本/项目/幂等身份，`/v1/project-metadata` 将最小项目登记与已接收消息归属分开，`/v1/search`、`/v1/read` 支持范围快照和新引用。对同一设备迁移后的旧式正文请求永久拒绝，不影响其他旧设备的兼容路径。

Hub 对归属元数据核验该设备确有已接收消息来源，并核验当前管理版本；不能仅因另一设备已有相同会话就为本设备登记尚未接收的会话，也不能借旧元数据请求绕过新确认边界。

范围解析返回带格式版本与 HMAC 的快照：目标、请求项目稳定身份、直接一层项目集合及关联版本。Hub 搜索验证快照后使用这个集合，不再展开；本机仅映射属于当前设备且稳定键相等的项目。`Archive.search` 增加明确项目集合参数，不调用 `effective_projects` 再扩展，空集合必须返回空而非全部。Hub 不可用的 A 回退也用“仅 A”的明确集合。

内部召回均采用同一 N 和当前会话过滤，读取完整命中消息后才压缩展示。归并/重排仅针对正常候选，不新增扩大召回或自动补足。对旧 Hub 可取得的完整全项目候选按能力处理，不能发送丢失项目限制的请求作项目查询。

新 `reference` 封装版本化的本机或 Hub 引用：档案身份、原消息及版本、查询时允许消息/上下文和实际范围。使用规范化 JSON 与 HMAC-SHA256 检验完整性，各档案的随机签名材料随相应档案的一致性备份保留，不使用会随凭证更换失效的 Bearer Token 代替。`references.py` 保持为无网络的签名/校验模块，跨档案读取编排仍在 `federation.py`；Hub 构建仅 vendoring `archive_protocol.py` 和引用基础模块，不复制本机网络层。范围引用只允许读查询时确定的消息及同项目上下文，后续改变读取区间仍需与引用集合取交集。

归并后的结果保留多个独立来源引用；读 Hub 时只发送该 Hub 的引用组件，不把含本机候选的整个封装发出。原来无 `reference` 的 CLI/MCP/Web 读取保留旧路径，冲突参数直接拒绝。搜索结果逐条记录实际来源和可读取的消息位置，顶层 `combined` 不决定单条引用的档案。

### 3.4 三端入口与一致性

本机 API 增加上传状态/保存/对账/恢复前标记、全局项目/归属预览确认；所有新状态变更及被接入的归属维护继续走 `require_local_control`，不能新增可被外网页面直接调用的控制接口。CLI 调用同一规则服务，网络不可用但本机已保存时返回明确的待确认状态。MCP 本次不新增修改规则工具。

Web 搜索和阅读改接 `search_archive/read_archive` 的共用路径，表单增加默认联合/仅本机、范围说明和逐条原文操作；保留原本机读取 URL 的兼容形式。MCP 为旧位置参数保留读取能力，同时增加可单独使用的 `reference` 参数。CLI 允许 `read --reference` 不填旧整数位置参数，禁止冲突组合。

BM25 使用 SPEC D3 的词项、参数、文档频率和平局规则。测试的预期来自独立夹具清单及数学公式，不从被测排序器产生；重复副本先归并，再统计词频。预览截断只改变显示，不能改变重排输入或读取位置。

## 5. 可回归夹具、命令与工具

### 5.1 固定数据及独立预期

夹具由 `scripts/acceptance/selective_upload_fixture.py` 生成，并导出不可变 `fixture-manifest.json`。每次运行使用全新 run-id，准备下列资料：

- 设备甲本机普通 A、普通 B、全局 G、归属待定 U、仅本机关联 D；设备乙有同名但不同键的项目。Hub 中加入二层 C 及合成 VibeInsight 项目 V。Hub 关系设为 A—B、B—C、A—V，本机关系 A—D；A—G 只在对应测试步骤明确建立。
- A、B、G、U、C、D、V 含共同词和唯一词。A 有未上传历史、已接收旧副本、停传期新会话及旧会话追加；B 的扫描进度先越过 A。准备真实 Codex 和 Claude Code JSONL（含重复文字但不同轮次、缺 `cwd`、Unicode/空格路径）。另以现有插件夹具取得至少一种不可上传的有效来源，不能只手写一条无效来源名。
- V 的隔离归档通过现有 VibeInsight 转换/归档逻辑和合成事件读取器准备，再由实际服务查询/读取；此处验证新增检索与引用，不重新验证真实 PostgreSQL 拉取。夹具不接收真实来源 DSN，也不修改真实服务器。
- 单独准备本机与 Hub 同整数会话 ID、不同消息/版本、长消息关键字位于 600 字之外、当前会话副本、跨项目共享会话、未知同源及重复偏移位置。原始期望按来源身份/角色/完整正文/位置给出，不从最终查询反向生成。
- 共用竞态控制器在请求到达、持久保护、规则提交、消息提交、确认返回前后设置可复现屏障。测试专用屏障通过测试适配层或仅测试进程配置提供，不新增生产 HTTP 任意暂停/写入接口。
- 数学夹具包含去重后文档、词频、df、平均长度、独立 BM25 预期及平局身份顺序。另保存删除副本前后的预期，明确区分不同轮次/版本。

旧包固定为已发布 **0.4.0**，源码标记 `v0.4.0` 对应 `4d58202f60d8dfa1292e0feae28447e115d08cd9`。构建/下载时记录实际 wheel SHA-256；在独立环境中由真实旧包生成旧档案、上传游标、项目键和旧引用，禁止用新包仿造“旧库”。旧包测试只使用合成资料和临时凭证。

A1 要求的同目标升级在每个 E1 平台使用该平台独立的旧 Local 环境生成任务档案，再由新 Local 接管；设备身份按平台/run-id 隔离。完整三种新旧组合与恢复专项集中在 E5，不要求每个平台重复安装旧 Hub。

### 5.2 可重跑入口与实施调整

以下 `python` 表示验收控制环境的解释器；Windows 使用其 `Scripts/python.exe` 绝对路径。SSH 只编排和收集证据，被测 CLI、MCP 与浏览器仍在目标系统执行。独立包安装步骤见 5.1，以下入口已实现，但每次结果只代表其 manifest 绑定版本实际执行到的检查。

```text
python scripts/acceptance/selective_upload_prepare.py --work <新任务目录> --local-python <LocalPython> --hub-python <HubPython> --local-wheel <LocalWheel> --hub-wheel <HubWheel>
python scripts/acceptance/selective_upload_platform.py client --target-config <私有目标配置> --output <新目录>
python scripts/acceptance/selective_upload_platform.py hub-service --target-config <平台配置> --output <新目录>
python scripts/acceptance/selective_upload_platform.py login-service --target-config <macOS配置> --output <新目录>
python scripts/acceptance/selective_upload_platform.py self-managed --target-config <单平台配置> --output <新目录>
python scripts/acceptance/selective_upload_compatibility.py --target-config <新旧环境配置> --output <新目录>
python scripts/acceptance/selective_upload_recovery.py self-managed --case R1 --target-config <新配置> --output <新目录>
python scripts/acceptance/selective_upload_recovery.py self-managed --case R2 --target-config <另一新配置> --output <另一新目录>
python scripts/acceptance/selective_upload_recovery.py hub-service --case R3 --target-config <另一新配置> --output <另一新目录>
python scripts/acceptance/selective_upload_recovery.py hub-service --case R4 --target-config <另一新配置> --output <另一新目录>
```

原计划的 contracts compatibility/recovery 拆成两个独立控制器，避免兼容状态与恢复故障注入共享流程。原 `hub` 模式改名 `hub-service`，明确真实服务；不再使用独立 preflight 子命令，预检在各入口执行并落盘。`prepare` 生成一次性 CA/证书、私有目标配置和候选源码/两个 wheel 全部文件摘要；fixture 由控制器在任务目录创建，不再传单独 fixture-manifest。不匹配候选字节则拒绝执行。详细参数及 Windows Limited 交互包装入口见 `scripts/acceptance/README.md`。

`hub-service` 只用实际系统服务；`client` 使用真实 CLI、独立 stdio MCP 和本系统浏览器，保存响应、原文和截图。E3 可显式 protocol_only，但此结果不算 E1 浏览器验收。浏览器驱动独立于生产包；没有浏览器时先修复准备条件。恢复使用产品 prepare-restore、实际服务启停及 reconcile。每项执行有超时与 finally 清理，只清理任务标记的资源，失败原始资料保留。

原独立 audit 脚本尚未实现，不能按该旧命令宣称覆盖审计完成。最终须由独立 Reviewer 对照每次 manifest、真实命令/响应/截图、清理结果和 A1–A12/E1–E5 表逐格审计并记录缺口；如果增加机器审计入口，一并更新本节和证据索引，不能拿产品重新查询生成预期替代原始证据核对。

### 5.3 本地回归与 CI

实现过程中先运行对应测试文件，相关测试通过后运行全套 `pytest` 和构建。拟定命令如下：

```text
uv run --extra test python -m pytest -q tests/test_upload_policy.py tests/test_upload_recovery.py
uv run --extra test python -m pytest -q tests/test_combined_search.py tests/test_archive_references.py
uv run --extra test python -m pytest -q
python3 scripts/build_packages.py
```

默认 `.github/workflows/tests.yml` 保留 Ubuntu 24.04、macOS 15、Windows Server 2022，新增共用行为回归、两个 wheel 独立安装及 CLI/MCP 协议烟测。保持 UTF-8、Windows `.exe`、源码字节不作 CRLF 自动转换的既有设置。生产模块新增共享依赖时必须同步 vendoring 清单，并在不安装另一包的环境导入和运行，防止源码环境掩盖打包错误。

各平台安装使用相同 wheel，解释器路径分别为 macOS/Linux 的 `<环境>/bin/python`、Windows 的 `<环境>/Scripts/python.exe`。从构建产物中取实际文件名后执行，不以通配符误装旧包：

```text
uv venv <任务目录>/local-env
uv venv <任务目录>/hub-env
uv pip install --python <LocalPython> <本次smm_local的wheel文件>
uv pip install --python <HubPython> <本次smm_hub的wheel文件>
<LocalPython> -m smm_local.cli --db <任务档案> upload status
<HubPython> -m smm_hub.cli hub --state-dir <任务Hub目录> status
```

`LocalPython/HubPython` 从上述新环境定位，wheel 从本轮构建清单定位；服务未注册时状态输出仅用于预检，不作为运行通过。旧包另建环境，不能安装到同一个 venv 后靠反复切包冒充同时存在的新旧组合。

新增 `workflow_dispatch` 验收任务可在托管 CI 中运行已安装包的普通进程、真实 MCP、浏览器及合成夹具，不需要 PostgreSQL、VibeInsight、家庭网络或人工造数。家庭机器上的服务身份与 macOS 登录服务通过同一组平台脚本按需重跑；默认 CI 不等待人工管理员认证。CI 产物只声称其实际覆盖的入口/运行方式，不能代替 E2/E3。

## 6. 实际平台、准备与执行步骤

### 6.1 目标与预检

| 目标 | 拟用机器与运行方式 | 准备条件与验收范围 |
|---|---|---|
| M-C / M-L | 当前 Mac；当前系统 macOS 15.3.1；普通用户本机后台进程及专用登录服务 | E1/E2：独立本机环境、任务档案、浏览器；登录服务使用单独 label/任务目录，不替换日常 SMM |
| M-H | 同一 Mac；系统级 launchd，配置普通账户运行 | E3：管理员认证安装/控制任务专用服务，记录 `UserName`、PID、状态目录；实际账户访问保护文件与档案 |
| L-C / L-H | 家庭 ESXi `codex-ubuntu`（VM 75）；本机用户进程与 systemd 用户服务 | E1/E3：执行前记录实际 OS（上轮为 Ubuntu 22.04.5）、浏览器及用户服务能力，不把 CI 的 24.04 当成该机版本 |
| W-C / W-H | 家庭 ESXi `win11-keysync-no-snapshot-test`（VM 76）；普通交互用户与 LocalService | E1/E3：核对正确 VM；用户浏览器/MCP 和 LocalService 分别执行，管理员仅用于服务及本任务目录的必要权限 |

远程操作依 `home-esxi-test` 技能：执行前使用技能脚本 `status windows/ubuntu` 核对 VM 身份、电源和 SSH；Windows 保留回退 VM 73 关闭，核对目标 MAC。严格校验 SSH 主机密钥，远端建立任务独有目录。地址、账号和登录配置仅进私有目标配置，不提交仓库。计划编写阶段未测试远程连通性、权限或浏览器就绪，不能据上轮结果填“已具备”。

预检须实际检查：目标身份/架构/OS、包安装/依赖、Python、浏览器可执行性、服务管理权限、状态目录与保护文件访问、测试 HTTPS/CA、可用端口和旧包可用性。Mac 管理员认证与 Windows 服务提升权限在实际执行需要时处理；Ubuntu 用户服务正常时不需要跨 UID 权限测试，本 SPEC 未要求新增秘密文件的另一身份读取验收。

不满足条件时先保留失败预检和修复环境，不能把系统服务换成前台进程、把 Windows 浏览器换成 Mac 浏览器，或直接跳过后判通过。此阶段不请求管理员认证或开关虚拟机；执行阶段按当次授权及实际需要处理。

### 6.2 每个平台本机客户端 E1 的执行顺序

1. 从同一候选提交构建两个 wheel，目标系统建立独立 Local 环境，清除开发 `PYTHONPATH`，核对实际导入路径、模块摘要及 wheel 哈希。用原始进程记录真实运行身份、后台服务 PID 和档案路径。
2. 使用合成来源导入 A/B/G/U/D 及插件资料，先取得本机基线原文。连接独立 Hub 后不选择上传，观察一次后台和一次手动同步，确认 Hub 只有最小登记；再验证四模式、错误输入及新项目。
3. 允许 A 上传已知旧副本，保存精确引用；改为禁止 A、允许 B，等待双方确认后追加 A 新会话和旧会话轮次。触发后台/手动/失败重试，确认 A 新内容仅在本机、旧 Hub 副本仍可读、B 有推进。
4. 按 A 分别通过 CLI、独立 stdio MCP 会话和本机浏览器查询。记录 A/B/V 的有效集合，排除 C/D，逐条沿各入口自己的引用读回本机、另一设备、VibeInsight 内容；切换仅本机得到 A/D；全部查询包括 G/U/插件。
5. 用同号 ID、不同消息版本和长消息夹具检查排序、准确来源、完整原文。浏览器沿实际按钮操作，不能只用 HTTP 客户端代替点击。检查 Hub 请求载荷和错误日志不含本机禁止内容。
6. 断开该客户端的任务专用 Hub 通道，三入口按 A 只查本机 A、不含 D；全项目回退为本机全部并说明原因。恢复通道后下一次回到联合查询，显式仅本机不变。
7. 在 A 仍禁止且已积压历史时停止并重新启动实际本机服务，不重新配置；检查规则/状态、旧 Hub 引用和本机新增命中。明确允许 A，补齐全部缺失及后续内容，从 Hub 检索并精确读回，再次同步数量/身份不变。关闭或暂时失效一个项目不能阻塞其他允许项目。

M-C、L-C、W-C 都执行以上流程，三个入口分别保存请求、响应和引用读取，不能仅把共享 Python 函数调用三次标作三入口。

### 6.3 macOS 登录服务 E2

用已安装候选包的 `login_service.install` 注册专用 LaunchAgent，给内部可选 label 和日志目录参数传入 run-id，默认正式 label 仍为 `ai.smm.local`。`location/install/uninstall` 使用同一 label，避免卸载时误删默认服务。确认其实际 `ProgramArguments`、运行用户和 PID。执行 6.2 的“旧副本→停止→新增”后，通过真实 `launchctl` 停/启该 label；规则继续禁止，本机可查询新增、Hub 旧副本可读。Web/CLI 状态一致。再明确允许并观察后台补齐、Hub 检索读回与重复同步不增。

仅重启前台 `serve` 不算登录服务证据；不为验收修改用户现有 `ai.smm.local` 注册。完成后卸载本任务 label，核对无残留及日常服务状态。

### 6.4 三平台 Hub 服务 E3 与自行管理 E4

每个 Hub 各用全新任务状态、HTTPS 端口、独立服务身份/注册名；客户端可复用一个已安装候选环境，不要求系统组合穷举。

1. 安装候选 Hub wheel，不安装 Local 包，核对模块（含 vendored 代码）摘要。通过系统管理器启动，取真实服务配置/账户/PID，不拿注册成功当运行成功。
2. Linux 使用任务专用 systemd 用户单元；macOS 使用任务专用系统级 LaunchDaemon 且 `UserName` 为配置账户；Windows 使用任务专用 LocalService，并核对 Python/依赖/档案及保护文件的叶子访问权限。Hub 现有服务名由状态目录摘要生成，使用独立状态目录即可隔离，不另设产品服务名选择功能。
3. 不上传 A 正文，先登记项目并由该 Hub CLI 关联；检查最小载荷。确认允许并上传旧消息，保存回执与原文；再确认禁止 A，重放旧策略批次及旧式无版本批次，两者拒绝且归档/正文未增加。
4. 在该服务运行期间执行范围快照查询和新范围引用读取，使用跨项目共享会话负例验证无范围外正文；旧引用仍可读。该 Hub 上其他设备/项目不受 A 限制影响。
5. 禁止期间追加本机内容，停止/重启真实 Hub 服务，客户端不重复配置；旧请求继续拒绝，规则及既有回执保留。允许后补齐新增，Hub 查询/读回正确，再同步不重复。
6. 每个平台至少完成一次真实旧请求重放、持久规则重启和恢复允许补传。精细乱序/崩溃窗口由共用可控测试补齐，不把单次成功替代竞态全表。

E4 另在一个平台使用公开 `serve-hub --state-dir` 前台/自行管理进程入口完整执行上述判据，记录 argv、PID、退出码及相同状态目录重启；不以 E3 的系统服务记录代替。服务停止期间既有本机查询继续可用。

## 8. 兼容、恢复与竞争专项

### 8.1 真实版本组合

用同一夹具分别建立：new Local/new Hub、new Local/0.4.0 Hub、0.4.0 Local/new Hub。旧包调用旧命令和旧 MCP 参数，不通过新包 helper 代跑。

1. new/new 验证初始待选择、选择后写、联合范围及新旧引用。
2. new/old 反复触发后台与手动同步，确认无正文；按 A 仅本机 A 并报告能力不足，全局能处理可验证的旧候选，不冒充完整新能力。
3. old/new 先证明未迁移设备保持旧写/旧全局读；再由新包对同一设备建立新策略。重新运行旧进程，旧式正文被拒绝，旧式全局读及旧引用仍可读取。身份使用测试专用数据，不克隆用户配置。
4. 旧包生成含已确认游标的历史，升级为新包；核实同一 Hub 的迁移规则、项目键/显示名/关系和原精确引用，再允许或补齐此前缺少的消息。改变 URL、凭证及真正的 Hub 身份分别验证。

### 8.2 受支持恢复

每个恢复场景独立建档，先写入已知允许规则和旧消息，取得一致性 SQLite 备份及配套状态清单；随后执行收紧/新增，以制造有意义的新旧差异。

| 场景 | 操作 | 必须核对 |
|---|---|---|
| R1 本机回到旧允许 | 产品 `upload prepare-restore`→停本机服务→恢复该备份集，不覆盖保护标记→重启 | Hub 新停止不被旧允许覆盖；差异输出可查，正文阻断；仅查看不改规则，明确采用当前 Hub 后仍停止 |
| R2 Hub 丢失新归档及新限制 | Hub `prepare-restore`→停真实目标进程→恢复旧数据库→原目录重启 | 保护代次与迁移标记仍有效；旧确认失效；先对账，当前允许记录补回，禁止记录不补；旧式请求仍拒绝 |
| R3 Hub 配套状态也回旧 | 与 R2 同流程，但恢复清单中的配套状态也旧，保留排除项中的恢复标记 | 即使两端库内版本表面相同也不能自动解锁；对账后才接收，清单未误含保护标记 |
| R4 已有升级失败自动恢复 | 使用离线可控的升级失败/健康失败入口，走实际 `Hub.upgrade/restore`，不只直接调用 `restore` 单函数 | 恢复前先保护，原包/服务状态按既有承诺恢复，正文不恢复为旧允许；日志有实际安装版本、退出和恢复顺序 |
| R5 对账期间又有新修改 | 获取差异/Hub 版本后提交另一条有效规则，再用旧版本执行 `--use local`；Web 同样以旧页面提交 | 条件更新拒绝，不覆盖较新规则；取得新差异后方可明确提交；失败不虚报双方已确认 |
| R6 未确认提交与丢失回执 | 分别在保护落盘、数据库提交、确认返回、客户端账本提交前后中断；另删掉测试备份中的确认账本但保留可验证规则 | 可证明同一提交时幂等完成，否则停传待处理；已存消息不重复，未知不跳过，没有一个崩溃窗口默认允许 |

R1–R6 在 E5 至少一平台完整执行，跨平台的文件替换/锁/路径行为由 E1/E3 的真实持久规则和重启配合默认三平台测试覆盖。若实际差异使单平台专项不足，先补对应平台验证并更新本计划，不能以实现变更降低 SPEC 的恢复保证。

## 9. 证据格式、审查与清理

正式证据目录为本目录下 `evidence/<run-id>/`，run-id 使用日期及唯一后缀。调试失败与正式执行分开保留，输出目录存在则拒绝覆盖；不得复用上次 `passed` 文件填本次空格。

- `manifest.json`：基线/候选提交、是否有未提交变更、实际安装模块/两类 wheel 摘要、OS/架构/Python/浏览器版本、目标别名与服务运行方式、夹具/工具版本及起止时间。正式包必须对应可复核提交，环境不符则拒绝开始。
- `coverage.md/json`：逐 A1–A12、E1–E5 及各平台/入口列通过/失败/未验证，链接原始响应、断言和时间线；必要格子缺失则总状态为未完成。
- `commands.jsonl`、`service.json`：动作、脱敏参数、原始退出码、真实服务名/PID/账户/状态目录别名、启停事件；PowerShell 显式传播原生退出码。实际服务身份与普通客户端身份分开。
- `fixture-manifest.json`、`responses/`、`checkpoints/`：来源独立预期、消息身份/版本/完整合成正文、当前规则及代次/回执、前后消息差集、当前项目与有效范围、候选和最终得分、每个入口取得并使用的引用。负例保存实际错误及“数据未增加”的对照。
- `browser/`、`payloads/`：配置、状态、差异、覆盖和原文的截图/DOM 证据，实际浏览器/服务网络路径；Hub 端只记录合成请求，私有 Token/证书/路径脱敏。涉及禁传内容的证明保留可比对的合成唯一标记，而不是仅写“无泄漏=true”。
- `reviews/`、`SHA256SUMS`：证据审计结果、干净上下文 PR Review 依据、修复及复核记录、公开产物摘要。只展示行为测试通过不能替代使用路径审查，也不能把既有 003 证据写成本次新行为证据。

验收工具只清理本次 run-id 的服务、监听进程、目录和测试凭证。macOS 核对任务 LaunchAgent/LaunchDaemon 均已卸载，Linux 核对任务单元，Windows 核对任务服务及交互任务；保留必要失败日志，记录清理退出码。清理需要提升权限时使用原授权方式，不遗留等待认证的后台清理进程。用户日常 SMM 服务、档案和其他 VM 任务不修改。

## 10. 实施中的调整记录（2026-11-22）

- 归属预览/确认单独拆为 `src/smm_local/project_control.py`，供 CLI/Web 共用；它与正文派发共用保护锁，并绑定归属集合与规则版本，避免两入口各实现一套预览。

- 新 Local 对旧 Hub 的全项目候选，逐条以旧消息定位读回核验并绑定内容版本；缺失同源身份时不与本机副本误去重。按项目仍只回退本机原项目，不向旧 Hub 发丢失限制的全项目请求。
- 新增 `tests/test_005_contracts.py` 记录六项核心 TDD 中的五项；恢复核心用例在 `test_upload_policy.py`。其余回归按本计划的排序、引用、恢复文件划分。六项均已有独立复审的红灯及同版绿灯；这不代替完整 A1–A12/E1–E5 验收。
- 平台控制器使用 TLS 审计转发保存合成请求，以任务专用通道制造离线，不替换产品请求函数。浏览器使用验收专用 Playwright 依赖和实际浏览器。可选 CI 只验证其真实运行的已安装包/普通进程入口，不宣称系统服务或 macOS 登录服务通过。

- 真实 0.4.0 组合调试发现：新档案已进入待选择，但同档案旧后台仍可用旧接口写入新 Hub。按 SPEC B8/A10 的降级边界，新协议首次登记即持久标记该设备采用控制；未选择规则仍保持 null/待选择，不替用户决定上传模式，Hub 先拒绝该设备旧式正文。已有规则不被登记重置；其他未迁移设备仍走旧兼容路径。新增 `/v1/upload-policy/register` 与 `hub_managed_devices`，标记和保护文件共同处理丢失/恢复。该实际失败已记录红灯并独立复审，修复后另复验真实旧后台进程。

- 家庭测试机访问 PyPI 的大型浏览器工具包超时，验收控制端可复用已取得的官方 Playwright 1.65.2 平台无关 Python/JS 文件，逐文件核验清单，并通过其 `PLAYWRIGHT_NODEJS_PATH` 入口使用目标机已有 Node。绿色扩展仍按目标 Python ABI 安装。实际 Node 版本/摘要与工具文件清单写入运行 manifest；不把本机 Node 二进制复制到其他平台。产品子进程清除开发 PYTHONPATH，Local/Hub 仍只使用独立 wheel；可选 CI 沿用正常安装 Playwright 的路径。
- 增加 `selective_upload_recovery.py` 对安装包执行恢复流程；R4 的离线可控入口将包安装替换为明确标识的成功桩，实际运行候选包 `Hub.upgrade`、systemd 服务重启、健康失败与数据库恢复，期间确认新的停止规则再验证保护。它不声称验证真实版本发布/下载或未来新包迁移，源文件/实际包字节和模拟边界写入证据。
- 三平台 CI 的 Windows 跨进程用例发现锁文件初始化在取锁前写入首字节，触发受另一个进程锁住区域的访问拒绝。按 Windows `_locking` 可锁 EOF 外区域的语义，改为先取锁、只在持锁后初始化空文件；复跑原用例与三平台 CI，不改变约定的互斥/超时行为。
- Windows 普通客户端调试发现 WMI 创建的后台进程没有继承调用方私有 CA 路径，导致配置命令可连接而实际后台不能连接。`service.py` 的既有显式环境白名单增加 `SSL_CERT_FILE/SSL_CERT_DIR` 与任务端口，不复制任意环境或秘密；真实 HTTPS 后台上传回归使用临时 CA。隔离 Python 的验收命令显式加 `-X utf8`，避免 `-I` 忽略 Python 环境变量后把正确中文误解码。
- 安装包恢复探针发现 `hub prepare-restore` 的连字符未映射到方法名，修复公共 CLI dispatch 并加入实际命令回归。候选完整内容与签名的竞争窗口也按 B6/B7 收紧：先以全文/原消息键绑定引用，再截断预览；单个候选缺失时排除并标记部分覆盖，不补召回、不丢掉其他有效候选。旧 Hub 的能力限制显式显示。

- 固定 b76 的独立审查新增四个实际反例及红灯：晚到 offset 前缀导致重复轮次漏传、核对后切换 Hub 仍派发旧端、时间戳版本被旧存储指纹错误确认、正文失败未进入独立状态。修复时重算受影响会话完整 occurrence/order，并把来源位置/顺序接收回执与正文版本回执分开；派发在同一 SQLite 写边界重新核对实际连接及消息身份；Hub 保留兼容指纹并为冲突内容版本保留独立实体和原 canonical 身份；持久传输失败/补齐状态与规则确认分开。独立红灯/绿灯和最终平台重跑分别记录，不把草稿审查或历史通过当最终交付。

- E1 的同 Hub 真实旧 Local 升级在 macOS/Linux/Windows 分别使用四个独立环境的兼容探针，扩大复跑的实际组合而非用合成旧库代替。Windows 包装器新增 compatibility 探针选择，继续使用 Limited 交互身份。实际 VM 的启动开销较大，专用任务超时为20分钟/调度硬上限22分钟，进程结果与清理仍须核对。
