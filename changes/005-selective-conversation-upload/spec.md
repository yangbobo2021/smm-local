# 规格：按项目控制本机对话上传，并联合检索本机与 Hub

状态：SPEC 已确认（2026-11-22）。依据：[已确认意图](intent.md)，已随 [PR #27](https://github.com/yangbobo2021/smm-local/pull/27) 合并。现状基线为 SMM 0.4.0。本文件定义交付要求，不记录执行结果，不代表功能已实现或验收通过。

## 预期行为

### B1. 查找入口与选择上传范围

用户已通过 `configure-hub` 或现有 MCP 配置入口提供 Hub 的 HTTPS 地址、本机显示名及本机凭证文件。凭证由 Hub 维护者提供，继续沿用现有保管方式。上传规则绑定本机档案的设备身份和 Hub 返回的稳定 `hub_id`，不按显示名或 URL 单独判断是否同一目标。

本机 Web 的“配置”提供“对话上传”入口，“导入进度”展示对应摘要。CLI 提供以下操作；它们与 Web 使用同一份状态，不能各维护一份规则：

| 操作 | 输入及含义 | 用户可见结果 |
|---|---|---|
| `smm upload status` | 无额外输入；使用当前档案及 Hub 配置 | 目标 Hub、规则、项目选择、确认状态、未传/未确认数量及最近失败原因 |
| `smm upload set --mode <模式>` | `all` 全部、`only` 仅指定、`except` 排除指定、`none` 全部不上传；`only`、`except` 通过可重复的 `--project-id` 指定本机项目 | 校验并保存完整规则，返回本机与 Hub 的实际生效状态；不把保存当成同步完成 |
| `smm upload reconcile` | 无参数时显示本机与 Hub 差异；经查看后，以 `--use hub` 接受 Hub 当前规则，或以 `--use local --expected-hub-revision <版本>` 明确重新提交所显示的本机规则 | 解决恢复或并发冲突；版本来自本次差异输出，已过期则拒绝而不覆盖新规则 |

项目 ID 从 `smm projects` 或 Web 项目列表取得；列表同时显示名称、普通/全局类型、稳定身份及当前是否允许上传，用户不能只凭同名项目作选择。`only` 空名单表示全部不上传，`except` 空名单表示全部上传；`all`、`none` 不接受项目名单。无效模式、不存在的项目或无效版本不替换有效规则。未配置 Hub 时可以查看说明，但不能保存一份声称绑定目标的规则。

Web 同样提供差异查看与“采用 Hub 当前规则 / 重新提交本机规则”的处理入口，提交绑定页面所展示的 Hub 版本；页面过期时要求重新查看。CLI 修改失败以非零退出状态及可识别原因返回，Web 不展示保存成功；网络失败但本机规则确已保存时明确显示“本机已保存、Hub 待确认”。

MCP 保留现有配置 Hub、同步、查询及读取工具，本次不新增 MCP 修改上传规则工具；Agent 可通过 CLI 或打开 Web 管理规则。规则配置与项目关联分开，Hub 关联继续由维护者通过 Hub CLI 管理。

README 主使用路径须介绍“连接 Hub 后可控制上传、默认联合查询”，链接到具体使用说明。使用说明、CLI 帮助、Web 提示及检索 Skill 应让用户找到项目 ID、四种模式、历史副本保留规则、状态解释和恢复入口，不能只在本 SPEC 提供这些信息。

### B2. 默认选择、范围与状态

- **首次连接**：未明确选择前，不发送对话标题、正文、摘要或消息列表；允许查询、设备登记及 B3 的最小项目登记。状态为“待选择，不上传正文”。
- **同一 Hub 升级**：能验证升级前已配置的设备身份、Hub 身份及既有上传状态时，保留原本允许的 Codex、Claude Code 上传范围；0.4.0 对应“全部”。首次升级后的 Web 与 CLI 明确展示迁移结果。无法验证目标身份、控制状态丢失或已存在冲突时，先停止正文发送并要求处理，不能猜测“全部”。
- **更换目标**：URL 或凭证改变，但验证为同一 `hub_id` 且控制状态一致时保留规则；首次见到其他 `hub_id` 时重新选择，既有历史与进度按目标隔离。曾配置的 Hub 再接回时先核对其已保存规则与版本，不能把其他 Hub 的允许规则带入。
- **新增项目**：稳定归属明确后，普通项目与全局项目均按四种模式自然决定；归属待定不发送正文，即使模式为 `all`。同名项目不相互继承选择。

状态至少区分：待选择、本机规则已保存/Hub 待确认、双方已确认、在途结果未确认、正在补齐历史、存在冲突待处理。规则确认状态与数据上传进度分别报告，允许“规则双方已确认、仍有未确认记录”同时成立。计数覆盖当前目标，区分未发送、发送后未取得接收确认及已确认，不把跳过或扫描数量记作已上传。

保存规则不改变本机来源启停或全局暂停。全局暂停期间可保存规则、查询和最小项目登记，并可向 Hub 确认限制；不得因此恢复正文上传或本机自动导入。显式同步也不能绕过上传规则或现有暂停语义。

### B3. 稳定项目、全局项目与最小登记

普通项目沿用已有本机项目及持久随机项目键，Hub 身份为设备身份与项目键的组合。显示名、路径显示方式改变不重置选择或关联。不同设备的同名项目仍是不同项目。

每个本机档案有至多一个“全局项目”，具有独立持久项目键，类型为 `global`，与普通项目同级，可覆盖该档案内明确归为全局的不同来源会话。它不同于“全部项目检索”，也不同于目录根路径、用户主目录或任意无 `cwd` 的记录。

首版 Codex、Claude Code 按来源的 `cwd` 及现有路径映射识别普通项目；当前适配器没有可用的、已核实的全局标志，本次不凭空推断其存在。用户可在 Web 项目归属中将选定会话明确归入全局项目，CLI 提供等价的 `smm project assign-conversation <本机会话ID> --project-id <本机项目ID>`；全局项目可由 Web 创建，CLI 通过 `smm project ensure-global` 取得其 ID。该入口只修改 SMM 归属，不修改 Agent 源文件。缺少或冲突的归属在处理前保持待定，全部项目本机查询仍可找到它们。

本机会话 ID 来自显式本机搜索结果或 Web 会话详情，不能使用 Hub 会话 ID。CLI 归属命令默认返回受影响范围和确认标识，不执行变更；用户核对后增加 `--confirm <确认标识>` 提交。标识绑定会话归属、目标及规则版本，任一变化后须重新预览。

项目合并或路径映射导致会话转入另一个稳定项目时，须展示受影响范围和上传选择变化；不能因普通归属维护而静默把原禁止内容转成允许。会使允许范围扩大的归属操作先保留待确认状态，Web 与上述 CLI 归属操作通过明确确认后才可应用；确认须绑定所预览的范围和规则版本，过期则重新预览。全局与普通项目不能通过项目合并混成同一身份。已在 Hub 保存的副本不因这些操作自动撤回。

无论正文是否允许上传，都可登记项目显示名、类型、设备身份和稳定项目键。登记不携带本机路径、会话 ID、标题、消息列表、正文、摘要或可逆的内容片段；关联维护不要求先上传该项目任何会话。对话归属元数据只针对已获准发送且由 Hub 接收的记录发送，不通过元数据接口提前列出被禁止会话。

Hub 维护者通过既有 `smm-hub hub project list` 取得 Hub 项目 ID，用 `project link/unlink/links` 管理关联，不能拿本机整数 ID 直接代替 Hub ID。新设备项目登记应在后台自动完成；用户立刻查询时也可完成缺少的最小登记，不以先完成正文补传为条件。

### B4. 停止、在途请求与恢复上传

保存收紧规则成功后，本机不得再启动与新规则冲突的正文发送；已排队而未发出的任务按当前规则重新判断。在保存前已进入发送的请求列为在途，不能承诺召回已经发出的字节。

Hub 持久确认限制时，须把规则确认与正文归档在设备范围内串行判定：在确认之前完成提交的旧请求属于已接收历史；确认之后提交的旧版本、不带所需版本或违反限制的请求一律拒绝，不新增正文或改变已有正文。只有已持久确认后才返回对应规则版本，本机收到该确认后才显示“双方已生效”。

断线或确认响应丢失时，本机显示已停止、Hub 待确认；恢复连接先核对 Hub 当前规则及提交标识，再处理在途结果。快速执行“允许—停止—允许”等修改时，以最新有效意图和版本为准，过期响应不能覆盖较新保存的规则。明确拒绝的请求与接收结果未知的请求分别记录。

停止仅影响后续上传。Hub 已接收的副本继续可检索和读回，其他设备已经上传的同源副本也不受影响。本次不提供副本撤回或删除操作。

首次允许或重新允许后，自动补齐该项目对当前 Hub 尚未确认的全部已归档消息，包括停传期间的旧会话追加轮次和新会话。已经被确认的相同消息版本不重复存储；未知结果按稳定身份重试或核实，不能当作成功跳过。其他项目已推进的全局游标不得截断本项目历史。

单次失败不能让整个历史队列永久堵住其他允许项目；每轮工作量有界，下一轮继续，状态保持待补齐。本机导入、CLI/MCP/Web 查询和其他允许项目仍可使用。这里不承诺固定完成时间。

### B5. 在线联合查询与项目范围

CLI `smm search`、MCP `search_conversations` 和 Web 现有检索页采用相同语义。配置 Hub 后默认同时查询本机和 Hub；CLI `--local`、MCP `local=true` 和 Web“仅本机”明确关闭该次 Hub 请求。未配置 Hub 时按已有本机项目与直接关联规则查询。

在线按 A 查询时，Hub 解析 A 的稳定身份并返回 A 及直接一层关联的范围快照。两端都基于本次快照查询，不再各自扩展关联。例如 Hub 有 A—B、B—C，本机有 A—D，从 A 联合查询只覆盖 A、B；不会加入 C 或仅本机关联的 D。

本机只把快照中可按设备身份与稳定键精确映射到本机的项目纳入本机查询，不以名称匹配远程项目。Hub 中其他设备和 VibeInsight 项目由 Hub 提供；无法映射到本机的远端项目不是本机缺失错误。当前 A 及本机相应项目即使不上传，其本机对话仍参与。Hub 在查询期间关联发生变化时，本次仍用已取得的同一快照，下一次查询才采用新范围。

全部项目联合查询不需要按项目展开：本机所有可检索来源（包括归属待定），以及 Hub 所有可检索来源，均按各自正常规则参与。不支持上传的本机来源也不能被排除。当前会话默认排除、`include_current`、查询词有效性及 `limit` 范围继续沿用；同一来源的当前会话副本在两端都应排除。

两端各按本次 `limit=N` 正常返回至多 N 个会话候选（现有 N 为 1–50），不额外扩大召回。合并后的二次检索只处理这些候选及其已返回的完整命中消息；不会重新扫描两端完整档案。最终至多 N 条，去重或范围过滤后不足 N 时如实返回，不自动扩大检索补足。

### B6. 本机二次检索、去重和覆盖状态

二次检索使用同一查询的词项，在本机以去重后候选及其完整命中消息重新计算 BM25；两端原始分数不可直接比较、加权求和或以简单交替代替重排。详细判据见设计决策 D3。

只有来源、原始会话、原始消息身份及内容版本均可验证相同，才归并本机/Hub 或多设备副本。相同文本但不同会话、轮次或事件不因此合并，VibeInsight 与 Agent 副本也不能仅凭文本或相同显示会话号认作同源。保留所有有效来源引用；不同版本可作为同一来源会话内不同证据展示，不覆盖旧证据或冒充最新内容。

Web、CLI、MCP 都返回/展示查询范围、本机及 Hub 是否实际完成、实际项目集合、是否仅对候选重排，以及失败原因。正常在线使用 `archive_scope=combined`，明确本机或回退使用 `local`；结果逐条带真实档案归属，不能依据顶层 `archive_scope` 猜测每条来源。成功执行但零命中区别于该端未查询成功。

Hub 连接、身份或项目范围能力不可用时，按 A 查询只查询本机 A，不展开本机关联，也不改成所有项目；全部项目查询只返回本机全部项目，均说明 Hub 及关联范围未覆盖。在线仅本机查询继续按本机关联，不套用回退规则。Hub 恢复后下一次默认查询重新联合执行。

已经取得有效共同范围后，若只有 Hub 候选查询失败，本机可返回该快照对应的本机命中，并明确标为部分覆盖；若范围解析本身失败，则使用上一段的 A 本身回退，不能用陈旧快照宣称覆盖。若本机候选失败而 Hub 成功，返回 Hub 部分结果和本机失败；双方都失败则报错，不能当作完整零结果。候选所需完整内容无法取得时排除该候选并说明覆盖不完整，不把被截断内容作为完整输入重排。

### B7. 精确原文与旧引用

每条新命中提供可验证的 `reference`，包含或关联实际档案身份、原始会话/消息身份及版本、项目范围快照和可读取的消息范围。本机与 Hub 整数 ID 相同不能被当成同一对象。

CLI `smm read --reference <引用>`、MCP `read_conversation(reference=...)` 及 Web 的“读原文”使用该引用；原有整数会话参数在旧调用形式下继续可用。`reference` 与冲突的旧式定位参数同时提供时拒绝，不能以参数优先级静默读取另一条记录。引用内容及取得方式由搜索输出或页面直接提供，用户无需自行拼装。

本机命中直接读取本机原文；Hub 命中通过该 `hub_id`、会话及精确消息定位读取。保留同源副本引用可供明确选择，但一个档案不可用时不能只用另一个档案的同号 ID 自动代替。引用与内容版本不符、消息不存在或 Hub 已切换时给出准确错误。

新范围引用默认只读取命中及允许的同项目上下文，不因整段会话被多项目共享而读出范围外消息。读取长消息返回完整原文；搜索预览仍可按现有设置截断，但候选内容获取、评分和引用定位发生在预览截断之前。旧式引用保持原有读取语义；引用范围是新查询的正确性约束，不新增多用户授权模型。

### B8. 重启、恢复与版本兼容

普通服务重启自动读取持久规则及待确认任务，先完成身份/版本核对再发送正文，不要求用户重复选择。进程崩溃于任一发送或确认阶段，恢复后不能把未确认消息跳过；Hub 已提交但响应丢失时重试幂等。

受支持的恢复范围为：同一设备身份下恢复本机 SQLite 档案及配套 Hub 配置/策略状态；现有 Hub 升级失败自动恢复数据库；维护者停服务后通过有恢复标记的流程恢复 Hub 数据库。备份须为 SQLite 一致性备份，跨文件控制状态须来自同一备份集，操作入口应说明文件范围及恢复前停服务要求。

手动恢复前，本机使用 `smm upload prepare-restore`，Hub 使用 `smm-hub hub --state-dir <状态目录> prepare-restore`，输出须恢复的文件清单、不得回滚的恢复标记位置及当前设备/Hub 身份。状态目录取自现有 Hub 状态输出，须与实际服务一致。本机命令立即阻断正文发送，Hub 命令立即阻断正文接收；随后停止对应服务，按清单还原备份并重启。标记跨服务重启保留，不能随备份覆盖；恢复后先对账，再由 B1 的入口确认。现有升级失败自动恢复也须在还原前完成同等标记和阻断。

本机启动对账须识别旧备份的规则版本或未确认提交与 Hub 不一致：保持本机导入、查询可用，暂停正文并显示差异，由 B1 的 `reconcile` 明确处理。不能用旧备份中的允许规则自动覆盖 Hub 新限制。仅确认记录丢失但规则可验证一致时，可自动幂等重传，不能把旧扫描位置当作接收确认。

Hub 数据库恢复须使旧同步确认失效，并保留恢复前最新限制或进入等待对账状态；客户端重核对接收进度并补齐当前允许的缺失历史。数据库与配套控制状态一起恢复到更早版本时，也须通过恢复标记阻断自动正文接收，不能把两端表面一致视作安全继续。

任意绕过恢复流程的文件替换、克隆设备身份、同时回滚所有状态及恢复标记，不在自动识别承诺内；说明须明确这些操作需先停止同步并重新确认，不能声称任意手工拷贝均可检测。旧程序直接读写新策略数据库或降级运行不属于支持方式，应报告不兼容或拒绝正文，不得静默恢复旧上传行为。

## 边界与约束

- 首版正文上传仅覆盖现有 Codex、Claude Code 来源的已归档消息；不增加其他 Agent 上传适配器，不扩大文档或飞书上传范围。其他有效来源继续本机查询和原文读取。
- 全局项目提供明确归属能力；没有实际来源依据时，不承诺自动识别额外 Agent 的全局会话。归属未知与全局是两种状态。
- 保持现有单用户 Hub、HTTPS、凭证管理、对话归档、项目双向一层关联和 VibeInsight 自动同步。项目上传选择不传播给其他设备或关联项目，也不关闭 Hub 的 VibeInsight 拉取。
- 本机 CLI、MCP、Web 及其共用后台服务继续支持 macOS、Linux、Windows；macOS 还包括现有登录后启动服务，Linux、Windows 沿用现有按需/自行启动的本机服务，不新增本机系统服务安装承诺。
- Hub 继续支持 Linux systemd 用户服务、macOS 系统级 launchd 服务及配置运行账户、Windows LocalService，以及自行管理的 `serve-hub` 进程。策略确认、项目范围及读取接口须在这些运行方式成立。
- 联合排序及本机候选内容留在本机，不新增外部模型依赖。用户查询、最小项目身份和正常 Hub 读取请求可发送；禁止上传的本机候选不能以预览、摘要、评分输入、遥测或错误日志提交 Hub。
- 不承诺捕获来源没有产生可导入记录的历史原地修改；对已经进入本机档案的不同消息版本必须保持引用区别。源文件保持原样。
- 已确认的旧副本仍可跨设备检索和读取；新增停止上传入口必须说明它不能撤销已经发送或已保存的内容。
- 当前 0.4.0 的“在线只查 Hub”、Web“只查本机”和 Hub 失败时项目查询退到本机全部的行为，分别由 B5–B7 的新行为替换；其他既有本机入口保持兼容。

## 设计决策

### D1. 分离策略版本、接收确认与扫描进度

本机保存完整期望规则、修改序号、提交标识及对应目标；Hub 保存设备规则版本、规则摘要及已处理提交标识。策略变更采用基于已读版本的条件更新；版本冲突返回当前状态，不以“最后到达请求”覆盖。每批正文携带 Hub 身份、控制代次、已确认策略版本、记录项目稳定身份和幂等消息身份。

Hub 在同一提交边界核验当前限制并归档，规则确认与旧批次不能跨过该边界竞争成功。规则变化或项目归属变化后，排队任务须重新装配，不能只在生成队列时判断一次。旧请求失败也不能退回到不携带策略的旧上传接口重试。

消息接收账本按目标 Hub、设备、原始来源/会话/消息与内容版本记录；批次归档和对应确认一起持久化。扫描游标仅作为发现优化。0.4.0 游标不作为新账本的完整性证明，升级通过幂等核对或重放建立已确认状态。单批异常时不能确认未提交记录，混合项目批次不能因只接受其中一部分却推进整个批次。

有来源消息 ID 时沿用该 ID；仅有字节偏移的内建来源，沿用现有上传的时间、角色、内容及同类消息出现序号来核实身份，不能把本机字节位置当成 Hub 消息位置。内容版本包括实际角色与正文的摘要及对应来源时间；不同出现序号仍是不同轮次。无法证实等价时保持不同记录，不强行跨设备去重。

Hub 的控制状态具有独立恢复代次；正常重启不改变已确认规则。受支持的 Hub 恢复必须先持久登记恢复事件并改变代次，才允许服务接收正文；该标记不能随被恢复的归档数据库自动回滚。控制状态缺失时关闭正文接收，直至维护者明确恢复/确认；不能自动初始化为允许。具体持久化布局留给计划，但以上提交顺序与恢复判据不能省略。

### D2. 协议能力与渐进升级

沿用现有 Hub 身份及能力协商，增加上传策略、共同范围快照、候选完整内容和范围引用能力。新本机连接缺少策略能力的旧 Hub 时不发送正文；可查询其已存档案，不能把“不支持规则”当作默认允许。缺少共同范围能力时，项目请求按 A 本机范围降级并说明原因，不能向旧 Hub 发送无范围请求后冒充项目命中；全项目查询可使用兼容结果，内容或来源不够重排的候选须按 B6 标示缺失。

新 Hub 对尚未采用新策略的旧设备保留原有兼容路径，不为其他设备隐式设定规则。某设备一旦采用新策略，Hub 必须持久拒绝该设备的旧式正文请求，避免旧程序或旧任务绕过已经确认的限制。旧客户端的无项目检索及旧原文读取继续可用。新本机不得借重新登记同名设备、改变 URL 或元数据接口绕过上述约束。

协议输入允许旧查询字段继续存在；`reference` 和逐条档案归属为增量字段。顶层 `combined` 是本次新增值，CLI/MCP/Web 及检索 Skill 必须同时理解；不能把联合结果交给仍仅支持单一档案的读取逻辑。

### D3. 候选重排及原文定位

候选单位沿用会话结果。先用可验证原始消息身份及版本归并重复证据，同一来源会话内保留不同轮次/版本及其原始顺序；未知同源关系保持分开。相同消息的多个设备副本只计一份内容、一份词频，不因增加副本而改变得分；原文引用可列出多个实际来源。

对每个归并后会话，将返回的完整命中消息按稳定原始顺序组成评分文档，标题、设备名、上传状态和外部摘要不参与评分。同一消息只出现一次。复用现有中英文词项切分，在本次候选集合计算 BM25，参数 `k1=1.2`、`b=0.75`；文档频率、平均长度仅来自去重后的候选文档。分数相同按最新命中消息时间降序、稳定原始身份字典序排序，缺失时间视为早于有效时间，不以本机/Hub 优先打破平局。

查询词项先去重。设候选文档数为 M，含词项 t 的文档数为 df，`idf(t)=ln(1+(M-df+0.5)/(df+0.5))`；对查询中的每个词项按上述参数计算标准 BM25 贡献后求和。无候选时直接返回空集合，不使用端点原分数兜底；无匹配词的候选不进入最终命中。

端点内部正常召回及命中消息选择不改变。为避免预览改变得分，内部返回或按本次范围引用取得候选的完整命中消息，最后才做 600 字等展示压缩；额外内容读取不能变成第二轮扩大召回。精确复核以归并后候选、完整消息、最终分数及引用为依据，不能只证明两边都有结果就视为完成排序。

### D4. 环境风险决定验收范围

本次变化不新增 `psql`、OCR 或外部模型依赖。主要跨平台风险来自后台/前台进程共用策略、原子持久化和锁、路径与项目身份、实际 Hub 服务账户访问状态目录，以及进程退出后的恢复。浏览器展示和 MCP 序列化还可能丢失逐条来源与范围引用，因此三个入口都须完成实际检索后读取，不能以 API 单测代替。

协议排序与竞态可由可复现的共用测试覆盖；实际服务身份、已安装包路径、进程重启和浏览器操作分别需要相应环境证据。无需所有本机与 Hub 系统作笛卡尔积组合；具体充分覆盖在下表限定，不留到计划再决定。

### A1. 入口、参数与默认行为（B1–B2）

在 E1 各平台，从 README 的主使用路径找到说明，再从已安装 CLI 帮助和 Web 配置选择规则。新连接未选择时执行后台及手动同步：本机有历史，Hub 可查询和登记项目，但未收到标题、正文或摘要。四模式对普通 A、普通 B、全局 G 及新增项目的判断正确；空名单和非法输入符合 B1，错误输入不改变有效状态。

相同设备升级后，在可验证同一 Hub 的条件下显示原“全部”选择并继续原允许来源；换成另一个 Hub 身份时不自动上传。换 URL/凭证但验证为同一 Hub 保留选择。`status`、Web 与持久状态一致，来源开关及全局暂停未被规则修改。全部不上传时仍可查询 Hub。

### A2. 保存、暂停与在途停止（B2、B4；D1）

各 E1 平台在服务自动同步中保存禁止 A 的规则后，新加入 A 的记录不再开始发送，B 可继续；显式同步和失败重试不绕过。暂停时修改上传选择不恢复自动导入或正文上传；恢复全局同步后仍遵守新规则。

共用竞态测试至少覆盖：旧请求在限制确认前提交、限制确认后才尝试提交、已提交但响应丢失、Hub 确认丢失、本机保存后进程崩溃、两入口同时保存、允许/停止/允许请求及响应乱序。结果符合 B4：确认前历史可保留，确认后无违规提交，未知不报成功，旧响应不覆盖最新状态。每个 E3/E4 实际 Hub 至少执行一次“确认停止后重放旧批次被拒绝且数据库未增加正文”，并在服务重启后复验限制仍有效。

### A3. 项目、全局归属与最小登记（B3）

E1 各平台通过 Web 与 CLI 建立或取得 G、明确会话归属，重复操作不生成第二个 G；缺失 `cwd` 的记录不会自动进 G。按 A 查询不包含 G，全部查询可找到 G 和待定记录；显式关联 A—G 后才在 A 范围纳入 G。归属未明确时即使 `all` 也不发送正文。

E3/E4 中，不上传的 A 仅登记最小项目资料后，维护者能在 Hub CLI 识别并关联；对发送请求及 Hub 记录检查，不出现未许可会话 ID、标题、路径、正文或摘要。同名不同设备项目不合并，显示名修改保留稳定身份、规则与关联。项目合并、路径映射或会话转移引起允许范围扩大时必须先确认范围，过期预览不能应用，不能静默继承允许。

### A4. 历史补齐、幂等与公平推进（B4；D1）

各 E1 平台以 A 禁止、B 允许开始，B 的进度已越过 A 的历史；A 停传期间新增会话及旧会话轮次。允许 A 后，A 的全部未确认历史和随后新内容都到达 Hub，原会话身份与来源顺序保留，检索与精确原文读取均成功。重复同步不增加相同消息，已有同源副本也不重复。

共用故障测试覆盖整批失败、部分响应无效、归档成功但确认丢失、扫描后跳过、重启、单个项目反复失败及旧账本缺失；无未提交记录被确认或永久跳过。大量历史补齐时，在其完成前本机能继续导入/检索，其他允许项目至少有新记录推进；不得只在总队列清空后才证明可用。E3/E4 在实际服务身份下确认和读回上述补传结果。

### A5. 规则隔离与副本保留（B2–B4；D2）

至少在一个实际 Hub 完成：设备甲禁止 A，甲已接收旧副本仍可查和读，新增禁止消息未到达；甲的关联项目 B、设备乙以及 Hub 的 VibeInsight 状态不被该操作关闭。VibeInsight 的行为以现有自动测试回归确认，不要求为本次修改连接真实 staging 或向来源造数。

每个 E3/E4 在策略确认后既拒绝该设备旧式正文请求，也继续允许按当前新规则提交，项目登记不能绕过限制。未迁移的其他旧设备保留兼容行为。正文已接收后关闭上传不删除旧引用。

### A6. 三入口联合范围与候选（B5–B6）

在 E1 的每个平台，以本机 A 的未上传命中、Hub 直接关联 B 的命中、二层 C 及仅本机关联 D 的干扰命中准备数据。CLI、真实 MCP、Web 分别按 A 查询：结果来自本机 A 与 Hub 的 A/B，显示同一快照，排除 C/D；结果中的本机未上传内容确实参与候选与最终重排。三入口分别读回至少一条本机、另一设备和 VibeInsight 来源原文，可使用隔离归档中的合成来源数据。

显式仅本机按 A 查询恢复本机 A/D 规则，不请求 Hub；全部项目查询包含本机普通、全局、待定及一个不支持上传的已归档来源，也包含 Hub 远端记录。排除当前会话同时作用于同源副本。请求 N 时，两端各正常至多 N 个候选，最终至多 N，去重不足不偷偷扩召回。

每个 E3/E4 实际 Hub 的项目范围响应与同一次候选/读取一致；共用并发测试改变查询中的关联，证明一次查询不混用两个范围。Hub 返回的远端同名项目不被本机名称映射放大。

### A7. 重排、去重与禁止内容外发（B6；D3）

共用测试用已知候选文本独立计算 BM25，验证分数、稳定平局顺序及最终数量；输入改变原端分数不影响重算结果。加入可验证同源同版本副本不增加名额、词频或分数；相同文本的另一轮、另一会话及不同版本不被误删。不同版本的原文引用准确。

每个 E1 平台在包含本机禁止上传候选的真实联合查询中，检查 Hub 收到的正常/失败载荷和日志：仅有允许的用户查询、最小项目资料及范围内远端读取，不出现本机禁止正文、摘要或预览。搜索短预览与完整展示用同一候选输入得出同样分数和顺序；关键词位于长消息预览之外时仍有有效命中并能完整读回。

### A8. 引用、消息范围与冲突（B7）

E1 三入口分别在本机/Hub 整数会话 ID 相同但正文不同的条件下读取新命中，均回到正确档案；Hub 不可达时不读本机同号替代。E3/E4 通过新引用读取共享会话的范围内消息，不带出范围外项目正文。

共用测试覆盖精确消息、重复位置、不同内容版本、被删除消息、Hub 身份切换、引用篡改/过期及 `reference` 与旧参数冲突；分别正确读取或明确失败。升级前 CLI/MCP/Web 旧引用及旧式读取仍可用。新引用不能通过丢弃范围字段扩大读取。

### A9. 回退、部分失败与恢复（B5–B6）

每个 E1 平台的 CLI/MCP/Web 均从已连接 Hub 的状态开始，断开 Hub 后按 A 查询只得到本机 A，排除本机 D，说明未查 Hub/关联；全部项目查询得到本机所有项目并说明原因。恢复连接后默认查询再次联合，显式本机不变；本机/Hub 成功零命中与不可用明确不同。

共用测试分别使范围解析失败、取得快照后 Hub 查询失败、本机查询失败、候选全文读取失败以及两端都失败，得到 B6 指定的范围和状态，不扩大范围、不宣称完整零结果。无效查询参数直接报参数错误，不能伪装 Hub 故障扩大检索。

### A10. 新旧组合与迁移（B8；D1–D2）

E5 的真实包组合至少覆盖：新本机/新 Hub、新本机/0.4.0 Hub、0.4.0 本机/新 Hub。新本机遇旧 Hub 不传正文，项目查询不降成 Hub 全局；兼容全局查询要如实报告能力限制。旧本机在未迁移设备上继续旧调用；同一设备已启用新策略后旧式上传被 Hub 拒绝，旧式查询和读取仍可用。

升级已有档案且保存了旧游标时，旧历史不遗漏，显示名、项目键、旧关系及引用保留；新账本建立过程不重复消息。旧程序/降级对新策略状态不得静默恢复正文发送，说明提供支持的版本组合及处理路径。

### A11. 平台生命周期与恢复（B8；D1、D4）

E1–E4 每个指定运行环境从“已确认停止 A、旧副本存在、停传期新增内容”开始，停止实际服务并用原状态目录重启：不重新配置规则，A 仍禁止，本机可检索新增，旧 Hub 原文可读；明确允许后自动补齐全部缺失，Hub 检索读回成功，再同步不重复。状态路径、服务身份及版本须可复核。

E5 另外覆盖：本机数据库/配套状态回到旧允许备份而 Hub 已确认停止；Hub 数据库回到缺少最近消息及限制的旧备份；Hub 配套状态也恢复到旧版本但保留受支持流程恢复标记；现有 Hub 升级失败自动恢复。手动场景均从 `prepare-restore` 开始，经停服务、按清单恢复、重启与对账完成。按 B8 关闭不确定正文发送/接收，显示真实差异。通过 `reconcile` 处理后仅补齐当前允许内容，旧允许不能静默覆盖新限制；丢失进度可重传，已提交副本不重复。

恢复确认前发生再次修改时，旧 `--expected-hub-revision` 被拒绝；查看差异本身不改变规则。所有支持恢复入口说明一致性备份范围、停服务条件及不支持的任意手工克隆边界。
