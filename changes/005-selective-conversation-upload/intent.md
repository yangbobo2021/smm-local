# 意图：按项目控制本机对话上传，并联合检索本机与汇总端

状态：意图已确认。维护者已采用本轮六项建议，以下按已确认约束记录。

父意图：[项目知识检索与内容上传控制](../004-project-knowledge/intent.md)。相关子项：[Hub 文档检索与同步](../007-hub-document-search/intent.md)。进度见[父目录导航](../004-project-knowledge/README.md)。

## 现有问题

SMM 0.4.0 在本机配置并连通 Hub 后，会在同步中上传当前可汇总的 Agent 对话。当前公开配置没有提供“不上传本机对话但继续查询 Hub”及“只上传某些本机项目”的独立选择。全局暂停还会影响本机自动同步，不能表达用户仅限制对话上传的目标。

有些 Agent 支持不属于普通项目的全局对话。维护者已明确将它们归入与普通项目同级的“全局项目”，因此上传和项目检索不能仅按目录或有无项目字段推断。

当前默认在线检索主要返回 Hub 的结果，本机内容只在明确本机查询或回退时直接参与。控制上传后，未上传内容也必须参与正常查询，需要把本机与 Hub 各自正常检索返回的集合，合并后按同一查询重新检索排序。

## 受影响的用户

已配置或准备配置 Hub，需要控制本机对话上传范围，同时查找本机与汇总端资料的使用者及其 Agent。也包括负责登记项目、配置关联和理解所收内容范围的 Hub 维护者。

## 期望结果

- 用户可选择全部不上传本机对话，或按项目决定上传范围；Agent 的全局对话进入“全局项目”，使用与普通项目相同层级的选择和检索方式。
- 按 A 项目查询不会因“全局”这个名称而自动带入全局项目。全局项目遵循与普通项目相同的明确归属及关联规则。
- 对话的上传选择不影响本机归档和本机查询。已连接 Hub 的默认查询同时检索本机和 Hub，本机候选不因已上传、未上传或不具备上传能力而被排除。
- 两端分别正常检索，返回的两个结果集合在本机合并，并按原查询重新检索排序；最终结果保留可读取的准确原文引用，用户能理解实际覆盖的资料范围。
- 不上传对话的 A 仍可在 Hub 登记名称及识别它所必需的项目身份资料，由维护者在 Hub 配置关联，并据此检索关联项目。
- 首次允许或重新允许项目上传时，补齐本机尚未被该 Hub 确认接收的全部历史，包括停传期间新增的内容，并继续处理后续新增；已经确认的同源记录不重复，不因其他项目已推进进度而漏掉历史。
- 策略在重启、断线、快速连续修改和恢复备份时有可理解的有效状态。旧任务或旧状态不能静默覆盖当前有效规则，尤其不能用旧允许状态重新开启已限制范围；项目显示名变化不使既有选择失效。
- 用户可以区分本机保存规则、Hub 确认规则、已发出但接收结果尚未确定，以及 Hub 已存副本等状态；停止后续上传不删除已被 Hub 接收的内容。

## 范围与约束

- 本项控制当前本机向所配置 Hub 上传 Agent 对话的范围，不自动改变其他设备或关联项目的上传选择。首版上传沿用当前可汇总的 Codex、Claude Code 来源；其他已归档来源继续参与本机检索，不因未具备上传能力而排除。Hub 从 VibeInsight 拉取对话仍按已有规则运行。
- 正文上传前应能确定适用的项目和有效选择，不能因为项目归属尚未登记或识别失败而绕过限制。后台同步、明确触发的同步、历史补传和失败重试均应遵守上传选择；上传开关不隐式恢复全局暂停或改变来源启用状态。
- “全局项目”是对话归属；“全部项目检索”是不限定单个项目的查询范围。两者分别表达。全部项目检索包括范围内的普通项目、全局项目和仍待明确归属的本机记录；归属不足的记录不能仅凭缺少字段被认定为全局会话。
- 项目按稳定身份登记，同名项目不自动合并，名称调整不重置关联和上传选择；全局项目也适用这些规则。具体身份字段在 SPEC 中限定，不因项目登记而自动提交对话标题、正文或摘要。
- 联合排序在本机完成。正常 Hub 检索请求可携带用户查询和必要项目资料，禁止上传的本机候选正文不能因排序而作为预览、摘要或其他候选内容被隐式提交 Hub。
- 二次检索的输入是两端正常检索已返回的候选集合，不预先另设扩大召回目标，也不声称已重新扫描两端完整档案。最终数量遵循本次查询要求，实际候选不足时如实返回。
- 去重只归并可确认同源、同版本的副本；不同轮次或版本的有效命中保留区别。副本不应占用重复结果名额或因重复出现取得额外副本权重，上传状态不作为本地内容参与或相关性降低的依据。
- 原文读取保留真实来源和原始身份，不能用另一档案的同号记录替代。长消息不能因只处理被截断预览而丢掉有效命中；需要读取的内容仍受本次查询范围约束。
- 保留显式仅本机查询和现有对话原文引用。在线项目联合查询以 Hub 配置的直接一层关联为共同范围，本机查询对应的本机项目，双方不各自再次扩大成另一套关联。显式仅本机查询继续遵循本机关联。
- 未配置 Hub 时继续正常本机检索。Hub 不可用时，按 A 查询只返回本机 A，并说明 Hub 与关联范围未覆盖；全部项目查询返回本机全部项目结果并说明原因。这明确替换 0.4.0 项目查询在 Hub 失败时回退到本机全部项目的行为，不假设本机已持有 Hub 关联。历史补传期间，本机归档与查询仍可使用，其他允许项目的上传也应能继续推进。
- 上传应以 Hub 的实际确认区分成功、未确认和未传；扫描过、因规则跳过或尝试发送不代表已上传。重试或恢复不能把未确认记录错误跳过，也不能用旧允许状态悄然重新开启已经限制的范围。通过受支持的备份恢复流程发现两端状态无法确认一致时，应暂停正文发送并给出处理入口；可支持的恢复路径、协调方式及版本兼容进入 SPEC。
- 本项的停止动作仅控制后续正文上传。确认生效前已被 Hub 接收的内容继续保留、检索和原文读取；副本撤回是另行明确的操作，不作为关闭上传的自动行为。文档上传由 007 明确，飞书上传不因本项而自动启用；后续来源的联合检索沿用父意图的共同边界。

- 保存停止规则后，本机停止启动新的相关上传，未发送任务按当前规则处理；已经进入发送过程的请求显示为在途待确认。Hub 确认新限制后，才显示双方已生效；随后到达的旧请求和旧规则重试不能绕过限制。离线时显示本机已停止、Hub 待确认。
- 新连接在明确选择前允许检索及必要项目登记，不上传正文；已有配置在同一 Hub 上升级时保留既有已允许来源与上传模式并明确展示。目标 Hub 身份改变时重新确认选择。
- 上传选择提供全部、仅指定、排除指定、全部不上传四种可理解的模式。新发现的普通项目和全局项目按已选模式处理；归属不足的记录保留本机并显示待处理，不自动继承一个允许上传的项目身份。
- 本机 Web 和 CLI 提供上传选择及生效状态；CLI、MCP 和现有 Web 检索均体现一致的联合查询与显式本机语义。Hub 项目关联继续由维护者集中配置。该入口范围仅确认本子意图，其他子项分别确认。
- 全局项目作为可复用的归属能力；现有来源怎样表达全局会话，需在 SPEC 阶段用实际记录核实。额外 Agent 的 Hub 上传需另行明确来源名单、项目归属及原文读取支持，不能仅增加名为“全局”的项目就声称支持完成。
