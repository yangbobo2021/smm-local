## 现有问题

SMM 已能归档本机 Agent 对话，连接 Hub 后上传可汇总的记录，并检索其他设备和 VibeInsight 的关联项目对话。当前公开配置没有把“连接 Hub 检索”和“是否上传某个本机项目的对话”分别交给用户选择。

用户处理一个项目的问题时，依据还可能保存在本机或汇总端的文档、飞书聊天、聊天附件和飞书文档中。现有公开检索与原文读取路径以对话为对象，缺少这些资料的完整接入、内容定位和关联阅读路径。用户需要分别寻找资料，再自行拼接讨论背景与最终约定。

这次扩展同时涉及上传选择、文档检索、文件格式和飞书内容理解。维护者已同意拆成六个子意图，分别确认范围、交付和验收。

## 受影响的用户

- 在本机使用 SMM 或调用 SMM 的 Agent，希望按项目取得相关原始依据的使用者。
- 希望控制哪些本机对话进入 Hub，同时继续使用汇总检索的使用者。
- 管理 Hub 文档来源、同步和项目关系的汇总端维护者。
- 希望检索本人获授权读取的飞书聊天及相关材料的使用者。

## 期望结果

- 用户可以选择本机对话的上传范围，本机归档、上传选择和使用 Hub 检索分别有明确含义。
- Agent 全局对话归入与普通项目同级的全局项目，不自动参与其他项目的查询；查询全部项目与查询全局项目分别表达。
- 用户可按项目找到已纳入范围的对话、文档和飞书消息，了解命中的来源、时间或版本，并打开支撑判断的原内容。
- 联合检索分别取得本机与 Hub 的正常查询结果，再在本机对合并候选按原查询重新检索排序；本机内容是否上传不影响其在查询范围内参与召回。
- 文档与飞书资料的更新、不可读取或处理不完整具有可理解的状态，用户能判断本次检索实际覆盖了什么。
- 对同一项目的问题，Agent 能取得相关讨论、实现记录及文档约定，保留各自的出处，供用户核对。
- 六个子意图分别提供可独立使用的能力；整体完成情况可以从各项交付结果和跨来源使用结果中追溯。

## 范围与约束

- 六项范围分别为本机对话上传选择、本机文档、Hub文档、常用文档格式、飞书聊天历史、飞书长对话及关联材料，具体见各子意图。008首版范围收窄为docx/xlsx/PDF文字与表格，独立图片和图像语义理解留给后续确认，不当作本次已交付。
- 共同保留现有对话归档、检索和原文读取的使用路径；沿用当前单用户使用方式及已确认的项目身份、Hub 直接一层关联规则。
- 全局项目适用普通项目的独立归属、上传选择和明确关联规则，不因“全局”名称默认加入 A 项目范围。同名项目保留来源身份，不自动合并。
- 不上传本机正文的项目仍可在 Hub 登记名称及必要稳定身份，并由 Hub 配置关联。项目登记与对话内容上传分别表达。
- 默认联合查询在本机完成合并与二次检索排序，不能借排序隐式上传应留在本机的候选正文或摘要。保留同源命中、版本和原文定位的区别，不以简单拼接或错用另一档案的数字 ID 代替。
- 005 首先交付对话的联合检索；在线以 Hub 的直接一层关联为共同范围。Hub 不可用时，项目查询只返回本机所请求的项目，全部项目查询返回本机全部项目，并说明未覆盖范围；显式仅本机查询继续遵循本机关联。文档和飞书在各自范围确认后接入相同共同语义，不因此自动取得新的上传授权。
- 资料绑定多个项目，与项目之间建立关联分别表达。共享一份资料本身不自动扩大两个项目全部内容的检索范围。
- 本机对话上传策略的范围是本机到 Hub；本机先停止新的相关上传，Hub 确认后标记双方生效，旧副本保留，重新允许后补齐全部未确认历史。新连接默认不传正文，已有同一 Hub 配置保留既有已允许来源与模式。完整约束见已确认的 005。文档的上传选择由相应子意图明确，飞书相关子意图首先覆盖本机端。
- 文档项目由创建端负责管理与解析处理。本机和Hub对各自新建项目均具备完整处理/索引流程；本机项目获准同步时同步原文件及本机处理结果，Hub仅校验接收并直接建索引，不重新解析、识别或调用模型分析。文档更新、重试与重新分析仍由创建端完成，具体见008已确认边界。008首版不接入外部模型/识别服务，必要的PDF OCR由项目创建端本地组件完成；不因需要OCR而开放独立图片支持。
- 新资料须由用户或维护者明确纳入可读取的范围。检索命中、摘要或内容解释应能追溯到原始来源；具体版本保留和原文不可用时的行为留给相关子意图确认。
- 新能力在现有受支持平台的适用范围，以及需要验证的入口和运行方式，在各子 SPEC 中明确。不得把某一平台的结果直接当作其他平台的实测。
- 本阶段只起草意图。接口、数据结构和验收条件进入 SPEC，改动位置和实施步骤进入计划；当前草稿不代表功能已实现或验收通过。

## 006的授权定稿边界（2026-11-22）

本机文档先以独立、明确的仅本机CLI/MCP/Web入口交付，CLI/Web管理来源及手动刷新，MCP只读检索/读取。文档来源可绑定零/一/多个普通或全局项目，零绑定仅参加全部文档查询；共享来源不创建项目关联。这些决定仅回答共同待确认问题中006涉及的部分，不确定007的上传/联合文档协议或008/010的外部内容处理方式。

## 007的已确认边界（2026-11-23）

同时支持本机明确选择上传的文档和 Hub 自己管理的文件/目录，按本机文档项目独立选择同步、默认关闭，不继承对话授权。暂停保留 Hub 已有快照可查；来源移除或明确刷新发现文件删除/失效时撤回相应资格，离线明确显示尚待确认。不同设备文件保留各自身份，同设备重叠来源按006合并；不凭相同字节跨设备合并。具体契约及验收进入007 SPEC，不扩展008的格式或外部模型处理。

## 008的已确认处理责任（2026-11-24）

维护者明确，本机和Hub均可创建项目、上传文件，并对各自创建的项目提供完整文件处理及索引流程；“哪里的项目哪里负责解析处理”。本机文档项目获准同步时，原文档及本机处理后的结果一起同步到Hub；Hub直接消费这些结果建索引，不重新解析、识别或做模型分析。原件/处理结果/定位及处理状态须保持对应，更新和重处理仍由项目创建端负责。

该决定明确008的执行端及原件同步范围；维护者随后确认下述首版内容边界。009/010的飞书资料读取、外发与同步授权仍分别确认。详见[008意图](../008-document-format-support/intent.md#已确认的处理责任2026-11-24)。


## 008的已确认首版范围（2026-11-24）

- Word/Excel采用.docx/.xlsx，检索已有单元格值和公式并标注隐藏区域；暂不支持.doc/.xls、宏执行、公式重算或密码文件解密。
- PDF支持文字和表格，优先直接解析可取得的文字，必要时允许在项目创建端以本地OCR提取文字；保留页/内容定位、处理来源及不完整状态，不把OCR文本直接等同于完整表格结构。
- 暂不支持独立图片或文档插图/图表的图像语义理解。PDF内扫描内容的文字识别仍属PDF范围，不因此增加图片入口。
- 暂不接入或调用外部模型/识别服务；本机与Hub项目各在创建端完成解析及必要PDF OCR。同步原文件及处理结果后，Hub直接建索引，不重新解析、识别或模型分析。

具体提取/OCR质量与适用范围、定位、文件及工作量限制、组件/平台验收由008 SPEC定义。图片相关的后续目标仍保留在父意图和010草稿，不声称由008首版完成。
