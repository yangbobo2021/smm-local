## R1：实际 Web 验证尚未覆盖旧页面提交的目标与代次绑定

位置：PLAN 第49行 `TC-007-policy-choice`、第66行用户路径项及第83–88行 E1 步骤；对应 SPEC B2、A1 和已保留的 SPEC v3 目标绑定复审。

PLAN 第49行将旧 G、旧 HID 且新目标 G 恰相同及并发提交的拒绝分配给“公共 CLI/API”，但对真实 Web 仅明确“另由 E1/用户路径项核表单显示版本”。E1 第2步确有真实表单允许/同步，第3–5步有生命周期/重启；用户路径项有实际导航和必要输入核对。这些都没有安排：在另一入口已改变选择或目标后，通过仍打开的旧 Web 页面实际提交，并检查其携带的是页面原显示的 HID/G 及拒绝后的完整新状态。

影响：后端 CAS 正确仍不能独立证明浏览器遵守“提交同时绑定页面显示的 Hub 身份和 generation”。例如 Web 渲染 H1/g0 正确，但点击时先重新获取最新 H1/g1，再把旧页面选择与 g1 发送；API 的过期 g0 负例、Web 正常操作和显示值检查都可通过，旧页面却能覆盖另一入口的新选择。类似地，目标切换到 H2/g0 后若提交时改取 H2，也能把 H1 页面上的决定授权给新目标。这直接违反 B2/A1，不是新增产品要求。

最小修订：在已有真实 Web 人工 TC 中分配这两组动作，无需增加 TC 总数，也无需三个系统重复所有故障组合：

1. 页面保留 H1/gN 与原选择；另一页面或 CLI 保存不同选择并推进代次；实际点击旧页面的允许/暂停。请求仍绑定旧页面的 H1/gN，拒绝可见，最新选择、代次及任务完整状态保持不变。
2. 页面保留 H1/gN；将目标切换为独立 H2，刻意令其当前 generation 同为 N；实际提交旧页面。请求不得改绑 H2，提交拒绝且 H2 的默认/最新选择与待办完整状态不变。

分别保留动作前可见页面、实际请求/响应与独立完整预期、拒绝后关键 PNG 和 trace，并明确归属一个既有人工 TC。CLI/API 已有负例继续保留；PLAN 第23行的正确实现承诺也继续保留。修订后可独立判定 Web 绑定行为，而不只证明后端能拒绝人为构造的旧值。
