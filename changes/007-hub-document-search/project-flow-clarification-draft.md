# 007 项目文档主路径补充草稿

来源：2026-11-23当前用户补充，以及[只读路径核对](reviews/project-flow-assessment-v1.md)。原话：

> 文档处理的核心是验证检索确实可以检索到对应文档。文档也需要按项目来组织，所以对应也就需要新建项目，上传文档等。
>
> 这个是补充信息，避免对文档检索理解有误。对话项目与文档项目可以相互关联。

本稿尚未进入已确认SPEC/PLAN；不代表产品已实现，也不把尚未回答的“网页直接上传文件”写成已确认。

## 明确的主路径

验收从用户任务组织：新建可独立存在的文档用途项目 → 纳入/上传文档并确认该项目归属 → 按该项目检索确实命中正确文档 → 沿精确引用读回该文档原文。不能只证明传输成功、来源保存或有若干索引记录。

“文档项目”“对话项目”表示项目承载的内容用途，不强制新增互斥项目类型；一个项目也可同时组织两类资料。无对话的项目同样可以建立并绑定文档。已有普通/全局身份、显示名和稳定键的边界保留。

独立构造只含对话的C和只含文档的D，建立双向直接关联；从C查文档须命中D的正确文件，从D查对话须命中C的准确会话/轮次。C-D-E时从C不含E，未关联负控项目、全局项目和同名项目不混入。分别覆盖Local创建的D与Hub自有D，不因底层有关系记录就声称用户能完成反向检索。

## 需要补进SPEC的公共入口

- 保留当前`--project-id`/`project_id`表示本机项目ID的语义；增加明确、互斥的Hub项目选择器（建议CLI `--hub-project-id`、API/MCP `hub_project_id`），用于文档及对话查询。Web将本机与Hub项目带来源标识显示，不把两端同号ID混用。
- 增加用户可取得Hub项目ID的列表入口（建议`smm projects --hub`、MCP `list_projects(include_hub=true)`及Web查询选项），区分Hub自有、各设备及VibeInsight来源。同名项目保留身份。
- Hub项目作为根时，两端查询同一签名直接一层范围；Local只映射当前设备/档案对应的项目。Hub不可用时，不能把Hub ID当Local ID或凭同名猜范围；返回未覆盖说明，不查询不明本机项目。显式仅本机查询须使用本机ID。
- Hub自有D也须从公共对话入口查到关联C；不能只给Hub CLI文档查询而无反向路径。新增可选选择器保持旧参数和原有调用兼容，不把文档内容伪装为对话。

## 需要补进PLAN的证据

在既有项目范围/候选/回退/原文TC内分别加入上述C/D完整集合、文件身份/正文与会话身份/原轮次，Hub根ID与同号Local负控、互斥输入及离线不猜范围。真实使用路径和至少一组已要求的Web/stdio/跨机验收以项目为起点，体现创建、纳入/上传、命中与原文；不是只在内部API构造关系。
