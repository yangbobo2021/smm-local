# SMM 历史对话效用对照：公开数据与真实项目预检

日期：2026-10-29。状态：公开数据与真实项目结果均已核对。本文是小规模产品效用实验，**不是**三位同事、60 题的交付验收，也不证明普遍优于同类产品。

**最重要的真实项目结果：**在当前 SMM 项目的一段 2,373 条消息的真实长对话上，原始文件组 **7/8**、SMM **7/8**、第三方工具 **5/8**。SMM 与原始文件各有一题独赢：SMM 找到目录重组的后期修订；原始文件找到规模增大后的最终检索方向。SMM 在这批题上能工作，但还没有证明比直接搜索原始记录更准确。

## 测试到底比较什么

同一个 Codex Agent 使用 GPT-6 Luna、high 档，面对相同的历史对话与问题。三组分别为：仅用隔离的原始会话文件；额外启用 SMM MCP/Skill；额外启用开源 [Agent Session Search](https://github.com/benvenker/agent-session-search) 的官方 MCP。主指标是**答案的全部要点正确、能由题目发生时间之前的原始消息支持，并有有效出处**。找到一段对话、引用了官方来源 ID、本身都不算答对。

公开数据来自 LongMemEval-S cleaned：12 个 SHA 规则抽取的问题、605 段真实基准对话、6,083 条消息；1 题流程试跑不计分，1 题的官方参考信息发生在提问之后，时间上不成立，保留原始结果但从主口径排除。正式有效分母为 **10 题**。问题原文在导入语料中逐题检查为零次出现。所有组都面对同一来源、原问题、项目范围、240 秒限制，并要求引用历史出处。原始收据与评分规则留在本机 `/Users/boboyang/work/smm-utility-private`；正式运行前冻结了题目、正确答案、来源与评分口径。

版本固定为 SMM Git `2209d91`、Agent Session Search `0.9.1`、`fff-mcp 0.9.6`、Codex CLI `0.162.0-alpha.17.2`。一次运行只给一个模型调用实例，不对答错题后验改写问题或参考答案。

第三方 MCP 首轮在 Codex 的只读/不审批模式下被拦截，因此该轮不能算第三方工具结果。保留失败收据后，只对第三方组使用可让其官方 MCP 正常工作的 CLI 运行标志重跑；11 道正式题的 MCP 搜索均实际成功，参数中未发现答案文件、测试标签或互联网访问。**CLI 执行标志因此不是完全一致**，比较只限这套可工作的配置。Crispy Recall 的本地依赖安装未完成，未评分，也不把它记为失败。

## 真实项目对照

实际来源是当前 SMM 项目截至 2026-10-29 00:40 UTC 的一段真实长对话、**2,373 条可见消息**。8 道问题在运行前选定，覆盖首版范围、项目关联、长对话命中展示、目录重组、检索责任、BM25 边界、图谱合并、产品过滤。它们是人工挑选的真实后续问题，**并非随机盲测**。只有一段对话，因此只评价是否定位到正确**消息位置**并据此回答，不报告毫无区分度的“Top1 会话命中”。原文与完整 Agent 轨迹仅留本机 `/Users/boboyang/work/smm-utility-real-private`；本报告只展示汇总和必要的改写例子。

首次预检发现隔离档案路径提示不足；第二次预检发现符号链接使普通 `find` 不进入目录。这两次结果原样保留，但**不进入正式分数**。正式对照中，各组使用内容 SHA-256 完全一致的物理档案副本、相同的目录位置提示、相同的八题；第三方 MCP 单独使用已核验的运行标志。正式 24 份收据均为成功结束，未发现被拦截的工具调用、访问题目/标签文件或互联网的调用。SMM 组 8/8 题实际调用了 SMM 检索工具；第三方组 8/8 题实际调用了自己的检索工具。所有完整输入、输出、工具轨迹及前两次预检保存在上述本机目录。

最值得复核的两题说明了不同失败链路：

- **目录修订题：**你后来明确规定“非叶子目录不能直接关联原文；原文内容不变，只重归合适叶子”（原消息位置 10289）。SMM 找到并正确引用。原始文件组的命令输出中包含这句原文，但最终答案漏掉“非叶子不能挂原文”；第三方工具返回给 Agent 的结果没有出现这句，最终沿用较早的分类想法。
- **规模扩大题：**后来结论是 BM25 作为第一版基座，规模增大时优先用项目、领域等信息减少无关干扰（例如原消息位置 57644、79428、79433）。原始文件组找到并正确回答；两种工具都只给 Agent 较早的相关讨论，最终答成了“文档切分/目录导航”等中途方向。两工具返回内容中都未出现这些后期关键位置。

第二题暴露了 SMM 的具体实现短板：当前按整段对话做 BM25 后，每段对话只选最多 **3 条**匹配消息；选择规则先看命中查询词数量，分数相同时偏向较早消息。一个超长对话里，早期相近主题会挤掉后期结论。[当前实现](../src/smm_local/core.py)的这一步需要改进，再用未参与修复的新题验证。**不能把本次答错题修好后的重跑结果写回上表。**

## 结论边界

公开数据支持：SMM 可以帮助 Agent 找到并使用历史依据，在这 10 道有效题里观察到少量收益。真实项目显示：对于一段真实的超长历史对话，SMM 确实能找出处并答对多数题，但与直接检索原始文件的**正确题数持平**，同时暴露了后期结论容易被旧消息挤掉的短板。两组都只跑一次，同一 Agent 的随机性、人工选题和第三方 CLI 标志差异都会影响结果；耗时差异也不能直接外推。现有证据不足以宣称“同事用了就会稳定受益”，更不足以宣称“比成熟知识库更好”。正式公司试用仍需要更多真实使用者、多对话、多项目与跨 Agent 来源，并按[冻结的验收计划](utility-comparison-plan.md)执行。
