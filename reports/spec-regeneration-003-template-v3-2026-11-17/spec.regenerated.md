# 规格：汇总端同步 VibeInsight 对话并按关联项目检索

依据已确认的 [intent.md](intent.md)、补充决定及项目现有承诺起草。以下为交付要求，不代表已执行或通过验收。

## 预期行为

### 1. 配置与查看 VibeInsight 同步

Hub 维护者通过 Hub CLI 配置 VibeInsight 连接、只读凭据、同步周期和启用状态，并查看当前配置的脱敏状态、最近成功时间及失败原因。

配置前，维护者需向 VibeInsight 数据库维护者取得 PostgreSQL 主机、端口、数据库名、只读账户及密码，并确认：

- 该账户可读取的全部项目均获准归档到本 Hub；本次不提供项目同步名单或按项目移出操作。
- 部署中的 `fact_events` 包含适配器所需的 `id`、`created_at`、`user_id`、`platform_code`、`session_id`、`trace_id`、`event_type`、`event_timestamp`、`message`、`repo_hostname`、`repo_port`、`repo_path` 字段，并授予所需读取权限。
- Hub 服务运行账户能够执行 PostgreSQL 客户端 `psql`、访问数据库及读取保存凭据的位置。服务环境无法找到 `psql` 时，可指定其绝对路径。

配置入口为 `smm-hub hub vibeinsight configure`，连接参数包括 `--host`、`--port`、`--database`、`--user`，密码通过提示输入。同步周期默认 300 秒，可通过 `--interval` 调整。自定义状态目录通过 `hub --state-dir <状态目录>` 指定，并须与目标 Hub 服务使用的目录一致。

只有验证连接及所需读取权限成功后，新配置才替换有效配置。验证失败时报告原因，保留此前有效配置、凭据和同步进度。更换同一来源的凭据时沿用已有进度。

通过 `smm-hub hub vibeinsight status` 可检查同步状态。命令输出和日志不得显示秘密原值。凭据跨 Hub 服务重启保留，重启后无需重新输入。

### 2. 自动归档与持续同步

启用后，Hub 自动拉取连接可读取的全部项目及其历史对话，随后按配置周期同步新会话和旧会话追加的轮次。

首次发现的项目必须补齐历史，即使其事件时间早于已有同步进度，也不得因全局进度而遗漏。

同一来源会话追加消息时，沿用原汇总会话标识并保持来源顺序。重复事件按来源会话及消息标识去重，不生成重复消息。

同步失败时：

- 此前成功归档的对话继续可检索、可读取。
- 状态报告失败原因，不能将失败轮次报告为成功。
- 进度不得越过未成功归档的数据；恢复后重试未提交记录。
- 服务重启从已提交位置继续，不遗漏或重复归档消息。

没有新增事件的历史消息原地改写不在发现范围内，Hub 保留已归档的旧内容。

### 3. 上传和识别设备项目

本机端连接 Hub 后，上传对话的项目归属及稳定项目身份。已归档但没有新增消息的旧历史，也须补传项目归属，不能依赖新增消息触发。

Hub 项目列表区分来源、来源电脑、稳定项目身份及显示名，使维护者能够区分同名项目。设备项目修改显示名时，保留身份及已有关联。

VibeInsight 项目以仓库主机、端口和路径的组合确定身份。组合变化时形成新项目；旧归档及旧关联保留，新项目同步后可全局检索。维护者须为新项目重新建立所需关联。

### 4. 管理 Hub 项目关联

维护者在设备至少完成一次与 Hub 的同步、或 VibeInsight 项目已被发现后，通过 `smm-hub hub project list` 取得 Hub 项目 ID，并使用以下入口管理关系：

- `project links`：查看已保存的关联。
- `project link <项目ID> <项目ID>`：建立设备—设备或设备—VibeInsight 关联。
- `project unlink <项目ID> <项目ID>`：解除指定关联。

关联双向生效，仅扩展到已保存的直接一层关系；重复建立同一关系只保留一条。关联不改变对话的原项目归属。

例如 A 分别关联 B、C、D 后，按 A 检索包含 A 原有范围及 B、C、D；B 与其他项目的关联不会经 A 继续扩展。解除 A 与 C 后，A 的关联范围只保留 B、D，C 的归档仍可全局检索。

### 5. CLI/MCP 检索与读取原文

本机 CLI 和 MCP 在线按当前项目查询时，携带当前项目的稳定身份，由 Hub 查询当前项目及其直接关联项目。返回信息须表明使用了汇总端，并列出生效项目范围。

全局检索覆盖设备上传和 VibeInsight 同步的两类归档。旧客户端未提供项目范围的请求继续按全局检索处理。

命中结果提供来源、所属项目、原始会话及消息位置；设备来源还应保留来源电脑及 Agent 信息，VibeInsight 来源提供可定位的源事件位置。CLI 和 MCP 均可通过 Hub 与消息引用精确读回命中原文，既有旧引用继续可用。

Hub 不可用时，CLI 和 MCP 按现有行为回退到本机所有项目，并返回回退原因。用户显式选择本机查询时，继续使用本机项目关系。

## 边界与约束

- 首版沿用 Hub 单用户访问模式，不增加多用户隔离或新的授权体系。
- Hub 仅通过只读查询读取 VibeInsight，不修改来源数据库。全部可读项目均须获准归档，读取权限即同步范围边界。
- 本机端与 Hub 独立打包；本机 CLI/MCP 共用归档与检索逻辑。
- 本机端现有支持范围包含 macOS、Linux、Windows，本次项目身份补传及 CLI/MCP 行为须保持该范围。
- Hub 保持 Linux、Windows、macOS 的现有服务支持：Linux 为支持启动运行的 systemd 用户服务，macOS 为以配置账户运行的系统级 launchd 服务，Windows 为 LocalService 服务；同时保留自行管理进程的 `smm-hub serve-hub` 运行方式。
- 新增的 `psql` 依赖不得把上述服务支持范围隐式缩减为开发终端或某一操作系统。Windows 上仍须满足 LocalService 对运行环境的读取及执行要求。
- 保持既有 HTTPS、Hub 凭证、数据库、服务启停及升级保留状态的承诺。本次不要求改造这些既有功能，但新增配置、凭据和进度须能随既有服务生命周期持续使用。
- 本机 Web 功能扩展不在范围内；其仍管理本机档案和关联，在线 Hub 关联由 Hub CLI 管理。
- 不承诺发现未产生新增事件的历史内容改写。

## 设计决策

### 1. 来源读取与凭据保管

Hub 服务调用外部 `psql` 读取 `fact_events`。连接地址、周期和启用状态存于配置；秘密值存于 Hub 服务状态目录中的专用凭据文件，以操作系统权限限制访问。Hub 运行账户必须能读取，命令输出、日志和对话数据库不得包含秘密原值。

配置终端与实际服务的账户、环境变量及可执行文件搜索路径可能不同。因此，终端配置成功不足以证明服务同步可用；验收须覆盖各平台真实服务身份下的依赖执行、凭据读取及重启续跑。

### 2. 归档与进度提交

进度存于 Hub 数据库。每轮固定读取上界，按批次归档，归档数据与对应进度一同提交。以 `created_at` 和事件 `id` 组成续跑位置，同时间事件按 `id` 区分。

每轮回看近期记录以覆盖常见延迟提交，重复读取按来源标识去重。首次发现项目的历史补齐不能受已有全局进度截断。

以下事项仍需维护者在实施前确认：

- 近期回看的时间范围，以及预期覆盖的延迟提交边界。该值决定延迟事件验收样本和保证范围，不能据此承诺任意延迟均可发现。
- `--interval` 的合法取值范围及非法值处理，以形成可判定的配置行为。
- 启用状态的具体 CLI 操作入口，以及停用对在途轮次的处理规则。
- 更换连接目标时，如何识别“同一来源”，以及切换到不同来源时如何隔离进度和去重身份，避免误用旧进度。

这些决定影响交付行为和验收，不能留给 PLAN 自行决定。

## 验收条件

### 1. 环境覆盖及证据要求

以下环境必须取得实际通过证据，不能以单测、包构建或交互终端能启动替代：

| 受影响组件及运行环境 | 必须覆盖的行为 |
|---|---|
| Linux Hub，systemd 用户服务 | 实际服务账户执行 `psql`、读取受保护凭据、周期同步、失败恢复、重启续跑 |
| macOS Hub，系统级 launchd 服务及配置运行账户 | 同上，包含服务环境与配置终端环境差异 |
| Windows Hub，LocalService 服务 | 同上，包含可执行文件访问、凭据文件 ACL 及服务重启 |
| Hub，自行管理的 `serve-hub` 进程 | 使用同一状态目录配置启动、周期同步、停止后重启续跑 |
| macOS、Linux、Windows 本机端 | 项目身份与旧历史归属补传；CLI 和 MCP 的在线项目查询、全局查询、引用读取及回退 |

自行管理进程方式可在一个受支持平台验证其通用生命周期；各平台服务身份差异仍由前三项实际服务验收覆盖。无需将每种本机系统与每种 Hub 系统做笛卡尔积组合。

以下第 2 项中的服务生命周期判据须用于三个平台的实际 Hub 服务；第 5 项须用于三个平台的本机 CLI 和 MCP。归档排序、去重、关联集合等共用逻辑可用一套共用测试充分覆盖，并在至少一个实际 Hub 环境完成端到端验证；这只能证明共用逻辑，不能表述为其他平台已经实际执行了该套测试。

### 2. 配置、服务身份与故障恢复

在各平台实际 Hub 服务环境中，准备兼容的来源数据库、获准的可读项目和对应只读账户，取得以下结果：

- 服务运行账户可执行配置的 `psql`，启用后自动完成历史拉取，并按周期归档随后新增的消息。
- 服务环境无法通过默认路径找到客户端时，配置有效绝对路径后同步成功；依赖缺失、不可执行或数据库不可达时，状态给出可识别原因。
- 已有有效配置时，提交连接失败或读取权限不足的新配置，原配置仍有效，既有档案继续可读。
- 更换同一来源凭据并重启服务，无需重新输入密码，沿用进度继续同步。
- 在尚未提交的归档阶段发生失败或进程中断，恢复后补齐未提交记录，进度不越过缺失数据，且不重复消息。
- 最近成功时间、失败状态和脱敏配置与实际结果一致；凭据文件限制非授权账户访问，命令输出、日志及对话数据库均无秘密原值。

启用、停用及非法周期的验收须按实施前确认的规则补齐，缺少决定或证据时不能判定本项完成。

### 3. 历史补齐与增量归档

在实际 Hub 环境中，至少验证：

- 首轮归档全部可读项目的历史；无读取权限的项目不被归档。
- 已有同步进度后，新发现项目中早于该进度的历史仍完整进入 Hub。
- 新会话可检索；旧会话追加轮次后沿用原汇总会话标识，来源顺序正确。
- 相同 `created_at` 的不同事件均被归档；重复事件及回看重复读取不生成重复消息。
- 在已确认延迟边界内提交的事件经回看被补齐。
- 无新增事件的历史原地改写不覆盖已归档旧内容。

### 4. 项目归属、关联及身份变化

在 Hub 已含设备 A、设备 B 和 VibeInsight 项目 C、D 的条件下：

- 项目列表能区分来源、电脑、稳定身份及同名项目；无新增消息的旧设备历史补传后可按项目归属检索。
- 建立 A—B、A—C、A—D 后，列表中的关系唯一且双向；重复建立不增加记录。
- 按 A 查询覆盖 A 原有范围和 B、C、D，且不经 B、C、D 扩展到二层项目。
- 解除 A—C 后，A 查询排除 C 的独有关联范围，C 原归档及引用仍可全局检索和读取。
- 设备项目仅改显示名后，稳定身份、历史归属及关联不变。
- VibeInsight 仓库主机、端口或路径变化后形成新项目；旧归档和旧关联保留，新归档全局可查，重新建立关联后纳入当前项目查询。

### 5. 各平台 CLI/MCP 完整用户路径

在 macOS、Linux、Windows 的本机端，分别对 CLI 和 MCP 执行下列共用判据：

- 已连接 Hub 且当前项目具备直接关联时，在线项目查询携带稳定身份，返回当前项目及直接关联项目的命中，并注明 Hub 和生效项目范围。
- 显式全局查询可命中设备及 VibeInsight 两类来源；每类命中均显示来源、项目、原会话和消息位置，并可沿引用读回准确原文。
- 升级前保存的旧引用仍可读取。
- Hub 不可用时，查询覆盖本机所有项目并返回回退原因；Hub 恢复后，在线查询重新使用 Hub 范围。
- 显式本机查询遵循本机项目关系，不受 Hub 关联替代。
- 本机项目归属上传后，未新增消息的历史也可从 Hub 按对应项目检索。

另须以旧客户端无项目范围的请求验证 Hub 继续返回全局检索结果。

所有必需平台、运行方式及路径的证据齐备后方可判定交付通过。当前资料仅提供设计和使用说明，未提供任何已执行的验收结果。具体机器、命令、实施位置、测试步骤及 CI 配置写入 `plan.md`。
